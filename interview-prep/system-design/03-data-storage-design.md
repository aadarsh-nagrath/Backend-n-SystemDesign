# Data Storage & Data Modeling — System Design Interview Questions

---

### 1. How do you decide how to shard a large table in a system design interview, and what makes a shard key "good"?
A good shard key distributes both data volume and *query load* evenly across shards (avoiding hot shards — see the fundamentals file), and ideally keeps data that's commonly accessed/queried together on the same shard (to avoid expensive cross-shard queries/joins, which most sharded systems handle poorly or not at all). Common strategies: hash-based sharding (hash the key, e.g., user ID, to pick a shard — even distribution, but range queries across the shard key become inefficient since related values are scattered); range-based sharding (contiguous ranges of the key go to the same shard — efficient range queries, but risks uneven load if certain ranges are much hotter, e.g., sharding by date puts all of "today's" traffic on one shard). Always state which access patterns you're optimizing the shard key for, since there's no universally "best" key independent of query patterns.

### 2. How would you design a system to support both a sharded write path and a need for cross-shard aggregate queries (e.g., "total sales across all shards")?
Cross-shard queries are the classic pain point of sharding, since no single shard has the full picture. Options: maintain a separate, denormalized aggregate/analytics store updated asynchronously (via events/CDC from each shard) specifically for cross-shard reporting queries, decoupling analytical query needs from the transactional, per-shard operational data path entirely; or, for less frequent/lower-urgency aggregate needs, run a scatter-gather query (query every shard in parallel and combine results in the application layer) — acceptable for occasional/admin-facing queries but doesn't scale well as a frequent, latency-sensitive access pattern since it's bounded by the slowest shard and adds real complexity to the application layer doing the combining.

### 3. What is Change Data Capture (CDC), and what problem does it solve for keeping multiple data stores in sync?
CDC captures row-level changes (inserts/updates/deletes) from a database's own transaction/write-ahead log in near real time and streams them as events (often into a message queue like Kafka) — without requiring the application to explicitly publish an event for every single write (which is easy to forget in some code path, causing silent drift) and without adding load to the primary database beyond what it already does for its own durability logging. This is commonly used to keep a search index, a cache, a data warehouse, or a denormalized read-optimized view in sync with the primary transactional database's actual state, reliably and with minimal coupling to application code.

### 4. How would you design the data model for a "who follows whom" social graph at very large scale (e.g., billions of edges)?
A relational table (`follower_id`, `followee_id`) with indexes on both columns works at moderate scale, but at billions of edges with extreme skew (some accounts followed by tens of millions of others), you typically need a specialized approach: sharding the edge table (often by `follower_id`, since "who does X follow" is a common query, though "who follows X" for a celebrity becomes a genuinely hard, separately-optimized query at that scale) or using a purpose-built graph database/wide-column store designed for this access pattern. A key design decision to state explicitly: do you need real-time strong consistency for follow/unfollow actions, or can "your follower count updated a few seconds late" be acceptable (almost certainly the latter, given the read-heavy, tolerant-of-slight-staleness nature of this data) — this directly informs whether eventual consistency and heavy caching/denormalization (e.g., a separately maintained, approximate follower *count* rather than always computing it live from the edge table) is an acceptable and preferable tradeoff.

### 5. How would you design storage for a time-series workload (e.g., metrics/IoT sensor data ingesting millions of points per second)?
Time-series data has distinctive characteristics worth calling out explicitly: append-mostly writes (rarely updated after being written), queries typically scoped to a time range, and value naturally decreasing over time (older data is queried less frequently and can often be aggregated/downsampled or moved to cheaper storage). This favors a purpose-built time-series database (or a wide-column store like Cassandra, or specialized engines like InfluxDB/TimescaleDB) using time-based partitioning (each time bucket, e.g., per hour/day, becomes its own partition, making both writes and time-range reads efficient, and making old-data expiry/archival as simple as dropping whole old partitions rather than deleting individual rows). Downsampling/rollup (aggregating older raw data into coarser-granularity summaries, e.g., keeping raw per-second data for 7 days but only per-hour averages beyond that) is a standard technique to control storage growth for indefinitely-retained metric history.

### 6. How would you design a "unique username" or "unique email" constraint at scale across a sharded database, where uniqueness must be enforced across ALL shards, not just within one?
This is a specifically hard sharding problem, since a per-shard unique index only guarantees uniqueness *within* that shard, not globally. Approaches: shard specifically by the field that needs global uniqueness itself (e.g., shard users by a hash of username/email, so a uniqueness check/constraint only ever needs to look at one specific shard for that specific value — trading away the ability to shard by a different, possibly more query-convenient key like user ID); or maintain a separate, smaller, dedicated "reservation" service/table (potentially a single, simpler, non-sharded store, since it only needs to store the unique key itself, not the full user record) that's checked/written atomically at signup time before/alongside creating the full user record in the main sharded store.

### 7. How would you design a search feature (e.g., product search, full-text search over documents) at scale, and why not just use `LIKE '%term%'` on your primary database?
`LIKE '%term%'` (a leading wildcard) can't use a standard B-tree index at all — it forces a full table scan for every search, which becomes prohibitively slow at any meaningful data volume, and it has no concept of relevance ranking, typo tolerance, or language-aware tokenization (stemming, synonyms). A dedicated search engine (Elasticsearch/OpenSearch, or a managed equivalent) builds an inverted index (mapping each term to the documents containing it) specifically optimized for fast full-text search with relevance scoring, faceting/filtering, and typo tolerance — kept in sync with the primary database via CDC or application-level dual-writes/events (accepting some eventual-consistency lag between "data is saved" and "data is searchable," which is almost always an acceptable tradeoff for search specifically).

### 8. What's the difference between storing a large binary file (an image, a video) directly in a relational database (as a BLOB) vs. in object storage (S3) with just a reference/URL stored in the database?
Storing large binaries directly in a relational database bloats the database's size/backup time, competes for the database's memory/cache with your actual transactional data (making the database's cache less effective for the data that actually needs fast transactional access), and most relational databases simply aren't optimized for large-blob storage/retrieval at scale. Storing the file in purpose-built object storage (S3, GCS) and keeping only a reference (URL/key) in the database keeps the database small/fast and lets you take advantage of object storage's own strengths (cheap at scale, built-in CDN integration, lifecycle policies for tiered storage) — the database's role becomes purely metadata/reference management, which is what it's actually good at.

### 9. How would you design idempotent, exactly-once-effect processing for financial transactions across a distributed system (e.g., a payments ledger)?
Use an append-only ledger model (every transaction is an immutable recorded entry — a debit and a matching credit — rather than mutating a running balance in place) so the current balance is always a derived, recomputable sum rather than a single point of failure/corruption if a bug ever mutates it directly. Require a client-supplied idempotency key for any transaction-initiating request (see the backend fundamentals and API design files), enforced via a unique constraint at the database level (not just application-level checking, which has its own race conditions) so a retried request can never create a duplicate ledger entry even under concurrent retries. Use a real database transaction to atomically write both sides of a double-entry transaction (debit and credit) together, ensuring the ledger can never end up in a state with one side recorded but not the other.

### 10. How would you design a rate-limiter's own storage backend at scale (millions of distinct clients, high request rate)?
A distributed, in-memory key-value store (Redis, typically) is the standard choice — extremely fast reads/writes (needed since rate-limit checks happen on the hot path of every single request), and supports atomic increment-and-check operations (`INCR` plus a TTL, or a Lua script for more complex algorithms like a sliding window) needed to avoid race conditions in concurrent rate-limit checks from multiple application instances simultaneously. At very high scale, Redis itself may need to be sharded/clustered (rate-limit keys distributed across a Redis Cluster) or the rate-limiting logic pushed even further to the edge (a CDN/API gateway's own built-in rate limiting, avoiding a round trip to a centralized store entirely for the coarse-grained global limit, with a more precise centralized check only for tighter/business-specific limits).

### 11. How do you approach "estimate the storage required" questions (e.g., "how much storage does this system need for 5 years")?
Break it down explicitly: estimate the size of one typical record/item (sum its fields' byte sizes realistically, including any embedded media/metadata), multiply by expected daily/monthly volume, multiply by the retention period, and add a reasonable overhead factor for indexes, replication (multiply by replication factor, e.g., 3x for triple replication), and metadata. Present the calculation with clearly stated assumptions (the interviewer is testing your ability to reason quantitatively and structure an estimate, not your ability to recall an exact real-world number) — e.g., "if each post averages 1KB of text plus a 200KB average image, 10M posts/day, over 5 years, times 3x replication, that's roughly [show the arithmetic] ≈ X petabytes," explicitly noting that image/video storage typically dwarfs text/metadata storage by orders of magnitude, which itself is a useful design insight (object storage + CDN becomes the dominant cost/architecture concern, not the metadata database).
