## 1. Design Google Docs (a real-time collaborative document editor)

**Requirements**: Multiple users edit the same document simultaneously; every user sees others' changes in near real time; edits must converge to the same final document for everyone regardless of network timing/order; document history/versioning; offline editing that syncs on reconnect (stretch goal).

**High-level design**: Each client maintains a local copy of the document and connects via a persistent WebSocket connection (similar to the chat-app case study's gateway pattern) to a Document Service. As a user types, their client sends incremental *operations* (not the whole document) — e.g., "insert 'x' at position 12" — to the server, which broadcasts them to all other connected clients editing the same document, and each client applies incoming operations to its local copy. The document's canonical state is periodically persisted to a document store, with an append-only operation log as the actual source of truth for reconstructing any point-in-time version.

**Deep dive — the core hard problem: concurrent edit conflict resolution (OT vs. CRDTs)**: If two users edit the same region of a document at nearly the same time, naively applying "insert at position 12" from both clients (each computed against a slightly different, now-stale view of the document) produces different, diverging results on each client — the central problem this system must solve. Two established approaches: **Operational Transformation (OT)** — transforms an incoming operation against any operations that happened concurrently (that the sender didn't yet know about) before applying it, adjusting position indices so the operation still makes semantic sense against the current state — this is what Google Docs itself uses, but OT algorithms are notoriously complex to implement correctly for anything beyond plain text. **CRDTs (Conflict-free Replicated Data Types)** — structure the document's data so that operations are mathematically guaranteed to converge to the same result regardless of the order they're applied in, without needing a central server to mediate transformation — simpler to reason about correctness for, and enable true peer-to-peer/offline-friendly editing, at the cost of typically higher memory overhead (CRDTs often retain "tombstone" metadata for deleted content to preserve convergence guarantees).

**Deep dive — the role of a central server despite OT/CRDTs theoretically allowing peer-to-peer**: Even with a mathematically sound conflict-resolution algorithm, a central server is still valuable in practice as the single ordering authority (assigning a definitive sequence to concurrent operations, simplifying the transform logic considerably versus true fully-distributed peer-to-peer ordering) and as the durable persistence layer — most real collaborative editors use a "central server with OT/CRDT" hybrid rather than pure peer-to-peer, trading a small amount of decentralization purity for significantly simpler correctness reasoning and reliable persistence.

**Tradeoffs**: OT's implementation complexity and years of production hardening (Google's specific advantage) vs. CRDTs' simpler correctness model but higher memory overhead — a legitimate, real industry split worth naming explicitly, since there's genuinely no universally "correct" choice between them, only different tradeoffs different companies have made.

## 2. Design Dropbox / Google Drive (cloud file storage & sync)

**Requirements**: Users upload/store files and folders; files sync automatically across a user's multiple devices; support very large files efficiently; handle offline edits and conflicting concurrent edits from multiple devices; support sharing files/folders with other users.

**High-level design**: Files are chunked into fixed-size blocks client-side before upload; each block is content-hashed, and only blocks not already present in storage are actually uploaded (deduplication) — blocks are stored in object storage (S3-like), while a separate metadata service tracks each file's block list, version history, and folder structure in a database. A Sync Service on each client watches the local filesystem for changes, computes which blocks changed, and pushes/pulls only the delta rather than re-uploading/downloading whole files.

**Deep dive — block-level chunking and deduplication, and why it matters at scale**: Splitting files into content-addressed chunks (rather than treating a file as one indivisible blob) means: (1) editing a large file only requires re-uploading the specific changed chunks, not the whole file (dramatically reducing sync bandwidth for, say, a small edit to a large document); (2) deduplication across users — if two users upload the exact same file (or files sharing common chunks, like near-identical documents), the underlying storage is only kept once, referenced by both — a very significant storage-cost saving at the scale of hundreds of millions of users, many of whom store overlapping/duplicate content.

**Deep dive — sync conflict handling when a file is edited offline on two devices**: If a file is modified on device A while offline, and separately on device B (also offline or simply not yet synced), both changes arrive at the server as claiming to be based on the same prior version. The system must detect this divergence (comparing the base version each edit claims against the server's actual current version for that file) — for structured/mergeable content this could attempt an automatic merge (rare in general-purpose file storage, more common for text/code), but the standard, robust approach for arbitrary file types is to keep *both* versions (renaming one to something like `file (conflicted copy from Device A).docx`) and let the user manually resolve the conflict — an explicit, deliberate design choice favoring data safety (never silently discard a user's edit) over automatic-but-potentially-wrong merging.

**Tradeoffs**: Smaller chunk size increases deduplication effectiveness and sync granularity (less wasted bandwidth on small edits) but increases metadata overhead (more chunks to track per file) — chunk size is a genuine tunable tradeoff, and real systems (Dropbox has published details on this) have iterated on it based on real usage data rather than picking an arbitrary "obviously correct" size upfront.

## 3. Design a Ticketing/Event-Booking System (e.g., Ticketmaster)

**Requirements**: Users browse events and book specific seats; a seat can never be sold to two different people (the core correctness requirement); must handle extreme concurrent demand for popular events (thousands of users trying to buy the last few seats for a sold-out show simultaneously); payment must complete before a seat is permanently allocated, but a seat shouldn't be held indefinitely for someone who never completes checkout.

**High-level design**: An Event/Seat-map service holds each venue's seat inventory and current status (available/held/sold) per event. A booking flow: user selects seats → system places a short-lived, time-limited *hold* on those specific seats (e.g., 10 minutes) → user proceeds to payment → on successful payment, the hold is converted to a permanent sale; if payment fails or the hold expires first, the seats are automatically released back to available inventory.

**Deep dive — preventing double-booking the same seat under extreme concurrency (this is the entire point of the question)**: This is fundamentally the same overselling problem as the e-commerce inventory case study, but concentrated on far fewer distinct "items" (a finite, small number of seats) under far higher concurrent demand per item — making it an even sharper version of the same problem. Use an atomic, database-level conditional update to place a hold (`UPDATE seats SET status = 'held', held_by = ?, held_until = ? WHERE seat_id = ? AND status = 'available'`, checking the affected-row count) so only one of many simultaneous requests for the same seat can actually succeed — everyone else's request for that specific seat simply fails immediately and cleanly (the UI shows "that seat was just taken, please pick another"), rather than a race condition allowing two successful holds. At truly extreme scale for a single blockbuster event's on-sale moment, some real systems add a queueing/virtual-waiting-room layer in front of the booking flow entirely (admitting a controlled number of users into the actual booking system at a time) specifically to keep the seat-contention problem itself at a manageable concurrency level rather than trying to make the database layer alone withstand unlimited simultaneous demand.

**Deep dive — releasing expired holds reliably**: A hold that expires (payment never completed) must reliably return to "available" — implemented via a background job periodically scanning for and releasing expired holds, or, more precisely, by checking `held_until` as part of the *next* availability query itself (treating an expired-but-not-yet-cleaned-up hold as effectively already available) so there's no window where a seat appears falsely unavailable just because the cleanup job hasn't run yet.

**Tradeoffs**: Hold duration (too short frustrates legitimate users who need time to complete payment; too long lets a large fraction of inventory sit artificially "unavailable" from indecisive/abandoned sessions, especially damaging during high-demand on-sales) — most real systems tune this based on measured checkout-completion-time data rather than an arbitrary guess, and some show a visible countdown timer to the user specifically to reduce abandoned/idle holds.

## 4. Design a Payment Processing System (e.g., Stripe-like)

**Requirements**: Merchants integrate to accept payments from customers; must support multiple payment methods (cards, bank transfers); money must never be lost, duplicated, or double-charged (the paramount correctness requirement — see the idempotency discussion in the backend fundamentals file); must handle regulatory/compliance requirements (PCI DSS for card data); must reconcile correctly even across partial failures in a multi-step flow (charge attempt → authorization → capture → settlement).

**High-level design**: A Payment API (idempotent, requiring a client-supplied idempotency key on every charge request — directly the backend fundamentals file's Q8 applied at maximum stakes) receives a charge request, validates it, and orchestrates a flow through: authorization (checking the payment method has sufficient funds/credit, without yet moving money) with an external card network/bank → recording the transaction state transitions in an append-only ledger (see the data storage design file's Q9 on double-entry ledger modeling) → capture (actually moving the funds, which can happen immediately or be deferred, e.g., for a "pay on shipment" flow) → asynchronous settlement/payout to the merchant's bank account on a schedule (batched, not per-transaction).

**Deep dive — why raw card numbers should almost never touch your own servers (tokenization and PCI scope)**: Storing/handling raw credit card numbers brings an organization into the strictest tier of PCI DSS compliance (extensive, expensive security audits/controls). The standard architecture instead uses client-side tokenization: the customer's browser/app sends card details directly to the payment processor's own hosted, PCI-compliant endpoint (never touching the merchant's servers at all), which returns an opaque token — the merchant's backend only ever handles this token, never the real card number, dramatically reducing their PCI compliance scope (they're handling a token, not cardholder data) while the processor bears the full compliance burden for the sensitive data itself.

**Deep dive — designing for reconciliation and auditability above almost all else**: Every state transition (authorized, captured, refunded, failed, disputed) is recorded as an immutable, timestamped entry in an append-only ledger — never mutating a "current balance" field directly (see the same principle in the e-commerce case study's Q9 discussion) — so that at any point, the system's state can be fully reconstructed and verified against the ledger, and any discrepancy (a bug, a processor-side error, a dispute) can be traced to the exact transaction and state transition responsible. This auditability requirement is arguably the single most distinctive design driver for a payment system compared to almost any other case study — correctness and traceability dominate every other concern (latency, even availability, are secondary to "we can never lose track of where the money is").

**Tradeoffs**: Synchronous authorization (blocking the checkout flow until the card network responds, giving immediate success/failure feedback to the customer) vs. asynchronous settlement (never blocking the customer-facing flow on the slower, batch-oriented process of actually moving funds between banks) — real payment systems always split these: fast synchronous authorization for the user-facing experience, slow asynchronous settlement happening independently in the background, exactly mirroring the general sync-vs-async design principle from the fundamentals file, applied to a domain where getting this split wrong has direct financial consequences.

## 5. Design Airbnb (a two-sided marketplace: search, booking, and availability)

**Requirements**: Hosts list properties with availability calendars and pricing; guests search by location/dates/filters and book available properties; a property can never be double-booked for overlapping dates (the core correctness requirement, structurally similar to the ticketing system's seat-double-booking problem); search must support geographic + availability + many filter combinations efficiently at scale; both sides need reviews/trust signals.

**High-level design**: A Listings service stores property details/pricing; an Availability service tracks each listing's booked/blocked date ranges; a Search service (backed by a dedicated search index — see the data storage design file's search question) combines geographic filtering (using the geospatial indexing techniques from the ride-hailing case study — a grid/geohash-based index for "properties near this location") with availability filtering (excluding listings already booked for the requested date range) and other facets (price range, amenities, guest capacity). A Booking service handles the actual reservation, atomically checking and locking the requested date range against the listing's availability before confirming.

**Deep dive — preventing double-booking overlapping date ranges (structurally different from a single-seat lock)**: Unlike the ticketing system's single discrete seat, a booking here spans a *range* of dates — the conflict check must verify no existing confirmed (or currently-held) booking overlaps the requested check-in/check-out range at all, not just check an exact match. This is typically implemented with a database-level exclusion constraint (Postgres supports `EXCLUDE USING gist` constraints specifically designed for preventing overlapping ranges at the database level, atomically, rather than relying on error-prone application-level overlap-checking logic that's vulnerable to the same race conditions discussed throughout this document if two overlapping-date booking attempts race each other) — a great example of pushing a genuinely hard correctness guarantee down into the database's own constraint system rather than trying to hand-roll it correctly in application code under concurrency.

**Deep dive — search combining geographic, availability, and facet filtering efficiently**: A naive approach checking every listing's availability against a date range for every search query doesn't scale. Practical systems pre-compute/maintain a materialized, frequently-refreshed view of "available listings" segmented by date range and geography specifically to make the common search path (a specific location + date range + filters) a fast, mostly-precomputed lookup rather than a live join across separate listings/availability/bookings tables on every single search request — trading some data freshness (a booking made seconds ago might not have instantly propagated into the search index) for dramatically better search latency at scale, an explicit, deliberate consistency-vs-latency tradeoff worth naming directly (very similar in spirit to the CDC-fed search index pattern from the data storage design file).

**Tradeoffs**: Real-time inventory accuracy in search results vs. search latency/scalability (the precomputed-view approach above) — and, separately, how aggressively to "hold" a listing during the booking flow (a shorter hold reduces the window where a listing is falsely shown unavailable to other searchers, but a too-short hold risks the guest's payment/booking flow timing out before completion, again echoing the ticketing system's hold-duration tradeoff in a different domain).

## 6. Design Zoom (a video conferencing system)

**Requirements**: Support many participants in a live video/audio call with low latency; handle participants with widely varying network conditions/bandwidth gracefully; support screen sharing and recording; scale to large webinar-style calls (thousands of viewers, mostly one-way) as well as small multi-way meetings.

**High-level design**: For small calls, a peer-to-peer mesh (every participant sends their stream directly to every other participant) is theoretically simplest but scales terribly (each participant's upload bandwidth must support N-1 simultaneous outbound streams for N participants) — real large-scale systems instead route all media through centralized Selective Forwarding Units (SFUs): each participant sends *one* upload stream to the nearest SFU, which forwards (selectively, not necessarily to everyone at full quality — see deep dive) copies to every other participant, so a participant's upload bandwidth requirement stays constant (one stream) regardless of how many other participants are in the call.

**Deep dive — Selective Forwarding Unit (SFU) vs. Multipoint Control Unit (MCU) architecture**: An MCU (older approach) decodes every incoming stream, composites them into a single mixed video output (e.g., a grid layout), and sends one unified stream back to each participant — simpler for the client (just decode one stream) but extremely CPU-expensive server-side (real-time transcoding/compositing for every participant) and adds noticeable latency. An SFU instead just forwards each participant's stream as-is (no server-side transcoding) to other participants, whose own client software handles decoding and compositing the layout locally — far more server-efficient and lower-latency, at the cost of requiring more capable client-side processing and more total bandwidth (a client receiving many separate streams, though modern SFUs mitigate this via simulcast — see next). Nearly all modern video conferencing platforms (Zoom included) use SFU-based architectures for this efficiency reason.

**Deep dive — handling participants with wildly different network conditions (simulcast and adaptive bitrate for real-time video)**: A sender's client can encode and send *multiple* quality versions (simulcast — e.g., high, medium, low resolution) of its own outgoing stream to the SFU simultaneously; the SFU then selectively forwards the appropriate quality version to each individual receiving participant based on *that specific receiver's* current network conditions/bandwidth — a participant on a poor connection gets the low-quality version of everyone else's video without degrading the experience for participants on good connections, and without the sender needing any awareness of each individual receiver's conditions (the SFU handles that selection centrally, hence "selective forwarding"). This directly parallels the adaptive bitrate streaming technique from the video-streaming-platform case study, applied to live/real-time media instead of pre-recorded/on-demand video.

**Tradeoffs**: SFU architecture (efficient, scalable, but requires more capable client-side decoding of multiple streams) vs. MCU (simpler client, but expensive/higher-latency server-side compositing) — and for very large webinar-style broadcasts (thousands of mostly-passive viewers), many systems switch strategy entirely for that scale, falling back to a CDN-based one-to-many broadcast/streaming model (much higher latency, seconds rather than the sub-second latency of true interactive SFU-based calls, but capable of scaling to audience sizes an SFU's per-participant-stream-forwarding model couldn't reasonably support) — explicitly naming that "interactive small/medium calls" and "large one-to-many broadcasts" are different enough problems to warrant genuinely different underlying architectures within the same product is a strong, senior-level answer.
