# Data Structures & Algorithms — Conceptual Interview Questions

> Focused on concept/tradeoff questions (as asked in SDE screens and backend interviews), not raw coding problems — pair this with a practice platform (LeetCode/HackerRank) for hands-on problem drilling.

---

### 1. What's the time complexity of common operations on an array vs. a linked list, and when is each preferable?
Array: O(1) random access by index, O(n) insertion/deletion in the middle (must shift elements), contiguous memory (cache-friendly). Linked list: O(n) access by position (must traverse), O(1) insertion/deletion *once you have a reference to the node* (no shifting needed), but no random access and worse cache locality (nodes scattered in memory). Prefer arrays when you need frequent random access or the size is roughly known; prefer linked lists when you need frequent insertion/deletion at arbitrary known positions and don't need random access (though in practice, dynamic arrays' amortized append performance and cache friendliness make them the default choice in most modern code even for many list-like use cases).

### 2. Explain the time complexity of hash table operations, and why "O(1) average case" isn't the whole story.
Average-case O(1) for insert/lookup/delete, assuming a good hash function distributing keys evenly across buckets. Worst case is O(n) if many keys collide into the same bucket (a pathological hash function, or an adversarially crafted input designed to cause collisions — a real security concern for hash tables keyed by untrusted user input, mitigated by randomized hash seeds). Additionally, resizing the underlying array (when the load factor gets too high) is an O(n) operation, though amortized across many insertions it doesn't change the average-case O(1) analysis — but it does mean any *individual* insertion can occasionally be slow, which matters for latency-sensitive real-time systems even if throughput amortizes fine.

### 3. What's the difference between a stack and a queue, and give a real backend/systems use case for each.
Stack — LIFO (last in, first out); use case: function call stacks (tracking return addresses/local variables), undo functionality, depth-first traversal/backtracking algorithms. Queue — FIFO (first in, first out); use case: task/job processing in order of arrival, breadth-first traversal, and the conceptual basis for message queues in distributed systems (though real message queue implementations add much more — persistence, distribution, delivery guarantees — on top of the basic FIFO concept).

### 4. Explain Big-O, Big-Theta, and Big-Omega notation, in plain terms.
Big-O describes an upper bound on growth rate (worst case, or sometimes used loosely for "typical" growth) — "this algorithm takes at most roughly this much time as input grows." Big-Omega describes a lower bound (best case) — "this algorithm takes at least roughly this much time." Big-Theta describes a tight bound — both upper and lower bounds match, meaning the algorithm's growth rate is precisely characterized, not just bounded from one side. In casual industry usage, "Big-O" is often used loosely to mean "the tight/typical bound," even when Big-Theta would be the technically precise term.

### 5. Why is quicksort's average case O(n log n) but worst case O(n²), and how do real implementations mitigate the worst case?
Quicksort partitions around a pivot; if the pivot consistently splits the data roughly in half, you get O(n log n) (log n levels of partitioning, each doing O(n) work). If the pivot is consistently the smallest or largest element (e.g., naively always picking the first element as pivot on already-sorted or adversarially-crafted input), each partition only removes one element, degrading to O(n²) (n levels, each doing O(n) work). Mitigations: choosing a random pivot, or the "median of three" heuristic (sampling a few elements and picking their median as the pivot) — both make the pathological worst-case input pattern much harder to trigger accidentally or deliberately, though a true worst case is still theoretically possible with any fixed pivot-selection strategy (which is why some standard library sort implementations, like introsort, detect excessive recursion depth and fall back to a guaranteed-O(n log n) algorithm like heapsort if quicksort's recursion looks like it's degrading).

### 6. What's the difference between BFS and DFS, and when would you choose one over the other?
BFS (Breadth-First Search) explores level by level (all neighbors at the current depth before going deeper), using a queue — naturally finds the *shortest path* in an unweighted graph, since it discovers nodes in increasing order of distance from the start. DFS (Depth-First Search) explores as deep as possible along one path before backtracking, using a stack (or recursion) — better suited for exploring all possibilities exhaustively (e.g., detecting cycles, topological sorting, solving puzzles/backtracking problems) and generally uses less memory than BFS for a graph with high branching factor but limited depth (BFS's queue can hold an entire "frontier" level, which can be very wide).

### 7. Explain how a binary search tree (BST) works, and why an unbalanced BST degrades to O(n) operations.
A BST maintains the invariant that every node's left subtree contains only smaller values and its right subtree only larger values, enabling O(log n) search/insert/delete by eliminating half the remaining tree at each comparison — *if* the tree is reasonably balanced (roughly equal-depth on both sides). If elements are inserted in already-sorted order (or another pathological order), a naive BST degenerates into effectively a linked list (each node has only one child, all in one direction), making every operation O(n) instead of O(log n) — this is exactly why self-balancing variants (AVL trees, red-black trees) exist, which perform additional rebalancing work on insert/delete specifically to guarantee the tree never degrades into this worst case.

### 8. What is a heap, and why is it the natural data structure for implementing a priority queue?
A heap is a complete binary tree maintaining the heap property (in a min-heap, every parent is ≤ its children; max-heap, every parent is ≥ its children) — this guarantees the minimum (or maximum) element is always at the root, retrievable in O(1), with insertion and removal of the root both achievable in O(log n) (bubbling the changed element up/down to restore the heap property). This makes it ideal for a priority queue, where you repeatedly need "give me the highest-priority item next" efficiently — used in algorithms like Dijkstra's shortest path, scheduling systems, and the "top-K" family of problems (maintaining a heap of size K while streaming through a larger dataset).

### 9. What's the difference between a Trie and a hash table for storing/looking up strings, and when is a Trie preferable?
A hash table gives O(1) average lookup for an *exact* string match but offers no efficient way to find all strings sharing a given prefix (you'd need to check every stored string individually). A Trie (prefix tree) structures storage character-by-character, so looking up all strings with a given prefix is a natural, efficient traversal from that prefix's node in the tree — making it the preferred structure for autocomplete/typeahead features (see the system design case study), spell-checking, and IP routing tables (longest-prefix matching), at the cost of generally higher memory overhead per stored string than a hash table.

### 10. Explain dynamic programming, and what makes a problem a good candidate for it (the two conditions).
Dynamic programming solves a problem by breaking it into overlapping subproblems, solving each subproblem once, and storing (memoizing) its result to avoid redundant recomputation — trading memory for a often-dramatic reduction in time complexity versus naive recursion. A problem is a good DP candidate if it has: **optimal substructure** (an optimal solution to the problem can be constructed from optimal solutions to its subproblems) and **overlapping subproblems** (the same subproblems recur multiple times during a naive recursive solution — if subproblems don't overlap, plain recursion/divide-and-conquer is already efficient and memoization wouldn't help).

### 11. What's the difference between memoization (top-down DP) and tabulation (bottom-up DP)?
Memoization starts from the original problem and recursively breaks it down, caching each subproblem's result the first time it's computed so repeated calls with the same inputs return instantly — intuitive to write (looks like ordinary recursion, plus a cache) but can hit recursion-depth limits for very deep recursion, and only computes subproblems actually needed for the specific input. Tabulation builds up from the smallest base-case subproblems iteratively (typically filling in a table/array in a loop) until reaching the final answer — avoids recursion overhead/stack depth limits entirely, and can sometimes be optimized to use less memory (only keeping the last one or two rows of a table if that's all subsequent steps need), but requires figuring out the correct iteration order upfront rather than letting the natural recursive structure guide it.

### 12. What is the two-pointer technique, and give a canonical example of when it applies.
Using two indices/pointers that move through a data structure (often an array, often sorted) according to some logic, typically to avoid an O(n²) nested-loop brute-force approach, achieving O(n) instead. Canonical example: given a sorted array, find two numbers that sum to a target value — start one pointer at the beginning and one at the end; if the current sum is too large, move the right pointer left (decreasing the sum); if too small, move the left pointer right — each pointer moves at most n times total, giving O(n) instead of the O(n²) brute-force check of every pair.

### 13. What is the sliding window technique, and when does it apply?
Maintaining a "window" (a contiguous subrange) over a sequence that expands/contracts as you iterate, used for problems asking about contiguous subarrays/substrings satisfying some condition (e.g., "longest substring without repeating characters," "smallest subarray with sum ≥ target") — rather than re-examining every possible subarray from scratch (O(n²) or worse), the window incrementally adjusts (extending one end, and shrinking the other end when a condition is violated), typically achieving O(n) by ensuring each element is added to and removed from the window at most once across the whole traversal.

### 14. What's the difference between a greedy algorithm and dynamic programming, and when does greedy fail where DP succeeds?
A greedy algorithm makes the locally-optimal choice at each step without reconsidering past decisions, hoping (and, for specific *provably* greedy-compatible problems, guaranteeing) this leads to a globally optimal solution — fast and simple when it works, but it doesn't work for every problem. DP explores/considers the implications of different choices more thoroughly (via exploring subproblems and combining optimal subproblem solutions), guaranteeing a globally optimal answer for a broader class of problems, at higher time/space cost. Classic example where greedy fails but DP succeeds: the 0/1 knapsack problem — greedily always taking the item with the best value-to-weight ratio can produce a suboptimal result, because an earlier greedy choice can preclude a better combination that requires "sacrificing" that immediate best-ratio item; DP correctly considers the actual combinatorial tradeoffs.

### 15. Explain what a graph's adjacency list vs. adjacency matrix representation is, and the space/time tradeoff between them.
Adjacency list — for each node, store a list of its directly connected neighbors; space-efficient for sparse graphs (O(V + E) total space), but checking "are nodes A and B directly connected" requires scanning A's neighbor list (O(degree of A)) rather than a direct lookup. Adjacency matrix — a V×V grid where cell (i, j) indicates whether an edge exists between node i and j; O(1) edge-existence lookup, but O(V²) space regardless of how many edges actually exist, wasteful for sparse graphs (most real-world graphs, like social networks or web link graphs, are sparse — most pairs of nodes are NOT directly connected) but reasonable/preferred for dense graphs or when frequent O(1) edge lookups matter more than memory.

### 16. What is amortized time complexity, and give the classic example of a dynamic array's `append` operation.
Amortized analysis looks at the *average* cost per operation across a sequence of operations, even if any single operation can occasionally be much more expensive than others. A dynamic array (like Python's `list` or Java's `ArrayList`) doubles its underlying capacity when it fills up — that specific resize-and-copy operation is O(n), but it only happens rarely (after n/2 more cheap O(1) appends have occurred since the last resize), so when you average the cost of the occasional expensive resize across all the cheap appends that led up to it, the *amortized* cost per append works out to O(1) — even though a naive worst-case-per-operation analysis would (misleadingly) suggest O(n) for "the append that triggers a resize."

### 17. What's the difference between a stable and an unstable sorting algorithm, and why does stability matter practically?
A stable sort preserves the relative order of elements that compare as equal (e.g., sorting a list of people by last name — if two people share the same last name, a stable sort guarantees they remain in whatever relative order they were in before sorting, e.g., preserving a prior sort by first name). An unstable sort makes no such guarantee — equal elements might be reordered arbitrarily. This matters practically when you need to sort by multiple criteria in sequence (sort by first name, then stably sort the result by last name — the final result is correctly sorted by last-name-then-first-name only if the second sort is stable; an unstable second sort could scramble the first-name ordering among same-last-name entries).

### 18. Explain the concept of tail recursion, and why some languages optimize it while others (like Python) don't.
A recursive call is in "tail position" if it's the very last operation in a function (nothing else happens after it returns) — this allows a compiler/runtime to reuse the current function's stack frame for the recursive call instead of pushing a new one (since there's nothing left to do in the current frame after the call returns), effectively turning the recursion into a loop under the hood and avoiding stack-depth growth/overflow for deep recursion. Some languages/runtimes (Scheme, some functional languages, some JS engines under specific conditions) guarantee this optimization; Python's reference implementation (CPython) deliberately does not implement tail-call optimization (a long-standing, debated design decision, partly for the sake of clearer stack traces), meaning deep tail-recursive functions in Python will hit its default recursion limit and raise a `RecursionError` where an equivalent loop would run fine indefinitely.

### 19. What's the difference between depth-first and breadth-first when doing a topological sort of a DAG, and why must the graph be acyclic for topological sort to be defined at all?
A DFS-based topological sort performs a DFS, and prepends each node to the result order as the DFS finishes exploring all of that node's descendants (a node is only placed in the final order once everything it depends on/points to has already been fully processed) — reversing this "finish order" gives a valid topological ordering. A BFS-based approach (Kahn's algorithm) instead repeatedly removes nodes with no remaining incoming edges (in-degree zero), adding them to the result and decrementing the in-degree of their neighbors, repeating until all nodes are processed. A topological order (any linear ordering where every edge points from an earlier to a later node in the ordering) is only well-defined for a Directed Acyclic Graph — a cycle would require some node to simultaneously come "before" and "after" another node it's mutually dependent with, which is contradictory and impossible to satisfy in a linear ordering; both algorithms can be adapted to *detect* a cycle (a DFS revisiting a node still on its current call stack, or Kahn's algorithm terminating with nodes still remaining that never reached in-degree zero) as a useful side effect.

### 20. In a technical coding interview, what should you do before writing any code, and why does this matter more than jumping straight to a solution?
Clarify the problem's exact constraints and edge cases (what's the expected input size/range, are there duplicates, can input be empty/null, is the array sorted), state your intended approach and its expected time/space complexity out loud before coding, and consider whether a simpler brute-force solution is worth mentioning first even if you plan to optimize — this matters because interviewers are evaluating your *thinking process and communication*, not just whether the final code compiles; jumping straight into code without this often leads to solving the wrong problem, missing an edge case that surfaces late and causes a scramble, or appearing to guess rather than reason through the approach systematically — the same communication discipline that matters in system design interviews (see that file's Q1) applies here too.
