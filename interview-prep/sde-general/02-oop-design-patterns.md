# OOP Principles & Design Patterns — Interview Questions

---

### 1. Explain the four pillars of OOP: encapsulation, abstraction, inheritance, polymorphism.
**Encapsulation** — bundling data and the methods that operate on it together, and restricting direct external access to internal state (private fields accessed only via public methods) — protects invariants and lets internal implementation change without breaking external callers. **Abstraction** — exposing only the essential, relevant interface/behavior while hiding implementation complexity (e.g., a `Car` class exposing `drive()` without callers needing to know the engine's internals). **Inheritance** — a class can derive from (inherit fields/behavior of) another class, enabling code reuse and establishing an "is-a" relationship. **Polymorphism** — objects of different types can be treated through a common interface, with the actual behavior invoked depending on the object's real (runtime) type — letting calling code work generically against an interface/base type without needing to know every concrete subtype.

### 2. What's the difference between method overloading and method overriding?
Overloading — multiple methods in the *same* class share a name but differ in parameter types/count; resolved at compile time based on the arguments provided (compile-time/static polymorphism). Overriding — a subclass provides its own implementation of a method already defined in its superclass, with the same signature; which implementation actually runs is determined at runtime based on the object's actual concrete type (runtime/dynamic polymorphism) — this is what enables a base-class-typed reference to correctly invoke subclass-specific behavior.

### 3. Explain the difference between an abstract class and an interface, and when you'd choose one over the other.
An abstract class can provide some concrete (implemented) methods/fields alongside abstract (unimplemented) ones, and a class can only inherit from *one* abstract class (single inheritance in most mainstream OOP languages) — use it when subclasses share meaningful common implementation/state, not just a common contract. An interface (in languages that distinguish it from abstract classes) traditionally defines only method signatures with no implementation (though many modern languages now allow default method implementations in interfaces too) and a class can implement *multiple* interfaces — use it purely to define a contract/capability ("this can be compared," "this can be serialized") that unrelated classes can all satisfy without needing to share a common ancestor's implementation.

### 4. What is the Liskov Substitution Principle, and give a classic example of violating it.
A subtype should be substitutable for its base type without altering the correctness of the program — anywhere code expects the base type, a subtype instance should work correctly in its place. Classic violation: a `Square` class inheriting from `Rectangle` and overriding `setWidth`/`setHeight` to keep both sides equal (since a square must have equal sides) — this breaks any code that relies on `Rectangle`'s expected behavior that setting width and height independently should produce a rectangle with those exact, independent dimensions; substituting a `Square` where a `Rectangle` is expected silently violates that assumption, even though "a square is-a rectangle" seems intuitively true geometrically.

### 5. Explain the SOLID principles briefly.
**S**ingle Responsibility — a class should have only one reason to change (one well-defined responsibility). **O**pen/Closed — code should be open for extension but closed for modification (add new behavior via new code/subclasses rather than editing existing, working, tested code). **L**iskov Substitution — (see Q4) subtypes must be substitutable for their base types. **I**nterface Segregation — prefer several small, specific interfaces over one large, general-purpose one, so implementing classes aren't forced to implement methods they don't actually need/use. **D**ependency Inversion — depend on abstractions (interfaces), not concrete implementations — high-level modules shouldn't directly depend on low-level implementation details, both should depend on a shared abstraction (this is the principle underlying dependency injection, see the backend fundamentals file).

### 6. What is composition over inheritance, and why is it generally preferred as a default?
Composition builds behavior by combining/containing other objects (a `Car` *has-a* `Engine`) rather than inheriting from a base class (a `Car` *is-a* `Vehicle`). It's generally preferred because inheritance creates tight coupling to a specific base class's implementation (changes to the base class can unexpectedly break subclasses — the "fragile base class" problem) and is fixed at compile time (a class's inheritance hierarchy can't change at runtime), whereas composition is more flexible (you can swap out a composed component, even at runtime, for a different implementation satisfying the same interface) and avoids forcing an "is-a" relationship onto situations that are really more naturally "has-a" or "can-do" relationships.

### 7. Explain the Singleton pattern, and why it's often considered an anti-pattern in modern software design.
Singleton ensures a class has exactly one instance, globally accessible (typically via a static method). It's often criticized because it introduces hidden global state/dependencies (any code can reach into the singleton from anywhere, making dependencies non-obvious from a class's constructor/parameters, unlike explicit dependency injection), makes unit testing harder (you can't easily substitute a mock/fake for a hardcoded global singleton reference without extra indirection), and can cause subtle bugs in multi-threaded contexts if initialization isn't done carefully (thread-safe lazy initialization is a classic tricky-to-get-right problem). Most modern guidance favors dependency injection of a single shared instance (letting a DI container manage the "one instance" lifecycle) over a hardcoded Singleton pattern baked into the class itself.

### 8. Explain the Factory Method and Abstract Factory patterns, and the difference between them.
Factory Method defines an interface/method for creating an object, but lets subclasses decide which concrete class to actually instantiate — decouples the calling code from needing to know the exact concrete class being created. Abstract Factory provides an interface for creating *families* of related objects without specifying their concrete classes (e.g., a `UIFactory` that can produce a matching `Button`, `Checkbox`, and `Scrollbar` for a specific theme/platform, ensuring all created components are consistently from the same family) — essentially a factory of factory methods, one level more abstracted, used when you need to guarantee a set of related objects are created consistently together.

### 9. Explain the Strategy pattern, and give a backend-relevant example.
Strategy defines a family of interchangeable algorithms/behaviors behind a common interface, letting the calling code select and swap which concrete strategy to use at runtime without changing the calling code's structure. Backend example: a payment-processing service defining a `PaymentStrategy` interface with `processPayment()`, implemented separately by `CreditCardStrategy`, `PayPalStrategy`, `CryptoStrategy` — the order-checkout code just calls `strategy.processPayment()` against whichever concrete strategy was selected/configured for that specific order, without needing conditional branching logic scattered throughout the checkout code for every possible payment method.

### 10. Explain the Observer pattern, and how it relates conceptually to pub/sub messaging systems (see the message queues file).
Observer defines a one-to-many dependency where multiple "observer" objects are notified automatically whenever a "subject" object's state changes, without the subject needing to know the concrete details of its observers beyond a common notification interface. This is the same conceptual pattern underlying pub/sub messaging at a distributed-systems scale (see the message queues file) — the in-process Observer pattern and a distributed pub/sub message broker solve the same fundamental "decouple a state-change notifier from an unknown/variable number of interested parties" problem, just at very different scales and with very different reliability/delivery guarantees (an in-process Observer call is synchronous and immediate; a distributed pub/sub message is asynchronous and must handle network failure, delivery guarantees, and independent consumer scaling).

### 11. Explain the Decorator pattern, and how it differs from simply subclassing to add behavior.
Decorator wraps an object with another object implementing the same interface, adding behavior before/after delegating to the wrapped object — multiple decorators can be layered/composed at runtime in any combination (e.g., wrapping a base `DataSource` with an `EncryptionDecorator`, then a `CompressionDecorator`, in whatever order/combination is needed for a specific use case). This is more flexible than subclassing for adding optional, combinable behaviors, because subclassing would require a separate, explicitly-defined subclass for every needed *combination* of behaviors (an explosion of subclasses: `EncryptedDataSource`, `CompressedDataSource`, `EncryptedCompressedDataSource`, etc.), whereas decorators can be composed dynamically at runtime from a small set of independent decorator classes.

### 12. Explain the Adapter pattern, and give a real backend integration example.
Adapter converts the interface of an existing class into a different interface that calling code expects, letting otherwise-incompatible interfaces work together without modifying either side's original code. Backend example: integrating a legacy third-party payment SDK with an inconsistent/awkward API into your application's own clean, internal `PaymentGateway` interface — an Adapter class implements your internal interface while internally translating calls into whatever the legacy SDK actually requires, isolating the rest of your codebase from that SDK's specific quirks and making it easier to later swap in a different payment provider by writing a new Adapter rather than touching calling code throughout the application.

### 13. Explain the Repository pattern, and why it's commonly used in backend applications with a database.
A Repository provides a collection-like interface (e.g., `findById`, `save`, `delete`) for accessing domain objects, hiding the actual data-access/persistence details (SQL queries, ORM specifics, which specific database technology) behind that clean interface. This decouples business logic from data-access implementation details (aligning with the Dependency Inversion principle) — business logic depends only on the Repository's abstract interface, letting the underlying data store/ORM be swapped or the query implementation optimized without touching business logic, and, critically, letting tests substitute an in-memory fake Repository implementation instead of needing a real database for every unit test (see the testing file's discussion of test doubles).

### 14. What is the Builder pattern, and when is it preferable to a constructor with many parameters?
Builder constructs a complex object step by step, via a series of chained method calls that each set one aspect of the object being built, finishing with a `build()` call that produces the final, fully-constructed (often immutable) object. It's preferable to a constructor with many parameters (a "telescoping constructor" — multiple overloaded constructors trying to cover various combinations of optional parameters) because it makes construction code self-documenting (`user.setName("x").setAge(30).setEmail("y").build()` clearly shows what each value represents, unlike a long positional argument list where it's easy to accidentally swap two same-typed arguments) and cleanly handles many optional parameters without needing an unwieldy number of constructor overloads for every combination of which optional fields are provided.

### 15. Explain the Command pattern, and a backend use case (e.g., for implementing undo, or a job queue).
Command encapsulates a request/action as an object (with all the information needed to perform it later), rather than executing it immediately and directly — enabling the request to be queued, logged, passed around, delayed, or undone. Backend use case: representing a background job as a Command object (containing the action to perform and its parameters) that gets serialized and placed on a message queue, to be deserialized and executed later by a worker — decoupling *when/where* an action is decided from *when/where* it's actually executed, which is exactly the conceptual foundation of most job-queue/task-queue systems.

### 16. What is the difference between composition and aggregation in UML/OOP terms, and why does the distinction matter for object lifecycle management?
Both represent a "has-a" relationship between objects, but differ in ownership/lifecycle: in composition, the contained object's lifecycle is tightly bound to the containing object (e.g., a `House` composed of `Room`s — the rooms don't exist independently of that specific house, and destroying the house destroys its rooms). In aggregation, the contained object can exist independently and outlive the containing object (e.g., a `University` aggregates `Student`s — a student exists independently and continues to exist even if they leave/the university closes). This distinction matters practically for resource management/cleanup logic (does destroying/disposing the container need to also clean up its contained objects, or do they need to be handled independently since something else might still reference them) and for correctly modeling real-world domain relationships in a data model.

### 17. What is a design pattern anti-pattern warning sign — when might using a "named pattern" actually be over-engineering?
Applying a design pattern preemptively for flexibility you don't actually need yet (e.g., building an elaborate Strategy pattern with a pluggable interface for something that has, and will very plausibly always have, exactly one implementation) adds indirection and cognitive overhead without a corresponding real benefit — a sign of over-engineering is when explaining *why* a pattern was used requires justifying a hypothetical future need rather than a concrete, current one. Patterns are tools for managing genuine complexity/variability that actually exists in a problem, not a checklist to demonstrate "good OOP" — a simpler, more direct solution is usually better until the actual need for the pattern's flexibility materializes (a principle sometimes summarized as YAGNI — "You Aren't Gonna Need It").
