# Testing & Quality — Backend Interview Questions

---

### 1. Explain the differences between unit, integration, and end-to-end (e2e) tests, with a backend example of each.
**Unit test** — tests a single function/class in complete isolation (all dependencies mocked/faked); e.g., testing a `calculateDiscount(order)` function's logic with a hand-constructed order object, no real database involved. **Integration test** — tests how multiple components work together, typically including a real (or realistic, e.g., a test-container) dependency like a database; e.g., testing that a repository class correctly persists and retrieves an order from an actual test database. **End-to-end test** — tests a complete user-facing flow through the whole system as a black box, typically via its real external interface (an HTTP API call or a browser); e.g., placing an order through the public API and verifying the order appears correctly, the inventory decremented, and a confirmation email was queued.

### 2. What is a mock, a stub, and a fake — and when would you choose each?
**Stub** — a hard-coded, canned response to a specific call, with no logic (e.g., a stubbed `getUser()` that always returns a fixed user object regardless of input) — used purely to feed a test with needed input data. **Mock** — like a stub, but also records *how* it was called and lets the test assert on that interaction (e.g., "was `sendEmail` called exactly once, with these arguments") — used when the *behavior* of calling a dependency (not just its return value) is what you're actually verifying. **Fake** — a real, working (but simplified) implementation, not just a canned response (e.g., an in-memory database implementing the same interface as the real one) — used when you need genuinely correct behavior across many calls/interactions (not just one canned answer) without the overhead/flakiness of the real dependency.

### 3. What makes a unit test "good" — what should you avoid testing?
A good unit test is fast, deterministic (same result every run, no flakiness from timing/randomness/external state), isolated (doesn't depend on other tests' side effects or run order), and tests *behavior/outcomes* rather than *implementation details* (so refactoring the internal implementation without changing behavior doesn't break the test — a test that breaks on every internal refactor, even when the actual external behavior is unchanged, is testing the wrong thing and will actively discourage safe refactoring). Avoid testing private implementation internals directly, testing framework/library code itself (trust that `sort()` sorts — test your own logic that uses it), and writing tests so tightly coupled to exact internal call sequences that any reasonable refactor breaks many unrelated tests.

### 4. What's the difference between test coverage percentage and actual test quality, and why is "100% coverage" not itself a meaningful goal?
Coverage measures which lines/branches of code were *executed* during tests — it says nothing about whether the test actually *asserted* anything meaningful about the resulting behavior (a test that calls a function and asserts nothing, or asserts something trivially true, still counts as "covering" that code). 100% coverage can be achieved while missing important edge cases (a loop executed with one input value "covers" the loop body but may not test empty-input, single-item, or many-item edge cases) or while having weak/absent assertions — coverage is a useful signal for finding completely untested code (a floor, not a ceiling), not a proxy for confidence that the code is actually correct.

### 5. What is a flaky test, and what are the most common root causes in a backend test suite?
(See also the CI/CD file's flaky-test question.) Common backend-specific causes: relying on real wall-clock time/`sleep()` calls instead of properly waiting for/mocking async operations to complete; tests sharing mutable state (a shared test database not properly reset/isolated between tests, so test order or parallel execution affects results); relying on real network calls to external services (which can be slow, rate-limited, or genuinely down independent of your code's correctness); and non-deterministic ordering assumptions (e.g., asserting on the exact order of results from a query that doesn't have an explicit `ORDER BY`, where the database happens to usually — but not always — return them in insertion order).

### 6. How do you test code that depends on the current time (e.g., "is this token expired")?
Never call `new Date()`/`time.Now()` directly deep inside business logic if it needs to be testable — inject the current time as a parameter, or through an injectable "clock" abstraction, so tests can supply a fixed, controlled time value (e.g., "pretend it's exactly 2026-01-01T00:00:01Z") rather than relying on the real, constantly-changing system clock, which would make time-boundary tests (like "expires at exactly midnight") flaky or impossible to write reliably.

### 7. What is a test double for an external HTTP API, and what are the tradeoffs of different approaches (full mocking vs. a local sandbox/test double server vs. recorded fixtures like VCR/nock)?
Full manual mocking of the HTTP client (stubbing its methods directly) is fast and simple but tests less of the real integration (doesn't verify your code actually constructs correct requests/URLs/headers). A recorded-fixture approach (record real HTTP interactions once, replay them in tests — tools like VCR in Ruby, `nock` in Node, `vcrpy` in Python) verifies real request construction against previously-recorded real responses, is fast and deterministic in CI, but fixtures can silently go stale if the real API's behavior changes and nobody re-records them. A local sandbox/test-double server (a lightweight fake HTTP server implementing the same API contract) gives the most realistic integration testing without hitting the real external service, at the cost of having to build and maintain that fake server's behavior yourself. Choice depends on how critical/complex the integration is and how much realism is worth the added maintenance cost.

### 8. What is contract testing, and how does it differ from integration testing for microservices communication?
(Also covered in the API design file.) Integration testing typically requires spinning up real or realistic instances of both services together to verify they work correctly combined — powerful but slow, and only tests the specific versions you happened to spin up together. Contract testing verifies each side (consumer and provider) independently against an explicit, shared contract of expected requests/responses — the consumer's tests run against a mock based on the contract, and the provider's tests verify it actually satisfies that same contract — catching breaking changes without needing both services running together at all, and each side can run its verification in its own independent CI pipeline.

### 9. How would you write a good test for an endpoint that has side effects (sends an email, charges a payment) without actually sending real emails/charging real money in every test run?
Inject the email/payment client as a dependency (dependency injection) so tests can substitute a fake/mock implementation that records "an email would have been sent with these parameters" or "a charge would have been attempted for this amount" without actually performing the real external action — then assert on what the fake recorded, rather than on any real-world side effect. For true end-to-end tests that need higher confidence the real integration works, use the payment/email provider's official sandbox/test-mode environment (most major providers offer one specifically for this purpose) rather than either skipping that layer of testing entirely or accidentally sending real emails/charges during CI runs.

### 10. What is property-based testing, and how does it differ from example-based (traditional) unit testing?
Example-based testing asserts specific expected outputs for specific hand-chosen input examples (`assert add(2, 3) == 5`). Property-based testing instead defines a general *property* that should hold true for a wide range of inputs (e.g., "for any two integers, `add(a, b) == add(b, a)`" — commutativity), and a framework (Hypothesis in Python, QuickCheck-derived libraries in many languages) automatically generates many varied (including edge-case, e.g., zero, negative, very large) inputs to try to find a counterexample that breaks the property — often uncovering edge cases a human wouldn't have thought to write an explicit example for, complementing (not replacing) example-based tests for specific known important cases.

### 11. What is mutation testing, and what problem does it solve that code coverage doesn't?
Mutation testing deliberately introduces small artificial bugs ("mutants" — e.g., changing a `>` to `>=`, or a `+` to `-`) into the code and re-runs the test suite against each mutant; if the tests still pass despite the introduced bug, that's a signal the tests aren't actually verifying that specific piece of logic meaningfully (a coverage report would still show that line as "covered," since it was executed — mutation testing catches that it was executed but not actually *effectively asserted on*). It's a stronger (though computationally much more expensive, since it requires running the full test suite once per mutant) signal of real test quality than coverage alone.

### 12. How would you approach load/performance testing a new API endpoint before it goes to production?
Establish realistic traffic patterns and volume expectations first (based on projected usage, not arbitrary numbers) using a load-testing tool (k6, Locust, JMeter, Gatling) that can simulate concurrent virtual users ramping up gradually. Measure latency percentiles (not just averages — see the observability file's discussion of why p99 matters) and error rates under increasing load to find the actual breaking point/capacity ceiling, and check resource utilization (CPU, memory, DB connections, downstream dependency load) at each load level to identify *which* component becomes the bottleneck first, rather than just knowing "it broke at X requests/sec" without knowing why — that "why" is what tells you what actually needs to be fixed/scaled.

### 13. What's the difference between smoke testing, regression testing, and exploratory testing?
**Smoke testing** — a minimal, fast set of checks confirming the absolute basics work after a build/deploy, before investing time in more thorough testing (see the CI/CD file). **Regression testing** — re-running previously-passing tests after a change to confirm the change didn't break existing functionality that used to work — the primary job of an automated test suite run in CI on every change. **Exploratory testing** — a manual, unscripted process where a tester actively investigates the system looking for unexpected behavior/edge cases without a predefined test script, relying on tester intuition and creativity to find issues automated tests weren't specifically written to catch — complementary to, not a replacement for, automated regression testing.

### 14. How do you decide what to test at the unit level vs. the integration level for a piece of backend code that involves both business logic and a database call?
Separate the business logic from the data-access code as much as possible (e.g., a pure function that takes already-fetched data and decides what to do, versus a repository/data-access layer that fetches/persists it) — unit test the business logic in isolation with fabricated input data (fast, many cases, no database needed), and write a smaller number of integration tests specifically to verify the data-access layer actually interacts correctly with a real (or realistic test) database (correct SQL, correct handling of constraints/edge cases the database itself enforces) — this separation lets you get the bulk of your test coverage from fast, cheap unit tests while still verifying the genuinely risky "does this actually work against a real database" question with a smaller, more expensive set of integration tests, following the testing pyramid principle (see the CI/CD file).
