# Concurrency, Multithreading & Async — Interview Questions

---

### 1. What's the difference between concurrency and parallelism?
Concurrency is about *structure* — dealing with multiple tasks that are in progress at overlapping times, potentially interleaved on a single core (making progress on each without necessarily running simultaneously at the same instant). Parallelism is about *execution* — actually running multiple tasks at the exact same instant on multiple cores/processors. A single-core system can be concurrent (via time-slicing/context switching) but not parallel; a multi-core system enables true parallelism for CPU-bound work, while concurrency (via async I/O, for instance) is valuable even on a single core purely by better utilizing idle time spent waiting on I/O.

### 2. Explain a mutex vs. a semaphore.
A mutex (mutual exclusion lock) allows only one thread to hold it at a time, protecting a critical section so only one thread executes it concurrently — it has an owner (the thread that locked it must be the one to unlock it, in most implementations). A semaphore maintains a count and allows up to N threads to proceed concurrently (a "counting semaphore"; a "binary semaphore" with count 1 behaves similarly to a mutex but typically without an ownership concept, meaning any thread can release it, not just the one that acquired it) — used to limit concurrent access to a pool of N interchangeable resources (e.g., allowing at most 10 concurrent connections to a limited external resource).

### 3. What is a race condition vs. a data race — are they the same thing?
A data race specifically refers to two or more threads accessing the same memory location concurrently, with at least one being a write, without proper synchronization — this is technically undefined behavior in many languages (C/C++) and can corrupt data in ways beyond just "wrong logical result" (torn reads/writes). A race condition is a broader term for any situation where the correctness of a program depends on the relative timing/interleaving of events — it can happen even with individually safe/atomic memory operations if the *logic* built on top of them isn't atomic (e.g., the check-then-act stock example from the backend fundamentals file uses individually safe reads and writes, but the overall read-then-write sequence is still a race condition, even without a low-level "data race" on any single memory access).

### 4. Explain deadlock, livelock, and starvation.
**Deadlock** — two or more threads are each waiting on a resource the other holds; nobody makes progress, permanently, unless something external intervenes (timeout, forced abort). **Livelock** — threads are actively responding to each other (not blocked/waiting) but never actually make forward progress — e.g., two threads each repeatedly yielding a shared resource to be "polite" to the other, but neither ever actually takes and uses it, endlessly. **Starvation** — a thread is perpetually denied the resources/CPU time it needs to make progress, not because of a deadlock/livelock, but because other threads are consistently prioritized ahead of it (e.g., a low-priority thread that never gets scheduled because higher-priority threads are always runnable) — the thread isn't stuck logically, it's just never actually given the chance to run.

### 5. Name the four conditions (Coffman conditions) required for a deadlock to occur, and how a system might break one to prevent deadlocks.
Mutual exclusion (resources can't be shared, only held exclusively), hold and wait (a thread holds one resource while waiting for another), no preemption (a resource can't be forcibly taken from a thread holding it), and circular wait (a cycle of threads each waiting on the next). Breaking any one prevents deadlock — the most common practical approach is eliminating circular wait by enforcing a global, consistent lock-acquisition order across all code paths (if every thread always acquires lock A before lock B, never the reverse, a circular wait can never form).

### 6. What is a critical section, and why should it be kept as small as possible?
A critical section is the portion of code that accesses shared state and must be protected from concurrent execution by more than one thread at a time (typically via a lock). It should be kept as small/short as possible because anything inside it serializes execution — other threads needing the same lock must wait — so a large or slow critical section (e.g., doing an I/O operation while holding a lock) drastically reduces achievable concurrency and increases the risk/duration of contention, even though functionally a larger critical section might be "simpler" to write correctly.

### 7. What is a thread-safe data structure, and are Java's `ArrayList`/Python's `list` thread-safe by default?
A thread-safe data structure can be correctly accessed/modified by multiple threads concurrently without external synchronization, because its internal operations are properly synchronized/atomic. Neither Java's `ArrayList` nor Python's plain `list` is thread-safe for concurrent modification — concurrent writes (or a write concurrent with iteration) can corrupt internal state or throw exceptions (`ConcurrentModificationException` in Java is actually a *best-effort detection*, not a guarantee — true corruption is still possible); thread-safe alternatives (`Collections.synchronizedList`, `CopyOnWriteArrayList`, `java.util.concurrent` collections in Java; using explicit locks, or preferring message-passing/queues over shared mutable collections in Python) must be used explicitly for concurrent access.

### 8. Explain the producer-consumer pattern and why a bounded queue between them matters.
Producers generate work items and consumers process them, decoupled via a shared queue so producers and consumers don't need to run at the same pace or know about each other directly. A *bounded* queue (with a maximum capacity) is important because it provides natural backpressure — if consumers fall behind, the queue fills up and producers block/are slowed down (rather than an unbounded queue letting producers pile up unlimited work in memory, risking OOM if consumers can never catch up) — turning a potential unbounded-memory-growth failure mode into a controlled, visible slowdown instead.

### 9. What's the difference between `async`/`await` and traditional callback-based asynchronous code?
Callback-based async code registers a function to be called upon completion of an async operation, but chaining several sequential async operations via callbacks leads to deeply nested, hard-to-read code ("callback hell") and awkward error propagation (each callback needs its own error handling, rather than a single try/catch covering a whole sequence). `async`/`await` (built on promises/futures underneath) lets asynchronous code be *written* in a linear, sequential-looking style while still being non-blocking under the hood — the runtime suspends the `async` function at each `await` point and resumes it when that awaited operation completes, without blocking the underlying thread, while error handling can use ordinary try/catch across the whole sequence just like synchronous code.

### 10. Is `async`/`await` in JavaScript/Python true parallelism? Explain what's actually happening under the hood.
No — `async`/`await` provides *concurrency*, not parallelism, for I/O-bound work on a single thread (in JavaScript's single-threaded event loop, or Python's `asyncio` single-threaded event loop). When you `await` an I/O operation, control returns to the event loop, which can run other pending work while the I/O completes in the background (handled by the OS/runtime), and your function resumes once its result is ready — many logical tasks make progress "at once" from an outside perspective, but only one piece of your JavaScript/Python code is actually executing at any given instant. True CPU parallelism still requires actual multiple threads/processes (Web Workers in JS, `multiprocessing` in Python).

### 11. What is a promise/future, and what states can it be in?
A promise (JavaScript) / future (many other languages) represents the eventual result of an asynchronous operation that may not have completed yet. States: **pending** (not yet resolved or rejected), **fulfilled/resolved** (completed successfully, with a value), **rejected** (failed, with an error/reason) — once settled (fulfilled or rejected), a promise's state and value are final and won't change again, which is what lets `.then()`/`await` reliably attach a handler that will definitely eventually run exactly once with the final outcome.

### 12. What is a common bug pattern with `async`/`await` and loops — e.g., using `forEach` with async callbacks in JavaScript?
`Array.prototype.forEach` does not await or respect returned promises from its callback at all — `arr.forEach(async (item) => { await doSomething(item); })` fires off all the async callbacks essentially concurrently/immediately and `forEach` itself returns synchronously right away, without waiting for any of them to actually finish — a very common bug when a developer expects sequential processing (or at least for the calling code to wait for all items to be processed before continuing). Correct approaches: a plain `for...of` loop with `await` inside for true sequential processing, or `Promise.all(arr.map(item => doSomething(item)))` for correctly-awaited concurrent processing.

### 13. What is `Promise.all` vs `Promise.allSettled` vs `Promise.race`, and when would you use each?
`Promise.all` resolves when *all* input promises resolve (with an array of their results), but rejects immediately as soon as *any* one of them rejects (short-circuiting, ignoring the outcome of the others) — good when you need every operation to succeed and any single failure should be treated as an overall failure. `Promise.allSettled` waits for *all* promises to settle (whether fulfilled or rejected) and returns the outcome of each individually, never short-circuiting — good when you want to know the result of every operation regardless of whether some failed (e.g., firing off notifications to five services and wanting to know which specific ones failed, without aborting/losing information about the others). `Promise.race` resolves/rejects as soon as the *first* promise settles (whichever finishes first, success or failure) — useful for implementing a timeout pattern (race the real operation against a timer promise that rejects after N seconds).

### 14. Explain optimistic locking vs. pessimistic locking in the context of concurrent updates to shared application state (not just databases).
(See also the database file's Q7 for the DB-specific framing.) In application-level shared state, pessimistic locking means acquiring an actual lock (mutex) before reading/modifying shared state, blocking other threads for the duration — safe but limits concurrency and risks deadlock if multiple locks are involved. Optimistic approaches instead use atomic compare-and-swap style operations (read a value and a version/expected-current-value, then attempt an atomic update only if nothing else changed it in between, retrying if it did) — better throughput under low contention since threads don't block each other while merely reading, though it requires the underlying platform/language to support atomic compare-and-swap primitives and the retry logic adds its own complexity.

### 15. What is a lock-free data structure, and what makes it hard to implement correctly?
A lock-free data structure allows concurrent access without using locks/mutexes, instead relying on atomic hardware operations (compare-and-swap) to make progress — guaranteeing that *some* thread always makes progress even if others are paused/delayed (unlike a lock, where a thread holding it and getting descheduled can stall every other thread waiting on it). It's hard to implement correctly because you must reason about every possible interleaving of concurrent operations without the simplifying guarantee a lock provides (that only one thread is "in" the critical section at a time) — subtle issues like the ABA problem (a value changes from A to B and back to A between a thread's read and its compare-and-swap, making the CAS incorrectly appear to succeed as if nothing changed) require careful additional handling (versioned pointers/tags) that's easy to get wrong, which is why lock-free structures are typically written by concurrency specialists and used via well-tested libraries rather than hand-rolled per-project.

### 16. In a web backend, why can a single slow synchronous database call in an otherwise async framework block far more than just that one request?
In an async, single-threaded (or few-threaded) event-loop-based server, if a call is made *synchronously* (blocking) rather than through the async I/O mechanism the framework expects, it blocks the entire event loop thread for its duration — meaning *every other concurrent request* being handled by that same event loop is also stalled, not just the one that made the slow call, because there's no other thread available to make progress on them in the meantime. This is why using a blocking database driver (or any blocking library call) inside an async framework like Node.js or Python `asyncio` is a serious anti-pattern — always use the async-native version of the client library, or explicitly offload genuinely blocking calls to a separate thread/worker pool so they don't stall the shared event loop.

### 17. What's the difference between horizontal request concurrency (many simultaneous requests) and concurrency *within* handling a single request (e.g., fetching from 3 services in parallel to build one response)?
The former is about a server handling many independent requests from different clients simultaneously (the server's overall throughput/scaling concern). The latter is about a single request's handler internally kicking off multiple independent sub-operations (calls to different downstream services/data sources needed to assemble one response) concurrently rather than sequentially, to reduce that single request's own total latency (e.g., `Promise.all`-ing three independent API calls instead of awaiting them one after another) — both are legitimate and often necessary simultaneously in the same system, but they solve different problems (system throughput vs. individual request latency) and are optimized somewhat independently.
