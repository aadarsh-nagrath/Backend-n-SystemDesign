# API Design: REST, GraphQL, gRPC — Interview Questions

---

### 1. What makes an API "RESTful"? Name the key constraints.
REST (Representational State Transfer) constraints: client-server separation; statelessness (each request contains all info needed, no server-side session state between requests); cacheability (responses explicitly indicate if/how they can be cached); a uniform interface (resources identified by URIs, manipulated through representations, self-descriptive messages, HATEOAS); a layered system (client can't necessarily tell if it's talking directly to the origin server or an intermediary like a proxy/gateway); and optionally code-on-demand. In practice, most "RESTful APIs" implement the uniform-interface/resource idea and statelessness but skip HATEOAS entirely — which is common enough that "REST" in industry usage often just means "resource-oriented HTTP JSON API," a looser definition than Roy Fielding's original dissertation.

### 2. What is HATEOAS, and why is it rarely fully implemented in practice?
HATEOAS (Hypermedia as the Engine of Application State) means API responses include links describing what actions/related resources are available next (like a web page's hyperlinks), so a client can navigate the API dynamically without hardcoding URL structures/knowing every endpoint in advance. It's rarely fully implemented because it adds real complexity (designing and maintaining a hypermedia format, client tooling that actually follows links dynamically rather than hardcoding endpoints) for a benefit (loose coupling to URL structure) that most internal/first-party API consumers don't strongly need, since they're built and deployed in lockstep with the API anyway.

### 3. Explain proper use of HTTP methods in a REST API: GET, POST, PUT, PATCH, DELETE.
`GET` — retrieve a resource, no side effects, safe to cache and retry freely (idempotent). `POST` — create a new resource (or trigger a non-idempotent action); not idempotent (calling it twice typically creates two resources). `PUT` — replace a resource entirely with the given representation; idempotent (calling it N times with the same body results in the same end state). `PATCH` — partially update a resource (only the specified fields); not necessarily idempotent depending on the patch format (a JSON Patch "increment" operation wouldn't be, a simple "set field X to value Y" would be). `DELETE` — remove a resource; idempotent (deleting an already-deleted resource is still "gone" either way, though the HTTP status code returned on a repeat call might differ, e.g. 404 vs 204).

### 4. What does "idempotent" mean precisely for an HTTP method, and why does it matter for retry logic?
An idempotent method produces the same server-side end state no matter how many times an identical request is repeated (the *response* to each call can differ, e.g., a `DELETE` returning 200 then 404, but the resulting state on the server is the same). It matters for retries because a client (or an intermediate proxy/load balancer) that doesn't get a response due to a network issue can safely retry an idempotent request without risking unintended side effects (like creating duplicate resources) — this is exactly why `POST` (non-idempotent) typically needs an explicit idempotency-key mechanism to be safely retryable, while `PUT`/`DELETE`/`GET` are inherently safe to retry.

### 5. How should a well-designed REST API handle pagination? Compare offset-based and cursor-based pagination.
Offset-based (`?page=3&limit=20` or `?offset=40&limit=20`) — simple to implement and understand, supports jumping to an arbitrary page, but has correctness issues under concurrent writes: if items are inserted/deleted while paginating, offsets shift and a client can see duplicate or skipped items across pages, and it becomes slow on large datasets (`OFFSET 1000000` in SQL still has to scan/skip that many rows). Cursor-based (`?after=<opaque_cursor>&limit=20`, where the cursor encodes the last seen item's sort key, e.g. its ID or timestamp) — stable under concurrent inserts/deletes (each page is defined relative to a specific item, not a shifting numeric position), and efficient at any depth (`WHERE id > cursor_id ORDER BY id LIMIT 20` uses an index directly) — the standard choice for large, frequently-changing, or infinite-scroll-style datasets, at the cost of not supporting random access to an arbitrary page number.

### 6. How do you design API error responses well? What should a good error body contain?
Use the appropriate HTTP status code as the primary, machine-checkable signal (don't return 200 with an error described only in the body). Include a structured, consistent error body across the whole API: a machine-readable error code/type (stable, documented, so client code can branch on it reliably — not just parsing a human-readable message string), a human-readable message (for logs/debugging, and often safe to show users for simple cases), and, for validation errors, field-level details (which specific field failed and why) so a client can surface precise feedback rather than a generic "something went wrong." Avoid leaking internal details (stack traces, internal file paths, raw database errors) in production error responses — that's both a security and professionalism issue.

### 7. What is over-fetching and under-fetching, and how does GraphQL address them compared to REST?
Over-fetching: a REST endpoint returns more fields than the client actually needs (e.g., a full user object when the UI only needed the display name), wasting bandwidth/parsing. Under-fetching: a REST endpoint doesn't include enough related data, forcing the client to make several additional round-trip requests to assemble what it needs (e.g., fetch a post, then separately fetch its author, then separately fetch its comments). GraphQL addresses both by letting the client specify exactly which fields (across potentially several related resources/types) it wants in a single query, resolved server-side in one round trip — the client gets exactly what it asked for, no more, no less, and doesn't need multiple sequential requests to gather related data.

### 8. What is the N+1 query problem in GraphQL (or any ORM-backed API), and how is it typically solved?
If a query fetches a list of N parent objects, and resolving each parent's related child data triggers a separate database query per parent (rather than one batched query for all children at once), you end up with 1 query for the parents plus N queries for children — N+1 total, scaling linearly (and expensively) with list size. In GraphQL specifically, this is commonly solved with the DataLoader pattern: instead of each resolver immediately firing its own query, requests for related data within the same request/tick are batched together and deduplicated into a single query (`WHERE id IN (...)`) before being distributed back to each individual resolver's result.

### 9. What are GraphQL's main tradeoffs compared to REST (not just its advantages)?
Caching is significantly harder — REST's `GET` responses map naturally onto HTTP/CDN caching by URL, while GraphQL typically uses a single `POST` endpoint with a query in the body, so standard HTTP caching doesn't apply out of the box (requiring specialized client-side caching like Apollo/Relay's normalized cache, or persisted-query techniques). Query complexity is client-controlled, which can be a performance/DoS risk (a client can request an expensive, deeply nested query) requiring query complexity analysis/depth limiting server-side. It also adds a real learning curve and server-side implementation complexity (schema design, resolver implementation, the N+1 problem) compared to a simple REST CRUD endpoint, and file uploads/streaming are comparatively awkward in the standard GraphQL request/response model.

### 10. What is gRPC, and why might you choose it over REST/JSON for service-to-service communication?
gRPC is an RPC framework using Protocol Buffers (a compact binary serialization format) over HTTP/2, with a strongly-typed contract (a `.proto` file) that generates client/server code in many languages. Advantages over REST/JSON for internal service-to-service calls: significantly smaller payload size and faster serialization (binary vs. text JSON), built-in support for streaming (client-streaming, server-streaming, bidirectional) over HTTP/2 multiplexed connections, and a strict, code-generated contract that catches many integration mismatches at compile time rather than at runtime. Tradeoffs: not natively browser-friendly (requires gRPC-Web + a proxy for browser clients), less human-readable/debuggable on the wire (binary, not plain-text JSON you can eyeball in a network tab), and a steeper tooling/learning curve — generally preferred for internal, high-throughput/low-latency microservice communication, while REST/JSON (or GraphQL) remains more common for public-facing/browser-facing APIs.

### 11. What is Protocol Buffers (protobuf), and how does schema evolution work with it (adding/removing fields safely)?
Protobuf defines a message's structure in a `.proto` schema file, compiled into typed code for serialization/deserialization; each field has a unique numbered tag (not just a name) that's what's actually encoded on the wire, not the field name itself. Safe schema evolution: adding a new field with a new tag number is safe (old clients simply ignore it, and it defaults to its zero-value/absent if an old message without it is read by new code); removing a field should reserve its tag number/name (`reserved 5, "old_field_name";`) rather than reusing it for something else, since old serialized data or old clients might still reference that tag, and reusing it for an incompatible type would cause silent misinterpretation; changing a field's type or its tag number is generally unsafe and breaking.

### 12. What's the difference between REST resource-oriented design and RPC-style API design, and where does gRPC fit?
Resource-oriented (REST) design centers on nouns (resources: `/users/123/orders`) manipulated via a small, standard set of HTTP verbs. RPC-style design centers on verbs/actions directly (`createUser`, `cancelOrder`, `getUserOrders`) as explicit named operations, which maps more naturally onto arbitrary business operations that don't cleanly fit a CRUD-on-a-resource model (e.g., "reconcile these two accounts" isn't naturally a `PUT`/`PATCH` on a single resource). gRPC is fundamentally RPC-style (you literally define and call named service methods) — well-suited to internal service APIs that are largely action/operation-oriented rather than needing REST's resource/caching semantics.

### 13. How do you design an API to support idempotent retries for a non-idempotent operation like "create an order" (`POST`)?
Require the client to generate and send a unique idempotency key (e.g., a UUID) with the request (commonly as a header, `Idempotency-Key: <uuid>`). The server records, per key, that it has processed this exact request and what the result was; if a request arrives with a key it has already seen (e.g., a client retry after a timeout, unsure if the original request succeeded), the server returns the *original* stored result instead of executing the operation again — the client can safely retry a `POST` without the server-side operational risk of duplicate execution, as long as it reuses the same idempotency key for retries of the same logical attempt (and generates a new key for a genuinely new, separate order).

### 14. How would you design rate limiting into a public API, and what should the response look like when a client is rate limited?
Choose a limiting algorithm (token bucket is common — allows reasonable burstiness while enforcing a sustained rate, see the networking file's rate-limiting question), scoped per API key/client (not just per IP, since many legitimate clients can share an IP behind NAT, and a malicious client can rotate IPs). Return `429 Too Many Requests` with a `Retry-After` header (or `X-RateLimit-Remaining`/`X-RateLimit-Reset` headers) so well-behaved clients know exactly how long to wait before retrying rather than hammering the API immediately again, and document the limits clearly so legitimate API consumers can design their usage (and their own backoff logic) around them upfront.

### 15. What's the difference between authentication schemes commonly used in APIs: API keys, OAuth 2.0 bearer tokens, and mTLS?
API keys — a simple static secret string identifying the calling application/client, easy to implement but typically all-or-nothing (limited fine-grained scoping) and risky if leaked (long-lived unless manually rotated) — suited for simple server-to-server or low-security use cases. OAuth 2.0 bearer tokens (often JWTs) — support delegated authorization (a user grants a third-party app limited access to their account without sharing their password), fine-grained scopes, and typically short expiry with a refresh mechanism — the standard for user-delegated API access (e.g., "let this app read your calendar"). mTLS — both client and server present certificates, providing strong, mutually-verified cryptographic identity, well-suited to service-to-service communication in a zero-trust internal architecture, though less practical for third-party/public API consumers who'd need to manage client certificates.

### 16. What is API contract testing (e.g., Pact), and what problem does it solve in a microservices architecture?
Contract testing verifies that a service (the "provider") actually satisfies the expectations a consuming service (the "consumer") has of its API — the consumer defines a contract (specific requests it will make and the responses it expects), and this contract is verified against the real provider's implementation, independently of end-to-end integration tests. It solves the problem of expensive, slow, flaky full end-to-end tests being the only way to catch "service A changed its API in a way that breaks service B" — contract tests catch this at the API boundary, fast and in isolation, without needing to spin up the entire system together, and can run as part of each service's own independent CI pipeline.

### 17. When designing a public API, how do you handle deprecating an old version/field without breaking existing integrators?
Announce deprecation well in advance with a clear timeline, and mark deprecated fields/endpoints explicitly in documentation and, where the format supports it, in the response itself (e.g., a `Deprecation` HTTP header, or a `"deprecated": true` field). Keep the deprecated version/field fully functional throughout the announced sunset period rather than degrading it silently. Monitor actual usage of the deprecated version (via API key/client analytics) to know who's still depending on it and can be proactively contacted before removal, rather than discovering active usage only after removal breaks someone in production. Prefer additive changes and a new version only for genuinely breaking changes, since every version bump imposes a real migration cost on every downstream integrator.
