# Backend Security & Authentication — Interview Questions

> Complements `devops/11-security-devsecops.md` (which covers OWASP Top 10, encryption, secrets) with backend-implementation-specific questions.

---

### 1. Walk through a typical username/password authentication flow, end to end, done correctly.
Client submits credentials over HTTPS. Server looks up the user by username/email, retrieves the stored password *hash* (never a plaintext password — nothing should ever store one), hashes the submitted password with the same algorithm/salt and compares (using a constant-time comparison to avoid timing attacks on the comparison itself, though this matters less than it once did since the hash comparison is on already-hashed values, but is still good practice). On success, issue a session token or JWT representing the authenticated identity; on failure, return a generic error (not "wrong password" vs. "user doesn't exist" separately, which would let an attacker enumerate valid usernames) and apply rate limiting/lockout after repeated failures to slow down brute-force attempts.

### 2. Explain session-based authentication vs. token-based (JWT) authentication, and the core tradeoff between them.
Session-based: server creates a session record (in memory, or more commonly a shared store like Redis) on login, and gives the client an opaque session ID (typically via a cookie); every subsequent request's session ID is looked up server-side to retrieve the actual session data. Token-based (JWT): the server issues a signed token containing the claims directly; the server can verify it (checking the signature) without any server-side lookup/storage at all. The core tradeoff: sessions are trivially revocable (delete the server-side record, and the session is immediately invalid everywhere) but require a shared, available session store and a lookup on every request; JWTs are stateless and fast to verify (no lookup, easy to scale/verify by any service holding the public key/secret) but are hard to revoke before their natural expiry (since the server doesn't track "which tokens are still valid" anywhere by default) — a real security/operational tradeoff, not just a style preference.

### 3. How do you revoke a JWT before its expiry if JWTs are stateless by design?
There's no way to do this with pure, fully-stateless JWTs — any real solution reintroduces some server-side state, defeating pure statelessness to some degree: maintain a denylist of revoked token IDs (`jti` claim) checked on each request (a lightweight lookup, much smaller than a full session store but still a lookup); keep JWT expiry very short (minutes) paired with a separate, revocable refresh token (stored server-side, checked on each refresh) used to mint new short-lived access tokens — so even an un-revoked-but-compromised access token has a small, bounded window of danger; or, for a lower-security-need scenario, simply accept that instantaneous revocation isn't achievable and rely on short expiry as the primary mitigation.

### 4. What's the difference between access tokens and refresh tokens in OAuth 2.0?
An access token is short-lived and used directly to authenticate API requests (its short lifetime limits the damage if it's leaked/intercepted). A refresh token is longer-lived and used only to obtain new access tokens once the current one expires, without requiring the user to log in again — it's used much less frequently (only on refresh, not on every API call) and should be stored more securely (e.g., in an `HttpOnly` cookie or secure storage, never exposed to client-side JavaScript) since its compromise has much longer-lasting consequences than an access token's compromise.

### 5. Explain the OAuth 2.0 Authorization Code flow (with PKCE) at a high level, and why it's preferred for browser/mobile apps over the older Implicit flow.
The user is redirected to the authorization server (e.g., "Log in with Google") and authenticates there; on success, the authorization server redirects back to the app with a short-lived authorization *code* (not a token). The app's backend then exchanges this code (plus a PKCE code verifier, if used) for the actual access/refresh tokens via a direct, non-browser-exposed server-to-server call. This is preferred over the older Implicit flow (which returned the access token directly in the browser's URL fragment) because the token never appears in browser history/URLs/logs and is never directly exposed to potentially-compromised client-side JavaScript — PKCE (Proof Key for Code Exchange) additionally protects public clients (mobile/SPA apps that can't safely hold a client secret) by ensuring only the same app instance that initiated the flow can redeem the authorization code, preventing a stolen authorization code from being usable by an attacker.

### 6. What's the difference between authentication delegation (OAuth) and identity/authentication itself (OpenID Connect)?
OAuth 2.0 is fundamentally an *authorization* delegation framework — it lets an app get limited access to a resource on a user's behalf (e.g., "read my calendar"), without necessarily proving *who* the user actually is beyond that they successfully authorized access. OpenID Connect (OIDC) is built *on top of* OAuth 2.0 specifically to add a standardized *authentication*/identity layer — an ID token (a JWT with standardized claims like `sub`, `email`, `name`) that securely tells the app who the authenticated user actually is, which is what "Sign in with Google/GitHub" (as opposed to just "grant access to my data") is actually built on.

### 7. Where should you store a JWT/session token on the client, and what are the security tradeoffs of each option?
`localStorage` — accessible via JavaScript, meaning any successful XSS vulnerability on the page can read and exfiltrate it entirely; not protected by `SameSite` cookie mechanisms since it isn't a cookie at all. An `HttpOnly` cookie — inaccessible to JavaScript (mitigating XSS token theft specifically), automatically sent by the browser on matching requests, but vulnerable to CSRF unless paired with `SameSite` attributes and/or an anti-CSRF token, since the browser will auto-attach it even to a request initiated by a malicious third-party page. In-memory (a JS variable, not persisted at all) — safest against both XSS-exfiltration-for-later-use and CSRF, but the token is lost on page refresh, requiring a refresh-token flow (often itself in an `HttpOnly` cookie) to silently re-obtain a new access token after a reload. There's no single "always correct" answer — it depends on which specific threat (XSS vs. CSRF) a given application is more exposed to/hardened against.

### 8. How do you implement rate limiting to defend against a brute-force login attack, without locking out legitimate users unfairly?
Rate limit login attempts per account (e.g., after 5 failed attempts, require a delay or CAPTCHA before allowing more attempts on that specific account) and separately/additionally per source IP (to catch distributed attempts across many accounts from one attacker), since limiting only by account lets an attacker still hammer many different accounts from one IP, while limiting only by IP lets a distributed/botnet attacker bypass it entirely by spreading attempts across many IPs. Use exponentially increasing delays rather than a hard, long lockout (a hard lockout itself becomes a denial-of-service vector — an attacker can deliberately lock out a legitimate user's account just by repeatedly failing their login), and notify the account owner (via email) of suspicious repeated failed login activity.

### 9. What is multi-factor authentication (MFA), and what's the difference between TOTP, SMS-based, and hardware-key (FIDO2/WebAuthn) MFA in terms of security?
MFA requires a second, independent proof of identity beyond a password (something you know) — typically something you *have* (a device/key) or something you *are* (biometrics). **SMS-based** — a code sent via text message; convenient, but vulnerable to SIM-swapping attacks (an attacker socially engineers a mobile carrier into porting the victim's number to an attacker-controlled SIM) and SS7 network interception — considered the weakest common MFA method. **TOTP** (Time-based One-Time Password, e.g., Google Authenticator) — a shared secret established at enrollment generates a time-synchronized rotating code on the user's device, with no network transmission needed to generate/verify it, avoiding SIM-swap risk but still theoretically phishable (a fake login page could relay a real-time TOTP code to the real site in a live man-in-the-middle attack). **FIDO2/WebAuthn hardware keys** — use public-key cryptography bound to the specific origin/domain requesting authentication, making them phishing-resistant by design (a credential registered for `real-site.com` simply won't work/respond for `fake-site.com`, unlike a TOTP code a user could be tricked into typing into the wrong site) — the strongest widely-deployed option.

### 10. What is a timing attack, and how could it apply to a naive password/token comparison?
A timing attack infers secret information by measuring how long an operation takes, when the operation's execution time varies based on the secret value being compared. A naive string comparison (`==` in many languages, byte-by-byte, returning as soon as a mismatch is found) takes measurably longer the more *leading* characters of a guess match the real secret — an attacker who can measure response times precisely enough (feasible especially for local/low-jitter-network scenarios, and even remotely with enough statistical sampling) can incrementally guess a secret one character at a time by observing which guesses take slightly longer. Fix: use a constant-time comparison function (which compares the *entire* length regardless of where a mismatch occurs) for any comparison involving secrets (API keys, tokens, MAC/signature verification) — most languages provide one specifically for this purpose (`hmac.compare_digest` in Python, `crypto.timingSafeEqual` in Node.js).

### 11. What is CORS, and what security problem does it actually solve (and not solve)?
CORS (Cross-Origin Resource Sharing) is a browser-enforced mechanism that controls whether JavaScript running on one origin (domain) is allowed to read the response of a request made to a *different* origin. It exists because browsers, by default, allow a page to *send* a cross-origin request (the same-origin policy historically only restricted reading the response, not making the request itself) — CORS headers (`Access-Control-Allow-Origin`, etc.) let a server explicitly opt certain origins into being allowed to read its responses via JavaScript. What it does NOT solve: CORS is not a server-side authorization mechanism, and it does nothing to stop a request from being sent at all (a malicious page can still cause the browser to *send* a cross-origin request, e.g., a form submission or an image tag GET — this is exactly the CSRF problem, which CORS doesn't address; CORS only controls whether the *response* can be read back by the initiating page's JavaScript) — misconfiguring CORS (e.g., reflecting any `Origin` header back with `Access-Control-Allow-Origin: *` combined with allowing credentials) is a real, common vulnerability, but CORS itself is fundamentally a browser-JS-response-reading control, not a general request-authorization mechanism.

### 12. How would you securely implement a "forgot password" flow?
Generate a single-use, cryptographically random (not guessable/sequential) reset token with a short expiry, store only its hash server-side (so a database leak alone doesn't expose valid reset tokens directly, mirroring password storage practice), and email a link containing the raw token to the account's registered email address (never reveal via the API response whether a given email exists in the system at all, to avoid account enumeration). On the reset page, verify the token (matches, unexpired, unused) before allowing a new password to be set, then immediately invalidate that token (single use) and, ideally, invalidate all existing sessions/tokens for that account (in case the account was compromised and this is a legitimate owner regaining control) and notify the user via email that their password was changed.

### 13. Why should you never log sensitive data (passwords, tokens, full credit card numbers) even at DEBUG level?
Log files/aggregation systems often have broader access (many engineers, third-party log-management vendors, retained for long periods, sometimes with looser access controls than the production database itself) than the primary datastore — logging a secret anywhere significantly widens its exposure surface, and it's a common way credentials leak (a DEBUG log line temporarily left in during development, forgotten, then deployed to production and captured by a log aggregator, exactly as happened in several notable real-world incidents like Twitter's 2018 plaintext-password-in-logs disclosure). Sensitive fields should be explicitly redacted/masked in logging middleware (e.g., automatically scrubbing fields named `password`, `token`, `ssn`, `card_number`) as a systemic safeguard rather than relying on every individual developer remembering not to log them.

### 14. What is input validation vs. output encoding, and why do you need both, not just one?
Input validation checks that incoming data conforms to expected format/constraints (rejecting or sanitizing clearly invalid input early) — but it can't be relied on alone as your only defense against injection-style attacks, because validation rules can have gaps/edge cases, and the same piece of data might be used safely in one context but dangerously in another later on. Output encoding/escaping transforms data appropriately for the specific context it's being emitted into right before that emission (HTML-escaping for HTML output, parameterization for SQL, URL-encoding for a URL) — this is what actually prevents injection at the point of use, and should be applied regardless of whether input validation "should have" already caught something, as defense in depth (never trust that upstream validation was sufficient/bug-free).

### 15. How do you design authorization checks so a bug can't accidentally grant access rather than accidentally deny it (fail-safe defaults)?
Default to denying access unless a specific, explicit rule grants it ("deny by default, allow-list what's permitted") rather than the reverse ("allow by default, deny-list what's forbidden") — a bug/oversight in a deny-by-default system results in an over-restrictive but *safe* failure (a legitimate user is annoyingly blocked, a bug report gets filed, and it's fixed), whereas the same class of bug in an allow-by-default system results in an under-restrictive, *dangerous* failure (an unauthorized user silently gains access, potentially undetected for a long time). This "fail-safe" principle is why authorization middleware/frameworks are typically designed so that forgetting to add an authorization check for a new endpoint results in that endpoint being inaccessible (an obvious, immediately-noticed bug) rather than accessible-to-everyone (a silent, dangerous security hole).
