# Backend Fundamentals — Interview Questions

---

### 1. Explain the request-response lifecycle for a typical web backend (from request arriving to response leaving).
Request arrives at a server/load balancer → routed to an application process → the web framework's middleware chain runs (parsing, auth, logging, CORS) → routing matches the request to a specific handler/controller → the handler executes business logic (often involving DB queries, cache lookups, calls to other services) → a response object is constructed (status code, headers, body) → response middleware runs (e.g., adding security headers, compressing the body) → response is sent back through the load balancer to the client.

### 2. What is statelessness in the context of a backend server, and why does it matter for scaling?
A stateless server doesn't retain any client-specific session data in its own memory between requests — any instance can handle any request, because all the information needed to process it is either in the request itself (e.g., a token) or in an externalized shared store (a database, a distributed cache like Redis) rather than that specific server's local memory. This matters for horizontal scaling because a load balancer can freely distribute requests across any instance without needing "sticky sessions" tied to whichever server happens to hold a user's in-memory session state, and any instance can be replaced/restarted without losing user session data.

### 3. What's the difference between synchronous and asynchronous processing in a backend, and when do you use each?
Synchronous processing blocks and waits for an operation (e.g., a DB query, an external API call) to complete before continuing — simple to reason about, appropriate when the client genuinely needs the result before it can proceed (e.g., "did my payment succeed"). Asynchronous processing hands off work (to a background job queue, a message broker) and returns immediately, with the actual work completing later — appropriate for anything that doesn't need to block the user's response (sending a confirmation email, generating a report, processing an uploaded video) or for scaling throughput by decoupling request-handling capacity from processing capacity.

### 4. Explain blocking vs. non-blocking I/O, and how an event-loop-based runtime (like Node.js) achieves high concurrency on a single thread.
Blocking I/O halts the calling thread until an operation (disk read, network call) completes, wasting that thread's capacity to do anything else meanwhile. Non-blocking I/O initiates the operation and returns immediately, with completion signaled later (a callback, a promise, an event) — the thread is freed to handle other work in the meantime. An event-loop runtime (Node.js, or Python's asyncio) uses a single thread that continuously processes a queue of ready callbacks/events, delegating actual I/O operations to the OS/kernel (or a thread pool for things that are inherently blocking, like some filesystem calls) — this lets one thread handle thousands of concurrent I/O-bound connections efficiently, since it's never sitting idle waiting on any single I/O operation, though it means a single CPU-bound computation can block the entire event loop and stall every other concurrent request.

### 5. What is a thread pool, and why do most backend servers use one instead of spawning a new thread per request?
A thread pool maintains a fixed (or bounded, dynamically-sized) set of reusable worker threads that pick up incoming work from a queue, rather than creating a brand-new OS thread for every single request. Spawning a thread per request doesn't scale — thread creation/teardown has real overhead, and each thread consumes memory (its stack) and adds context-switching overhead, so under high concurrent load an unbounded per-request-thread model can exhaust memory or degrade performance due to excessive context switching long before the actual application logic becomes the bottleneck; a bounded pool caps resource usage predictably and queues excess work rather than letting the server collapse under unbounded thread creation.

### 6. What is a race condition, and give a concrete backend example.
A race condition occurs when the correctness of a result depends on the unpredictable timing/interleaving of concurrent operations. Example: two concurrent requests both read a product's stock count as 1, both decide there's enough stock, and both decrement it and confirm the order — resulting in two orders fulfilled from only one unit of actual stock, because the read-then-write wasn't atomic and both requests interleaved between the read and the write. Fixes include database-level atomic operations (`UPDATE ... SET stock = stock - 1 WHERE stock > 0`, checking the affected row count), row-level locking, or optimistic concurrency control (version numbers checked at write time).

### 7. What's the difference between optimistic and pessimistic concurrency control?
Pessimistic concurrency control locks a resource before reading/modifying it, preventing any other transaction from touching it until the lock is released — safe but can hurt throughput under contention (other transactions wait). Optimistic concurrency control assumes conflicts are rare: it reads data along with a version number/timestamp, and when writing, checks that the version hasn't changed since it was read (`UPDATE ... WHERE id = ? AND version = ?`) — if another transaction modified it in between, the write fails and the caller retries with fresh data, rather than blocking upfront. Optimistic is generally preferred when conflicts are actually infrequent (better throughput, no lock contention/deadlock risk), pessimistic when conflicts are common or the cost of a failed/retried operation is high.

### 8. Explain idempotency in an API context, and why it matters for payment/order endpoints specifically.
An idempotent operation produces the same result (and has the same effect) no matter how many times it's performed with the same input. It matters for payment endpoints because network failures are inherent to distributed systems — a client might send a "charge $50" request, the server processes it successfully, but the response is lost in transit; the client, seeing no response, retries. Without idempotency, this naive retry double-charges the customer. The standard fix is an idempotency key: the client generates a unique key per logical operation and sends it with the request; the server records which keys it has already processed and, on a retry with the same key, returns the original result instead of re-executing the operation.

### 9. What is a deadlock, and give a simple two-resource example?
A deadlock occurs when two or more processes/transactions each hold a resource the other needs, and each is waiting for the other to release its resource — neither can proceed. Example: Transaction A locks row 1, then tries to lock row 2; Transaction B, running concurrently, has already locked row 2 and is now trying to lock row 1 — both wait forever for the other. Most databases detect this automatically and abort one of the transactions (a "deadlock victim") to break the cycle; the calling application must be prepared to catch this and retry. Prevention includes always acquiring locks in a consistent, agreed-upon order across all code paths.

### 10. What's the difference between vertical and horizontal partitioning of a system's responsibilities (as opposed to database sharding)?
Vertical partitioning (in an architectural sense) splits a system by *feature/domain* — e.g., separate services for users, orders, payments — each owning its own logic and data (this is essentially the basis of a microservices decomposition). Horizontal partitioning replicates the *same* functionality across multiple instances to handle more load (e.g., running 10 identical copies of the order service behind a load balancer) — vertical partitioning is about dividing *what* different parts of the system do, horizontal is about dividing *how much load* any one part can handle.

### 11. What is backpressure, and why does a backend system need a mechanism for it?
Backpressure is a mechanism for a system to signal upstream ("slow down, I can't keep up") when it's receiving work faster than it can process it, rather than silently accepting unbounded work and eventually collapsing (unbounded memory growth from a growing queue, or cascading timeouts). Concretely: a message queue consumer that's falling behind should let queue depth (and, ideally, an active signal) inform upstream producers or an autoscaler to either slow down or add more consumer capacity, rather than a naive design that keeps accepting more work into an ever-growing in-memory buffer until the process runs out of memory and crashes.

### 12. What's the difference between vertical scaling a database and read replicas, and what does a read replica NOT solve?
Vertical scaling gives the single database instance more CPU/RAM/IO capacity — helps until you hit the largest available instance size, a hard ceiling. Read replicas add additional database instances that asynchronously (usually) replicate from the primary and can serve read-only queries, scaling *read* throughput horizontally by spreading reads across multiple instances. What replicas don't solve: write throughput (all writes still go through the single primary — this is a separate, harder problem usually requiring sharding or a different data store), and replicas typically have replication lag, meaning a read immediately after a write to the primary might not yet reflect that write on a replica (a classic source of "I just saved this and now it's gone" bugs if reads are naively routed to replicas without considering this).

### 13. What is the CAP theorem, in plain terms, and why is "pick 2 of 3" a common oversimplification?
CAP theorem: in the presence of a network Partition (which *will* happen in any real distributed system), you must choose between Consistency (every read sees the most recent write, or an error) and Availability (every request gets a response, even if it might not be the most recent data). It's a common oversimplification to say "pick 2 of 3" because partition tolerance isn't really optional in a real distributed system spanning multiple nodes/networks — the actual practical choice is CP vs. AP *specifically during a partition*; when there's no partition, a well-designed system can be both consistent and available simultaneously, so CAP is really about what tradeoff a system makes only in the (hopefully rare, but inevitable) partition scenario, not a permanent, constant tradeoff.

### 14. What is eventual consistency, and give a realistic example where it's an acceptable tradeoff.
Eventual consistency means that after a write, the system guarantees all replicas/nodes will *eventually* converge to reflect it, but doesn't guarantee an immediate read right after will see it. It's acceptable where a brief staleness window doesn't meaningfully harm the user experience or business logic — e.g., a "like count" on a social media post being off by a few for a couple of seconds after a new like is a non-issue, whereas a bank account balance check needing to reflect a just-completed transfer immediately is not an acceptable place for the same tradeoff.

### 15. What's the difference between vertical layering (presentation/business logic/data access) and hexagonal/clean architecture, at a high level?
Traditional layered architecture (presentation → business/service layer → data access layer) organizes code by technical role, with dependencies typically flowing one direction (top to bottom) — simple and familiar, but business logic can end up coupled to the specific data-access technology below it. Hexagonal (ports and adapters)/clean architecture instead puts core business logic at the center, depending on nothing external, with "ports" (interfaces) that "adapters" (concrete implementations — a specific database, a specific external API client, a specific web framework) plug into from the outside — inverting the dependency direction so the core business logic can be tested and reasoned about entirely independent of infrastructure details, and infrastructure (the database, the framework) becomes a swappable implementation detail rather than something core logic is built around.

### 16. What is dependency injection, and why is it useful for backend testing?
Dependency injection supplies a component's dependencies (a database client, an external API client) from the outside (via constructor/function parameters, or a DI framework) rather than the component creating/looking them up itself internally. This is useful for testing because a test can inject a mock/fake/in-memory implementation of a dependency (e.g., a fake payment gateway that always "succeeds" without hitting a real network) instead of needing the real, slow, external, potentially costly or non-deterministic dependency — letting unit tests run fast, deterministically, and in isolation.

### 17. What's the difference between a monolith and microservices, and what problem does a monolith actually solve well that's often underrated?
A monolith is a single deployable unit containing all (or most) of an application's functionality; microservices split functionality into many independently deployable services communicating over the network. A monolith is underrated for: simplicity of local development/debugging (one codebase, one process, no network calls to reason about or mock), transactional consistency (a single database transaction can span logic that would require complex distributed-transaction handling across microservices), and lower operational overhead (no service mesh, no distributed tracing requirement, no need to manage dozens of independent deployments/versions) — many successful companies run monoliths at very large scale, and microservices should be adopted to solve specific organizational scaling problems (independent team deployment cadence, independent scaling of genuinely different load profiles), not by default.

### 18. What is a "distributed monolith," and how does it happen?
A distributed monolith is microservices in name/deployment topology but still tightly coupled in practice — services can't be deployed independently without coordinating changes across several of them simultaneously (due to shared databases, synchronous chains of calls where any one being down breaks everything, or a shared library whose version must be bumped in lockstep everywhere). It typically happens when a team splits a monolith into separate services without first establishing clear ownership boundaries and independent data stores per service, ending up with all of microservices' operational complexity (network calls, distributed debugging) and none of its actual benefits (independent deployability, fault isolation).

### 19. What's the difference between vertical and horizontal API versioning strategies (URI path, header, query param)?
URI path (`/v1/users`, `/v2/users`) — most visible/explicit, easy to route at the infrastructure level (a load balancer can route different versions to different backend deployments trivially), but "pollutes" the URI and can imply a resource has fundamentally different identities across versions. Header-based (`Accept: application/vnd.myapi.v2+json` or a custom header) — keeps URIs clean/stable, but is less discoverable/debuggable (you can't just see the version by looking at a URL/browser address bar) and harder to route at the infra layer without inspecting headers. Query parameter (`?version=2`) — simple, but easy to omit accidentally (defaulting behavior needs careful thought) and less semantically "correct" from a strict REST perspective (a query param typically implies filtering/options, not identity/format). Path-based is the most common in practice for its operational simplicity, despite being the "least pure" from an API design purist's perspective.

### 20. What is backward compatibility in an API context, and give an example of a backward-incompatible ("breaking") change vs. a safe additive one.
Backward compatible means existing clients continue to work correctly, unmodified, against the new version. Safe additive changes: adding a new optional field to a response, adding a new optional query parameter, adding an entirely new endpoint. Breaking changes: removing or renaming an existing field, changing a field's data type (a string becoming a number), changing existing required behavior/validation rules, or changing the meaning of an existing status code — any of these can silently break clients that were written against the old contract, which is why API versioning and careful, deliberate deprecation processes (not just "breaking things immediately") exist for evolving public/widely-consumed APIs.
