# Node.js — Language & Runtime-Specific Interview Questions

> Sourced/topic-checked against GeeksforGeeks' 74-question Node.js interview list. Complements the language-agnostic `05-concurrency-multithreading-async.md` and `01-backend-fundamentals.md` with Node.js-runtime-specific mechanics.

---

### 1. How does Node.js work, and what is libuv's role?
Node.js runs JavaScript on Google's V8 engine but adds a C++ layer (via libuv) providing the event loop, a thread pool, and non-blocking I/O bindings to the OS — this is what lets Node handle file system, network, and timer operations asynchronously despite JavaScript itself being single-threaded. libuv abstracts OS-specific async I/O mechanisms (epoll on Linux, kqueue on macOS, IOCP on Windows) behind one consistent API, and also provides a thread pool (default size 4) that Node uses for operations that don't have a natural async OS primitive (some file system calls, DNS lookups via `dns.lookup`, and CPU-intensive crypto operations) so they don't block the main event loop thread.

### 2. Why is Node.js single-threaded, and how does it still handle high concurrency?
Node.js's core JavaScript execution runs on a single thread by design, avoiding the complexity/overhead of traditional multi-threaded concurrency control (locks, race conditions on shared memory — see the concurrency file) for the vast majority of typical backend workloads, which are I/O-bound rather than CPU-bound. It achieves high concurrency despite this via its event loop: I/O operations are delegated to the OS/libuv's thread pool and run in the background, with only their completion callbacks executed on the single JS thread — meaning thousands of concurrent connections can be "in flight" simultaneously as long as most of their time is spent waiting on I/O rather than actively computing on the JS thread.

### 3. Explain the phases of the Node.js event loop.
Roughly, in order per loop iteration: **timers** (execute callbacks scheduled by `setTimeout`/`setInterval` whose time has elapsed), **pending callbacks** (some system-level callbacks deferred from the previous loop iteration), **poll** (retrieve new I/O events and execute their callbacks; the loop will wait here if there's nothing else scheduled), **check** (execute `setImmediate` callbacks), **close callbacks** (e.g., a socket's `close` event). Interleaved between every phase, Node also fully drains the **microtask queue** (resolved Promises' `.then()` callbacks and `process.nextTick` callbacks) before moving to the next phase — this is why microtasks (especially `process.nextTick`, which has even higher priority than Promise callbacks) can starve the event loop if used recursively/excessively, since they're processed to completion before the loop is allowed to proceed.

### 4. What's the difference between `setImmediate()`, `process.nextTick()`, and `setTimeout(fn, 0)`?
`process.nextTick()` callbacks run before any other phase of the event loop, immediately after the currently executing operation completes — even before Promise microtasks. `setTimeout(fn, 0)` schedules a callback for the timers phase, subject to the minimum timer resolution (effectively similar timing to 1ms in practice, not truly zero). `setImmediate()` schedules a callback for the check phase, specifically designed to run "immediately after the current poll phase completes" — inside an I/O callback, `setImmediate` is guaranteed to run before any `setTimeout(fn, 0)` scheduled at the same point, though outside of an I/O context their relative order is not guaranteed and can vary.

### 5. What is callback hell, and what are three ways to avoid it?
Callback hell is deeply nested, hard-to-read/maintain code resulting from chaining many sequential asynchronous operations via nested callbacks, each one indented further than the last, with error handling scattered and duplicated at every level. Three solutions: (1) named functions instead of anonymous inline callbacks, reducing nesting depth visually; (2) Promises, which allow flattening a chain via `.then()` and centralizing error handling in a single `.catch()`; (3) `async`/`await`, which lets the same underlying Promise-based logic be written in a linear, synchronous-looking style with ordinary `try/catch` for errors — the modern default recommendation for new code.

### 6. What is an EventEmitter, and how does it relate to Node's overall event-driven design philosophy?
`EventEmitter` (from Node's `events` module) is the core building block behind Node's event-driven architecture — many built-in Node objects (HTTP servers, streams, child processes) extend `EventEmitter`, emitting named events (`'data'`, `'error'`, `'close'`) that other code can subscribe to with `.on()`. It's a direct application of the Observer design pattern (see the OOP patterns file) at the runtime level — decoupling the code that produces an event from the potentially multiple, independent listeners reacting to it, which is foundational to how idiomatic Node.js code is structured around reacting to I/O completion events rather than blocking and waiting for them.

### 7. What are streams in Node.js, and why are they preferred over reading an entire file/response into memory?
Streams process data incrementally, in chunks, rather than requiring the entire dataset to be loaded into memory before processing can begin — critical for handling large files or network responses efficiently (a multi-gigabyte file can be processed with a small, constant memory footprint via streaming, whereas reading it fully into memory first could exhaust available RAM or, at minimum, add significant unnecessary latency before processing starts). Node has four stream types: Readable, Writable, Duplex (both), and Transform (a Duplex stream that modifies data as it passes through) — `pipe()` connects a Readable stream's output directly to a Writable stream's input, automatically handling backpressure (see the concurrency/message-queue files) so a fast producer doesn't overwhelm a slower consumer's buffer.

### 8. What is a Buffer in Node.js, and why is it needed alongside JavaScript's native string type?
A Buffer represents raw binary data (a fixed-length sequence of bytes) — necessary because JavaScript strings are historically UTF-16-encoded text and aren't well-suited for handling binary data directly (network protocols, file contents, image/video data, cryptographic operations) without lossy or inefficient conversions. Buffers are used extensively under the hood in Node's stream and file system APIs whenever raw bytes (as opposed to decoded text) need to be handled directly.

### 9. What is the `cluster` module, and why is it needed given Node's single-threaded nature?
Since a single Node.js process only uses one CPU core for its JS execution (see Q2), the `cluster` module lets you fork multiple worker processes (typically one per CPU core) that all listen on the same port, with the OS/Node distributing incoming connections across them — achieving multi-core utilization for a Node application without needing to rewrite it around traditional multi-threading. Each worker is a fully separate process with its own memory/event loop (not shared memory like threads), so any state that needs to be shared across workers (session data, caches) must be externalized to a shared store (Redis) rather than kept in a single worker's in-memory state — directly connecting back to the statelessness principle in the backend fundamentals file.

### 10. What's the difference between `child_process.spawn()` and `child_process.fork()`?
`spawn()` launches any external command/executable as a new process, communicating via streams (stdin/stdout/stderr) — general-purpose, used for running arbitrary system commands or non-Node programs. `fork()` is a specialized case of `spawn()` specifically for launching *new Node.js processes*, automatically setting up an IPC (inter-process communication) channel that lets the parent and child exchange structured JavaScript objects directly via `.send()`/`on('message')`, in addition to the standard stdio streams — used for offloading CPU-intensive JavaScript work to a separate process (working around the single-thread limitation for CPU-bound tasks) while still easily passing data back and forth.

### 11. Explain the concept of middleware in the context of an Express.js application.
Middleware functions sit in the request-processing pipeline between the incoming request and the final route handler, each with access to the request, response, and a `next()` function to pass control to the next middleware in the chain (or short-circuit by sending a response directly). This enables composable, reusable cross-cutting request handling — authentication checks, request logging, body parsing, CORS headers — applied consistently across many routes without duplicating that logic in every individual route handler, directly mirroring the general request-response lifecycle/middleware-chain concept described in the backend fundamentals file.

### 12. What is CORS in the context of a Node.js/Express API, and how do you typically enable it?
(See the security-authentication file for the full CORS explanation.) In an Express app, CORS is usually enabled via the `cors` middleware package (`app.use(cors({ origin: 'https://myapp.com' }))`), which automatically adds the appropriate `Access-Control-Allow-Origin` (and related) response headers so that browser-based JavaScript running on the allowed origin(s) can read the API's responses — a common interview follow-up is emphasizing that this should be configured with an explicit allow-list of trusted origins rather than a blanket wildcard `*`, especially for any API that also handles authenticated/credentialed requests.

### 13. How would you connect a Node.js application to MongoDB, and what's the role of a library like Mongoose?
The native MongoDB Node.js driver provides low-level, direct access to MongoDB's API (raw queries, no schema enforcement). Mongoose is an Object Data Modeling (ODM) library built on top of the native driver, adding schema definition/validation, type casting, middleware hooks (pre/post-save logic), and a more application-friendly, model-based API — analogous to what an ORM (see the databases file) provides for relational databases, trading some raw flexibility for developer convenience and built-in structure/validation on top of MongoDB's naturally schema-less documents.

### 14. What is `NODE_ENV`, and why does setting it correctly matter in production?
`NODE_ENV` is a conventional (not Node-core-enforced, but universally adopted by the ecosystem) environment variable indicating the running mode (`development`, `production`, `test`). Many libraries (Express itself, various middleware, React's build tooling) branch their behavior based on it — e.g., Express enables view caching and less verbose error output when `NODE_ENV=production`, while leaving it unset or as `development` can leave debugging features (verbose stack traces in error responses, disabled caching) active in production, which is both a performance issue and a security concern (see the security file's discussion of not leaking internal details in production error responses).

### 15. How do you implement authentication/session management in a Node.js application, and what are the common approaches?
(See the security-authentication file for the full conceptual treatment of session vs. JWT auth, OAuth, etc.) In Node specifically, `passport.js` is the most widely used authentication middleware — a pluggable strategy-based system (`passport-local`, `passport-jwt`, `passport-google-oauth20`, etc.) that standardizes integrating many different authentication mechanisms into an Express app's middleware chain without hand-rolling each one. For session-based auth specifically, `express-session` (backed by a shared session store like `connect-redis` in production, rather than its default in-memory store, which doesn't scale across multiple Node processes/instances — directly tying back to the statelessness discussion in Q9) manages the session lifecycle.

### 16. What is the reactor pattern, and how does it relate to Node.js's architecture?
The reactor pattern is a general event-handling design where a single-threaded event loop ("the reactor") waits for events (I/O readiness) and dispatches each to its registered handler, delegating the actual blocking work to the OS/kernel or a background thread pool rather than blocking the main loop itself. Node.js's entire architecture (the event loop, plus libuv's I/O delegation described in Q1) is a direct, textbook implementation of the reactor pattern — understanding this pattern explains *why* Node.js is architected the way it is, rather than just memorizing "Node uses an event loop" as an isolated fact.
