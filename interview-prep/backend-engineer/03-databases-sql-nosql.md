# Databases: SQL & NoSQL — Interview Questions

---

### 1. Explain ACID properties with a concrete example for each.
**Atomicity** — a transaction's operations all succeed or all fail together (a bank transfer debiting one account and crediting another either both happen or neither does — never a debit with no matching credit). **Consistency** — a transaction moves the database from one valid state to another, respecting all constraints/invariants (a foreign key constraint prevents an order referencing a nonexistent customer). **Isolation** — concurrent transactions don't see each other's uncommitted intermediate state (two people booking the last seat simultaneously don't both see it as available). **Durability** — once committed, a transaction's changes survive a subsequent crash (typically via a write-ahead log flushed to durable storage before acknowledging commit).

### 2. Explain the SQL transaction isolation levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable.
**Read Uncommitted** — can see other transactions' uncommitted changes ("dirty reads"); rarely used, weakest guarantee. **Read Committed** — only ever sees committed data, but a value re-read within the same transaction can change if another transaction commits in between ("non-repeatable read"); the default in Postgres/Oracle/SQL Server. **Repeatable Read** — the same row read twice within a transaction returns the same value, but a range query might return different *rows* on a second read if new matching rows were committed by others ("phantom read"); MySQL's default (InnoDB's implementation also prevents most phantom reads via its specific MVCC mechanism, going further than the SQL standard strictly requires). **Serializable** — the strongest level; transactions behave as if executed one at a time in some serial order, preventing all anomalies, at the cost of the most contention/lowest concurrency (often implemented via locking or aborting/retrying conflicting transactions).

### 3. What is a dirty read, non-repeatable read, and phantom read?
**Dirty read** — reading data another transaction has written but not yet committed (which might later be rolled back, meaning you read data that "never really existed"). **Non-repeatable read** — reading the same row twice in one transaction and getting different values because another transaction committed a change to it in between. **Phantom read** — re-running the same range/filter query twice in one transaction and getting a different *set* of rows because another transaction inserted/deleted rows matching that filter in between.

### 4. What is MVCC (Multi-Version Concurrency Control), and how does it let readers avoid blocking writers?
MVCC keeps multiple versions of a row simultaneously (each tagged with information about which transaction created/deleted it); a read within a transaction sees a consistent "snapshot" of the data as of a specific point (its transaction start, or statement start, depending on isolation level) rather than the current, possibly mid-write state — so readers never need to wait for a writer's lock (they simply read the appropriate older version), and writers don't need to wait for readers. This is how Postgres and MySQL/InnoDB achieve high read concurrency without traditional read locks, at the cost of needing periodic cleanup of old row versions no longer needed by any active transaction (Postgres's `VACUUM` process).

### 5. Explain database indexing: what is a B-tree index, and why does it speed up lookups but slow down writes?
A B-tree index maintains a sorted, balanced tree structure of the indexed column's values, each pointing to the corresponding row(s) — a lookup for a specific value (or range) can navigate directly to it in O(log n) comparisons instead of scanning every row (O(n)), and it also enables fast range queries and sorted retrieval. Writes slow down because every `INSERT`/`UPDATE`/`DELETE` affecting an indexed column must also update the index structure(s) to keep them accurate — more indexes on a table means more work per write, which is why indexes are a tradeoff (read speed vs. write speed/storage), not a free win to add indiscriminately on every column.

### 6. When would you choose a composite (multi-column) index, and what's the "leftmost prefix" rule?
A composite index on `(a, b, c)` is useful when queries commonly filter/sort on those columns together. The leftmost prefix rule: the index can efficiently serve queries filtering on `a` alone, or `a AND b`, or `a AND b AND c` — but *not* efficiently serve a query filtering on `b` alone or `c` alone without `a`, because the index is physically sorted by `a` first, then `b` within each `a`, then `c` within each `b` — skipping the leading column(s) means the sorted structure doesn't help locate matching rows. This is why column *order* in a composite index matters significantly and should match your actual most common query patterns.

### 7. What is a covering index, and why can it make a query much faster even without changing the query itself?
A covering index includes *all* the columns a query needs (both the filter/sort columns and the columns being selected), letting the database satisfy the entire query directly from the index structure without needing to look up the actual full row in the underlying table ("index-only scan") — this avoids the extra random I/O of fetching each matching row's full data ("heap fetch"/table lookup), which can be a significant speedup, especially for queries scanning/returning many rows.

### 8. Explain the difference between a clustered and a non-clustered index.
A clustered index determines the *physical* storage order of the table's rows on disk — there can be only one per table (often the primary key), since rows can only be physically sorted one way. A non-clustered index is a separate structure that stores indexed column values alongside pointers (or, in some engines, the clustering key) back to the actual row location — a table can have many non-clustered indexes. Lookups via a clustered index can be slightly faster (no extra pointer-following step, and the actual data is right there in the index's leaf nodes), while non-clustered indexes offer more flexibility for indexing multiple different access patterns on the same table.

### 9. What is a query execution plan, and what do you look for when using `EXPLAIN`/`EXPLAIN ANALYZE`?
An execution plan shows exactly how the database intends to (or, with `ANALYZE`, actually did) execute a query — which indexes (if any) it used, the join algorithm/order chosen, the estimated (or actual) number of rows processed at each step, and the estimated cost. Key things to look for: a "sequential scan" (full table scan) on a large table where an index scan was expected (often means a missing/unused index, or a query pattern the optimizer can't use an existing index for — e.g., applying a function to an indexed column without a matching functional index); a large discrepancy between the planner's *estimated* row count and the *actual* row count (a sign of stale table statistics misleading the query planner into a bad plan); and expensive operations like nested loop joins over unexpectedly large row counts, which usually indicate a missing index on the join column.

### 10. What is database normalization, and what do 1NF, 2NF, and 3NF mean (informally)?
Normalization organizes relational data to reduce redundancy and prevent update anomalies. **1NF** — each column holds atomic (indivisible) values, no repeating groups/arrays crammed into one column. **2NF** — (builds on 1NF) every non-key column depends on the *entire* primary key, not just part of a composite key. **3NF** — (builds on 2NF) every non-key column depends *only* on the primary key, not on other non-key columns (no "transitive" dependencies) — e.g., storing a customer's city and that city's country in the same orders table is a 3NF violation if country is really a fact about the city, not the order.

### 11. What is denormalization, and when is it a legitimate, deliberate tradeoff rather than "bad design"?
Denormalization deliberately introduces redundancy (duplicating data, or precomputing/storing derived values) to optimize read performance, at the cost of update complexity (the same fact now needs updating in multiple places) and potential temporary inconsistency between copies. It's a legitimate tradeoff when read performance is critical and the specific query pattern involves expensive joins/aggregations that would otherwise need to be recomputed on every read — e.g., storing a denormalized `comment_count` on a post rather than always computing `COUNT(*)` over a comments table live, accepting the small complexity of keeping that counter updated (via a trigger, application logic, or eventual reconciliation) in exchange for O(1) reads of a frequently-displayed value.

### 12. Explain the difference between `INNER JOIN`, `LEFT JOIN`, `RIGHT JOIN`, and `FULL OUTER JOIN`.
`INNER JOIN` returns only rows with matches in both tables. `LEFT JOIN` returns all rows from the left table, with matching right-table columns where available and `NULL` where there's no match. `RIGHT JOIN` is the mirror (all rows from the right table). `FULL OUTER JOIN` returns all rows from both tables, with `NULL`s filling in wherever there's no match on either side.

### 13. What's the difference between `WHERE` and `HAVING` in a SQL query?
`WHERE` filters individual rows *before* any grouping/aggregation happens. `HAVING` filters *groups* after `GROUP BY` aggregation has been computed — you use `HAVING` when the filter condition itself depends on an aggregate value (e.g., `HAVING COUNT(*) > 5`), which `WHERE` can't reference since aggregates don't exist yet at the row-filtering stage.

### 14. What is a database transaction's write-ahead log (WAL), and why does it enable both durability and crash recovery?
Before a change is applied to the actual data files, it's first written (and flushed to durable storage) as a log record describing the change ("write-ahead" — log before data). This provides durability efficiently (the log write, often sequential/append-only, can be flushed to disk quickly, while the actual data-file update can happen lazily/asynchronously afterward, since the log guarantees it can be reconstructed even if the process crashes before that lazy write happens) and enables crash recovery (on restart after a crash, the database replays the log from the last checkpoint to reconstruct any committed changes that hadn't yet been fully applied to the data files, and can also discard uncommitted transactions' changes cleanly).

### 15. What's the difference between a NoSQL document store (MongoDB), a key-value store (Redis/DynamoDB), a wide-column store (Cassandra), and a graph database (Neo4j)?
**Document store** — stores semi-structured documents (typically JSON/BSON), flexible schema, good for data that's naturally hierarchical/nested and queried as whole objects. **Key-value store** — the simplest model, extremely fast lookups by key, minimal query flexibility beyond that (good for caching, session storage, simple lookups). **Wide-column store** — rows can have different sets of columns, optimized for very high write throughput and horizontal scalability across huge datasets, with queries designed around a specific partition/clustering key access pattern decided upfront (not flexible ad-hoc querying). **Graph database** — optimized for traversing relationships between entities efficiently (e.g., "friends of friends," recommendation paths) where relational JOINs across many tables would become prohibitively expensive at depth.

### 16. When would you choose a NoSQL database over a relational database, and what do you typically give up?
Choose NoSQL when you need horizontal write scalability beyond what a single relational primary can provide, your data access patterns are simple/predictable enough to design around a specific key structure upfront, your schema is genuinely variable/evolving rapidly across records, or you specifically need one of the specialized models above (graph traversal, huge time-series/wide-column ingest). What you typically give up: flexible ad-hoc querying/joins (most NoSQL stores require designing your data model around known access patterns in advance, rather than querying however you like after the fact), and often strong consistency/ACID transactions across multiple items (though many modern NoSQL databases now offer at least limited multi-document/multi-item transactions).

### 17. Explain database sharding, and the tradeoffs of choosing a good shard key.
Sharding splits a dataset across multiple independent database instances (shards), each holding a subset of the data, to scale beyond a single machine's write/storage capacity. The shard key (how data is partitioned) is critical: a poorly chosen key (e.g., sequential auto-incrementing IDs, or a key with very uneven value distribution) creates "hot shards" that receive disproportionate load while others sit underutilized, defeating the purpose of sharding. A good shard key distributes load evenly and, ideally, keeps data that's commonly queried/joined together on the same shard (since cross-shard joins/transactions are expensive or impossible) — e.g., sharding by `customer_id` so all of one customer's data lives together, if most queries are scoped to a single customer.

### 18. What is database replication, and the difference between synchronous and asynchronous replication?
Replication maintains copies of data across multiple database instances for redundancy/read scaling. Synchronous replication waits for a replica to confirm it has received/applied a write before acknowledging the write as committed to the client — guarantees no data loss if the primary fails immediately after (the replica definitely has it), but adds latency to every write (bounded by the slowest required replica) and can block writes entirely if a replica is unreachable. Asynchronous replication acknowledges the write immediately after the primary applies it, replicating to replicas in the background — faster writes, no blocking on replica health, but a primary failure before replication completes can lose the most recent write(s) that hadn't yet reached any replica.

### 19. What is a database connection pool, and why does an application need one instead of opening a new connection per request?
A connection pool maintains a set of already-established database connections that application threads/requests borrow and return, rather than opening (and the expensive TCP handshake + database authentication overhead of) a brand-new connection for every single request. Without pooling, both the application (overhead per request) and the database (each connection consumes real database-side memory/resources, and most databases have a hard maximum connection limit) suffer — a sudden traffic spike opening thousands of new raw connections can exhaust the database's connection limit and take it down entirely, whereas a bounded pool caps concurrent connections predictably and queues excess requests instead.

### 20. What is connection pool exhaustion, and how does it manifest as an application-level symptom?
When all connections in the pool are checked out/in-use (often because queries are running unusually slowly, or a leak means connections are never returned to the pool), new requests needing a database connection must wait in a queue for one to free up — this manifests as requests hanging/timing out even though the database itself might not be under heavy load, and CPU/memory on the application server can look completely normal, making it a somewhat non-obvious diagnosis (check pool utilization metrics and "waiting for connection" timing specifically, not just raw DB or app server resource usage).

### 21. Explain database migrations and why they should be run as part of a controlled process rather than ad hoc.
A migration is a versioned, incremental change to a database schema (add a column, create a table, add an index), tracked in sequence so the database's schema can be reliably and reproducibly brought from any prior version to the current one (and, ideally, rolled back). Running them ad hoc (manual `ALTER TABLE` statements run by hand against production) risks environments drifting out of sync with each other (staging schema no longer matches production), no audit trail of what changed and why, and no reliable, tested rollback path — a controlled migration framework (Flyway, Alembic, Django migrations, etc.) run through the same CI/CD pipeline as code changes keeps schema changes versioned, reviewed, and reproducible exactly like application code.

### 22. What's a common cause of a migration causing an outage, and how do you avoid it (e.g., adding a NOT NULL column, or an index, to a large table)?
Some schema changes require a full table lock/rewrite that, on a large table, can take a long time — during which the table may be completely locked for reads/writes (or at least writes), causing a de facto outage for anything depending on that table. Examples: adding a `NOT NULL` column without a default (historically forced a full table rewrite in many databases, though modern Postgres versions have optimized common cases); creating a regular index (locks writes on the table for the duration, though `CREATE INDEX CONCURRENTLY` in Postgres avoids this at the cost of being slower and non-transactional). Mitigation: know your specific database engine's locking behavior for each type of DDL operation, use online/concurrent variants where available, run risky migrations during low-traffic windows, and for very large tables, consider the expand-contract pattern with smaller, incremental, non-locking steps instead of one large blocking change.

### 23. How would you design a schema for a "soft delete" feature, and what are the tradeoffs vs. actually deleting rows?
Add a `deleted_at` (nullable timestamp) column instead of `DELETE`ing the row; "deleted" records are simply filtered out of normal queries (`WHERE deleted_at IS NULL`) but remain recoverable/auditable. Tradeoffs: every query touching that table must remember to add the filter (easy to forget, causing "deleted" data to leak back into results — often centralized via an ORM default scope to reduce this risk), unique constraints become tricky (two "deleted" rows and one "active" row with the same otherwise-unique value need careful constraint design, e.g., a partial/filtered unique index that only applies `WHERE deleted_at IS NULL`), and the table grows indefinitely unless a separate archival/purge process eventually removes very old soft-deleted rows — versus true deletion, which is simpler and reclaims space immediately but loses recoverability/audit history entirely.
