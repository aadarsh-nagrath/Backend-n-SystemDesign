# Caching Strategies — Interview Questions

---

### 1. Why is caching effective, fundamentally (what property of real-world data/access patterns does it exploit)?
Caching exploits locality of reference: in most real systems, a small subset of data is accessed far more frequently than the rest (temporal locality — recently accessed data is likely to be accessed again soon; and skewed popularity — a small number of items, like trending posts or popular products, account for a disproportionate share of all requests). Storing that hot subset somewhere faster to access than the true source of truth (memory vs. disk, a nearby cache vs. a distant database) serves the vast majority of requests cheaply/quickly, even though the cache itself only holds a fraction of the total data.

### 2. Explain cache-aside (lazy loading), read-through, write-through, and write-behind caching strategies.
**Cache-aside** — application code checks the cache first; on a miss, reads from the DB and populates the cache for next time; the application owns the caching logic explicitly. **Read-through** — the cache itself sits in front of the DB and handles populating itself on a miss transparently to the application (application only ever talks to the cache). **Write-through** — writes go to the cache and the underlying DB synchronously, together, before being acknowledged — keeps cache and DB consistent immediately but adds write latency (waiting on both). **Write-behind (write-back)** — writes go to the cache immediately and are acknowledged right away, with the DB updated asynchronously afterward — fastest writes, but risks data loss if the cache fails before the async write completes, and adds complexity in guaranteeing eventual persistence.

### 3. What is cache invalidation, and why is it famously called one of "the two hard things in computer science"?
Cache invalidation is the problem of knowing when cached data has become stale (the underlying source has changed) and needs to be refreshed or removed. It's hard because there's no single universal correct strategy: invalidate too aggressively and you lose most of the caching benefit (constant misses); invalidate too conservatively and users see stale data; and correctly invalidating *exactly* the right set of cache entries when an underlying value changes (especially cached aggregates/derived data touched by many different write paths) requires careful, often error-prone bookkeeping that's easy to get subtly wrong in ways that only surface as hard-to-reproduce "why is this data wrong" bugs.

### 4. Compare TTL-based expiration and explicit invalidation as cache-freshness strategies.
TTL (time-to-live) expiration is simple and self-healing (even if you forget/fail to explicitly invalidate an entry, it will eventually expire and be refreshed on its own) but means there's always some window of potential staleness up to the TTL duration, and choosing the right TTL is itself a tradeoff (too short = little caching benefit, too long = longer staleness windows). Explicit invalidation (actively deleting/updating a cache entry the moment its underlying data changes) can achieve near-immediate consistency, but requires reliably identifying and triggering invalidation from every code path that could change the underlying data — miss even one write path and you get indefinitely stale data with no self-correction, which is why many systems combine both: explicit invalidation for the common/known write paths, plus a TTL as a safety net for anything missed.

### 5. What is a cache stampede (thundering herd), and how do you prevent it?
When a very popular cache entry expires (or the cache itself restarts, going completely cold), many concurrent requests simultaneously find it missing and all rush to recompute/refetch it from the underlying source at once — potentially overwhelming the database/backend with a sudden burst of duplicate, expensive work, sometimes bad enough to cause a cascading outage. Prevention: a "single-flight"/lock mechanism where only the first request that detects a miss actually goes to fetch/recompute, while concurrent requests for the same key wait for that in-flight result rather than each independently hitting the backend; probabilistic early expiration (refresh slightly before actual expiry, staggered randomly per key, so not all requesters hit the exact same expiry moment); or serving slightly stale data while a single background refresh happens (see Q7).

### 6. What is a cache penetration attack/problem, and how do you defend against it?
Cache penetration occurs when requests target keys that don't exist in either the cache *or* the underlying data source (e.g., an attacker probing random/nonexistent IDs, or simply a legitimate but very long tail of unique invalid lookups) — every such request bypasses the cache (nothing to hit) and hits the backend directly every single time, since a "miss" for a nonexistent key is never cached, defeating the purpose of caching for that traffic pattern and potentially overwhelming the backend. Defense: explicitly cache the "not found" result itself (with a shorter TTL) so repeated lookups of the same nonexistent key are also served from cache, or use a probabilistic filter (a Bloom filter of known-valid keys) to reject obviously-invalid lookups before they even reach the cache/backend layer.

### 7. What is "stale-while-revalidate," and why is it a good default strategy for many read-heavy caches?
Serve the currently-cached (possibly slightly expired) value immediately to the requester, while asynchronously triggering a background refresh of that value for future requests — the current requester never waits on the recomputation, and staleness is typically bounded to a small, controlled window. It's a good default because it decouples user-facing latency entirely from cache-miss/refresh cost (users never experience a "cache miss penalty" directly) while still keeping data reasonably fresh, and it naturally avoids stampedes since only one background refresh needs to run regardless of how many concurrent requests are being served the stale value in the meantime.

### 8. What's the difference between a local (in-process) cache and a distributed cache (Redis/Memcached), and when is each appropriate?
A local/in-process cache (a simple in-memory map, or a library like Caffeine/Guava) is extremely fast (no network round trip) but is per-instance — with multiple application instances behind a load balancer, each has its own independent, potentially inconsistent copy, and the total effective cache capacity/hit rate is fragmented across instances (and a restart loses it entirely). A distributed cache is shared across all application instances (consistent view, much larger effective capacity, survives individual app instance restarts) but adds network latency per access and a new infrastructure dependency to operate/scale itself. A common pattern layers both: a small, very-hot-item local cache in front of a larger shared distributed cache in front of the database (a multi-level cache hierarchy), trading off hit rate, latency, and consistency at each layer.

### 9. Explain common cache eviction policies: LRU, LFU, FIFO.
**LRU (Least Recently Used)** — evicts the item that hasn't been accessed for the longest time; a good general-purpose default that adapts well to changing access patterns. **LFU (Least Frequently Used)** — evicts the item with the fewest total accesses; better than LRU for workloads with a stable set of consistently popular items, but can be slow to adapt if an item's popularity changes suddenly (an old, previously-popular item can be "stuck" if its historical count is high even though it's no longer actually being accessed — usually mitigated with a decay factor). **FIFO** — simply evicts whatever was cached longest ago regardless of access pattern; simple to implement but ignores actual usage entirely, so it's a poor fit whenever access patterns are non-uniform (which is most real workloads).

### 10. What is Redis, and name a few data structures it supports beyond simple key-value strings, with a use case for each.
Redis is an in-memory data store supporting rich data structures beyond plain key-value: **Lists** (ordered sequences — implementing a simple queue/recent-activity feed). **Sets** (unique unordered collections — tracking unique visitors, tag membership, set intersection for "mutual friends"). **Sorted Sets** (members with an associated score, kept in sorted order — leaderboards, rate-limiting counters with time-based scores, priority queues). **Hashes** (field-value maps within a single key — representing an object like a user profile compactly, allowing partial field updates without rewriting the whole value). **HyperLogLog** (probabilistic structure for approximate distinct-count cardinality estimation at a tiny fixed memory footprint — approximate unique visitor counts at massive scale). **Streams** (append-only log structures — a lightweight message queue/event log with consumer groups).

### 11. What is cache consistency in a multi-instance/distributed cache setup, and how does invalidation propagate?
When multiple application instances (or multiple cache nodes) each might hold a copy of the same logical data, an update to the underlying source needs its corresponding cache invalidation to reach every relevant copy, not just the instance that made the write — otherwise other instances continue serving stale cached data indefinitely (if relying purely on invalidation with no TTL safety net). Common propagation mechanisms: a shared distributed cache (Redis) as a single source, so there's only one copy to invalidate; a pub/sub invalidation broadcast (when a write happens, publish an "invalidate key X" message that all instances' local caches subscribe to and act on); or, more simply, relying on short TTLs as a bounded-staleness safety net when exact invalidation propagation is too complex to guarantee reliably.

### 12. Should you cache database query results or cache computed/derived application objects? What's the tradeoff?
Caching raw query results is simpler and more general (any query can be cached the same way) but the cached blob is often tightly coupled to the exact query shape, meaning small query variations produce cache misses even if the underlying data needed is the same, and invalidation still requires knowing which cached queries are affected by a given write. Caching computed/derived objects (e.g., a fully-assembled "user profile" object gathered from several sources) can be more targeted and reusable across different call sites that need the same object, but requires more deliberate application-level cache-key design and invalidation logic tied to the object's identity rather than a specific query's shape. In practice, most systems do both at different layers — query-result caching for cheap, broad wins, and object/computed caching for specific expensive, frequently-reused aggregations.

### 13. What's a realistic scenario where caching makes a bug worse rather than better, and how do you guard against it?
If a bug produces incorrect data (a wrong computed price, a stale permission check) and that incorrect result gets cached, the cache will now consistently and efficiently serve the *wrong* answer to everyone, for the TTL duration, even after the underlying bug is fixed — actually amplifying and prolonging the blast radius of the original bug rather than mitigating it, since without caching, a fix would take effect on literally the very next read. Guarding against this: keep TTLs reasonable rather than extremely long for data whose correctness matters, have a fast, reliable way to flush/invalidate cache entries as part of an incident response (a "flush the cache" runbook step, or targeted invalidation by key pattern), and be cautious about caching results from code paths that are newly deployed/less battle-tested, where correctness hasn't been proven under real production data yet.

### 14. How would you decide what NOT to cache?
Data that's cheap to compute/fetch already (caching adds complexity/infrastructure for negligible benefit). Data that changes so frequently that the cache would almost always be stale/invalidated before it's ever reused (low hit rate makes the caching overhead not worth it). Highly sensitive data where even a brief staleness window has serious consequences (e.g., real-time account balance used to authorize a transaction, unless very carefully designed with strong consistency guarantees). Data with extremely high cardinality/low reuse (e.g., a truly unique, one-off computed value per request that will never be looked up again) — caching only pays off when the same cached value is likely to be read again before it would need to change.
