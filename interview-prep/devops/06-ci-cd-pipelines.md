# CI/CD Pipelines — DevOps Interview Questions

---

### 1. What is the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment?
**Continuous Integration** — developers merge code into a shared branch frequently, with each merge automatically built and tested to catch integration problems early. **Continuous Delivery** — every change that passes the pipeline is automatically prepared into a deployable, release-ready artifact (and often deployed to staging), but production release still requires a manual trigger/approval. **Continuous Deployment** — goes one step further: every change that passes all automated gates is deployed to production automatically, with no manual approval step at all.

### 2. What are the typical stages of a CI/CD pipeline?
Source (trigger on push/PR) → build (compile, install dependencies, produce artifact/image) → static analysis (lint, type-check, security/SAST scan) → automated tests (unit → integration → possibly e2e) → package/publish artifact (container image, binary, package) → deploy to a lower environment (staging) → further tests/smoke checks → manual or automated gate → deploy to production (often progressively — canary/blue-green) → post-deploy verification/monitoring.

### 3. What's the difference between a build artifact and a container image, and why version/tag artifacts immutably?
A build artifact is the packaged output of a build (a jar, a compiled binary, a container image, a static site bundle). Immutable versioning (a unique build number, git SHA, or semver tag — never rebuilding/overwriting the same tag) is critical because it guarantees the exact same bytes that passed testing are what gets deployed to every environment ("build once, deploy many times") — rebuilding per environment risks subtly different artifacts (different dependency resolution timing, different base image patch level) passing tests in staging but failing in production.

### 4. Explain "build once, deploy many" and why it matters.
The same immutable artifact produced once in the pipeline is promoted unchanged through each environment (dev → staging → prod), with only *configuration* (environment variables, secrets, feature flags) varying per environment — not the artifact itself. This eliminates an entire class of "worked in staging, broke in prod" bugs caused by rebuilding (and thus potentially changing) the artifact at each stage, and makes it possible to be certain exactly what code is running in production at any time.

### 5. What is a canary deployment, and how do you decide when to proceed vs. roll back?
A canary deployment routes a small percentage of production traffic (e.g., 5%) to the new version while the rest continues to the stable version, monitoring key metrics (error rate, latency, business metrics) on the canary cohort specifically. If metrics stay within acceptable thresholds compared to the baseline (often via automated analysis, e.g. Kayenta/Argo Rollouts' analysis templates), traffic is progressively increased (5% → 25% → 50% → 100%); if metrics regress, traffic is automatically or manually shifted back to 0% on the canary — minimizing the blast radius of a bad release to a small fraction of users/requests.

### 6. What is blue-green deployment, and how does it differ from canary?
Blue-green maintains two full, identical production environments ("blue" = current live, "green" = new version); once the green environment is fully deployed and verified (often with synthetic/smoke tests, not real user traffic), a router/load balancer instantly switches *all* traffic from blue to green. Rollback is just switching back, and is nearly instantaneous. It differs from canary in granularity: blue-green is an all-or-nothing cutover of 100% of traffic at once (fast rollback, but any issue affects all users the moment it's switched), whereas canary gradually and partially shifts traffic, limiting exposure but taking longer to fully roll out and requiring the app to safely run two versions concurrently (an inherent requirement of canary, optional for blue-green).

### 7. What is a rolling deployment, and what's its main tradeoff vs. blue-green?
A rolling deployment incrementally replaces old instances with new ones a few at a time (as covered in the Kubernetes section's Deployment rollout), without needing double the infrastructure that blue-green requires. The tradeoff: both old and new versions serve traffic simultaneously for the duration of the rollout, so the application/API must tolerate that (backward/forward compatible schema and contracts) — and rollback is slower than blue-green's instant switch, since it requires rolling back the same way it rolled forward.

### 8. What is a feature flag, and how does it decouple deployment from release?
A feature flag is a runtime toggle (config-driven, often via a dedicated service like LaunchDarkly or a simpler config/DB flag) that controls whether a code path is active, independent of whether that code has been *deployed*. This decouples "deploying new code to production" (a low-risk, reversible, engineering-controlled event, often continuous) from "releasing a feature to users" (a business decision, potentially gradual — e.g., internal users → 1% → 100%, or instantly killable without a redeploy if something goes wrong) — a cornerstone of trunk-based development and continuous deployment.

### 9. What is a smoke test in a deployment pipeline?
A minimal, fast set of checks run immediately after a deployment to verify the absolute basics work (the service starts, responds to a health-check endpoint, can reach its database) before declaring the deployment successful or routing real traffic to it — designed to catch catastrophic failures quickly, not to be a substitute for the full test suite that already ran earlier in the pipeline.

### 10. Explain the testing pyramid and why it matters for CI pipeline speed/reliability.
Many fast, cheap, reliable unit tests at the base (isolated, no external dependencies, run in seconds); fewer integration tests in the middle (verify components work together — real or realistic DB, message queue, etc. — slower, some flakiness risk); very few end-to-end tests at the top (full system through the UI/API, slow, often flaky, expensive to maintain). Inverting this pyramid ("ice cream cone" anti-pattern — mostly e2e tests) leads to slow, flaky CI pipelines that erode trust in test failures and lengthen the feedback loop.

### 11. What makes a test "flaky," and how do you handle flaky tests in CI?
A flaky test passes and fails intermittently without any code change, usually due to: timing/race conditions (asserting before an async operation completes), shared/leaked state between tests, reliance on real network calls/external services, or non-deterministic ordering/data (relying on a specific, unguaranteed iteration order). Handling: quarantine known-flaky tests (mark and exclude from blocking CI while tracking them, rather than ignoring or repeatedly re-running until green, which erodes signal) and fix the root cause quickly — tests that are "usually right" train engineers to ignore CI failures, which is more dangerous than having fewer, trustworthy tests.

### 12. What's the difference between a CI pipeline running on every commit vs. a nightly build?
Per-commit CI gives fast feedback on the specific change just made, catching regressions immediately while context is fresh and the diff is small (easy to bisect/attribute). A nightly (or scheduled) build typically runs a slower, more expensive suite (full e2e tests, performance/load tests, security scans, dependency vulnerability scans against updated CVE databases) that would be too slow or costly to run on every single commit, trading immediacy for thoroughness/cost efficiency.

### 13. Explain how you'd design a CI pipeline to be fast for a large monorepo.
Only build/test what's affected by a given change (dependency-graph-aware build tools like Bazel, Nx, Turborepo, or path-based CI triggers that map changed files to affected packages) instead of rebuilding everything on every commit. Parallelize independent jobs/stages across multiple runners. Cache aggressively (dependency installs, compiled artifacts, Docker layers) keyed on content hashes, invalidated only when relevant inputs actually change. Use incremental/remote build caching so a change in one package doesn't force a full rebuild of unrelated packages.

### 14. What is a merge queue, and what problem does it solve?
A merge queue serializes merges to a protected branch: when a PR is approved and queued, CI re-runs tests against the *hypothetical combined state* (the PR's changes merged on top of the current head of the queue, not just the PR's original base) before actually merging — catching "my PR passed CI, your PR passed CI, but together they break" scenarios (semantic conflicts CI didn't see because each PR was tested in isolation against a now-stale base) before they ever reach the main branch.

### 15. What's the difference between SAST, DAST, and SCA in a secure CI/CD pipeline?
**SAST** (Static Application Security Testing) — analyzes source code/bytecode without running it, to find patterns like SQL injection, hardcoded secrets, unsafe deserialization. **DAST** (Dynamic Application Security Testing) — tests a *running* application from the outside (like an attacker would), probing for vulnerabilities via actual requests (fuzzing inputs, checking for injection, auth bypass). **SCA** (Software Composition Analysis) — scans third-party/open-source dependencies for known CVEs and license compliance issues. A mature pipeline runs all three at appropriate stages (SAST/SCA early and fast on every PR; DAST typically later against a deployed staging environment).

### 16. What's the difference between an artifact repository (e.g., Artifactory/Nexus/ECR) and a source control system?
Source control (Git) stores and versions human-authored source code and its history. An artifact repository stores and versions *build outputs* (container images, compiled packages/libraries, binaries) — optimized for large binary storage, retention/cleanup policies, immutable versioned retrieval, and access control for consumption (e.g., other teams/pipelines pulling a shared internal library) rather than collaborative editing/diffing of text.

### 17. Explain idempotency in the context of a deployment script/pipeline, and why it matters.
An idempotent operation produces the same end state no matter how many times it's run (e.g., "ensure this resource exists with this config" rather than "create this resource," which fails or duplicates on a second run). It matters because pipelines get retried (transient failures, manual re-triggers) and partial failures happen mid-execution — a non-idempotent deploy script can leave infrastructure in an inconsistent, hard-to-reason-about state if re-run after a partial failure, whereas an idempotent one safely converges to the correct state regardless of how many times or from what partial-failure point it's re-executed.

### 18. How would you design a pipeline to support fast, safe rollback?
Keep the previous N deployed artifact versions readily available (not just the latest) so "redeploy the last known-good version" is a fast, simple pipeline re-run rather than requiring a full rebuild. Prefer deployment strategies with fast rollback built in (blue-green's instant switch-back, or a Kubernetes Deployment's `rollout undo`). Ensure database migrations are backward-compatible (see Q19) so rolling back application code doesn't require also rolling back schema changes. Automate rollback triggers off of post-deploy health/error-rate monitoring rather than relying solely on a human noticing and manually intervening.

### 19. Why are backward-compatible database migrations important for CI/CD, and describe the "expand-contract" pattern.
During a rolling/canary deployment, old and new application code run simultaneously against the *same* database for some period — a migration that isn't backward-compatible (e.g., renaming or dropping a column the old code still reads/writes) breaks the old version's Pods before they've all been replaced, or breaks a rollback if you need to revert application code after the migration already ran. The **expand-contract** pattern splits a breaking change into safe phases: *expand* (add the new column/table alongside the old one, deploy code that writes to both), migrate/backfill data, *deploy* code that reads only from the new structure, then *contract* (a later, separate deployment removes the old column) — each individual step is independently backward-compatible and safely rollback-able.

### 20. What is a "dark launch" or "shadow traffic" testing technique?
Duplicate (mirror) real production traffic to a new version of a service running in parallel, without its responses actually being returned to real users — letting you validate correctness, performance, and error rates of the new version under real-world traffic patterns and data, with zero user-facing risk, before it ever serves live responses.

### 21. Explain the concept of pipeline-as-code (e.g., a Jenkinsfile, GitHub Actions YAML, GitLab CI YAML) and its benefits over configuring a CI tool through a UI.
Pipeline-as-code defines the entire build/test/deploy pipeline declaratively in a file committed alongside the application code in version control. Benefits: full history/diffability/code review of pipeline changes just like application code, reproducibility (the pipeline definition travels with the branch — a feature branch can safely modify its own pipeline without affecting others), easier disaster recovery (the CI system's configuration isn't trapped in a UI's database state), and the ability to reuse/template pipeline logic across many repositories (shared/reusable workflows).

### 22. What's the difference between a self-hosted CI runner and a cloud/SaaS-hosted runner, and when would you choose self-hosted?
SaaS runners (GitHub-hosted runners, etc.) are fully managed, ephemeral, zero-maintenance, but limited in available resources/customization and can't reach resources inside a private network without extra setup (VPN/tunneling). Self-hosted runners run on infrastructure you control — needed when builds require access to internal/private network resources (an internal artifact cache, a private database for integration tests), need specialized hardware (GPUs, specific architectures), have compliance/data-residency requirements, or need to avoid SaaS per-minute cost at high volume — at the cost of you now owning runner maintenance, scaling, and security patching.

### 23. What is a "poison pill" / bad deployment detection strategy, and how do automated rollbacks typically get triggered?
Automated rollback systems watch a defined set of golden signals (error rate, p99 latency, saturation, specific business metrics) on the newly deployed version immediately after rollout/during a canary phase, comparing against the previous version's baseline or a fixed SLO threshold; if the new version breaches the threshold for a sustained window (avoiding false positives from brief noise), the system automatically halts the rollout and reverts traffic/redeploys the previous version — without waiting for a human to notice a dashboard or get paged, minimizing time-to-detect and time-to-mitigate for a bad release.

### 24. How do you manage secrets (API keys, DB passwords) in a CI/CD pipeline securely?
Never commit secrets to the pipeline definition or source code. Use the CI platform's built-in encrypted secrets store (masked in logs) or, better, a dedicated secrets manager (Vault, AWS Secrets Manager) that the pipeline authenticates to at runtime using a short-lived, scoped credential (e.g., OIDC federation between the CI provider and the cloud provider, avoiding long-lived static cloud credentials stored in CI altogether) and fetches secrets just-in-time. Scope secrets as narrowly as possible (per-environment, per-pipeline-stage) and rotate them regularly; audit/alert on secret access.

### 25. What's the difference between a "push-based" and "pull-based" deployment model (relevant to GitOps vs. traditional CI/CD)?
Push-based: the CI/CD pipeline itself holds credentials to the target environment and actively pushes changes into it (`kubectl apply`, `terraform apply` run from the pipeline). Pull-based (GitOps): an agent running *inside* the target environment continuously watches a source of truth (a Git repo) and pulls/applies changes itself — the external pipeline never needs direct write credentials to the environment at all, reducing the credential attack surface and enabling built-in drift detection/reconciliation that a one-shot push doesn't provide.

### 26. What questions would you ask when designing a CI/CD pipeline for a new service from scratch?
What triggers a build (every push? only PRs? tags?) and what's the target deployment frequency? What environments exist and what's the promotion path between them? What's the required test coverage/gates before merge vs. before production deploy? What deployment strategy fits the service's risk profile and traffic pattern (rolling/canary/blue-green)? How are secrets and environment-specific config managed per environment? What's the rollback strategy and how fast does it need to be? What observability/alerting is wired to detect a bad deployment automatically? Who can approve production deploys, and is that approval itself automatable safely over time?
