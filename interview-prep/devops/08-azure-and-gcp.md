# Azure & GCP — DevOps Interview Questions

> Most concepts map 1:1 to AWS equivalents (see `07-aws-cloud.md`) — this file focuses on naming/mapping and the differences interviewers actually probe.

---

### 1. Give the AWS ↔ Azure ↔ GCP equivalents for core compute/networking/storage services.
Compute (VMs): EC2 ↔ Azure Virtual Machines ↔ GCP Compute Engine. Managed Kubernetes: EKS ↔ AKS ↔ GKE. Serverless functions: Lambda ↔ Azure Functions ↔ Cloud Functions/Cloud Run. Object storage: S3 ↔ Azure Blob Storage ↔ Google Cloud Storage. Relational DB: RDS ↔ Azure SQL Database/Azure Database for PostgreSQL ↔ Cloud SQL. NoSQL: DynamoDB ↔ Cosmos DB ↔ Firestore/Bigtable. Virtual network: VPC ↔ Virtual Network (VNet) ↔ VPC. IAM: IAM ↔ Azure Active Directory (Entra ID) + RBAC ↔ Cloud IAM. Load balancer: ALB/NLB ↔ Azure Load Balancer/Application Gateway ↔ Cloud Load Balancing.

### 2. What's distinctive about Azure's resource organization (Management Groups, Subscriptions, Resource Groups)?
Azure organizes resources hierarchically: Management Groups (group multiple subscriptions for org-wide policy/governance) → Subscriptions (billing + quota boundary, roughly analogous to an AWS account) → Resource Groups (a logical container for related resources — e.g., all resources for one application — that share a lifecycle and can be deleted together). This differs from AWS, where an account is the primary isolation boundary and "grouping" is more commonly done via tags or AWS Organizations OUs rather than a first-class nested resource-group container.

### 3. What is GKE Autopilot, and how does it differ from a standard GKE cluster?
Standard GKE requires you to manage and pay for the underlying node pools (VM instances) yourself, choosing machine types and scaling them. GKE Autopilot is a fully managed mode where Google manages the nodes entirely — you only define workloads (Pods/Deployments), and billing is per-Pod-resource-request rather than per-node, with Google handling node provisioning, scaling, and most security/OS hardening automatically. Tradeoff: less low-level control (some node-level customizations, like privileged DaemonSets, are restricted) in exchange for significantly less operational overhead.

### 4. What is Cloud Run, and how does it compare to Lambda and to a plain container on GKE?
Cloud Run runs a stateless container that automatically scales (including to zero) based on incoming request traffic, billed per request/duration like Lambda — but unlike Lambda's function-handler model, you package *any* container (any language/runtime, longer execution flexibility) rather than conforming to a specific function signature. Compared to running the same container on GKE, Cloud Run requires no cluster management at all — it's the serverless middle ground between "just a container" (GKE) and "just a function" (Lambda).

### 5. What is Azure Active Directory (now Microsoft Entra ID), and how does Azure RBAC differ conceptually from AWS IAM?
Entra ID is Azure's identity provider — it's the same directory used for both employee/user identity (SSO into Microsoft 365, etc.) and for authenticating to Azure resources, unlike AWS IAM which is a separate, AWS-specific identity system (even when federated with an external identity provider like Okta/Active Directory). Azure RBAC assigns roles (built-in like Owner/Contributor/Reader, or custom) to a security principal (user, group, or Managed Identity — Azure's equivalent of an IAM role for workloads) *scoped* to a management group, subscription, resource group, or individual resource — conceptually similar to IAM policies+roles, but the identity layer underneath is a full enterprise directory service rather than IAM's more narrowly cloud-scoped user model.

### 6. What is a GCP "project," and how does it relate to billing and IAM?
A GCP Project is the primary organizational and billing unit — every resource belongs to exactly one project, and IAM permissions, quotas, and billing are all scoped at the project level (with Folders and an Organization node above projects for broader hierarchy, similar in spirit to Azure's Management Groups). This differs from AWS's account-centric model in that a single GCP Organization commonly has many lightweight projects (e.g., one per environment or even per small team/service), whereas AWS more often uses fewer accounts with resource-group/tag-based subdivision, or many isolated accounts via AWS Organizations for the same net effect.

### 7. Explain the general cross-cloud tradeoff a DevOps engineer should be able to discuss: multi-cloud vs. single-cloud strategy.
Single-cloud reduces complexity — one set of APIs/tools/IAM models to learn, deeper access to provider-specific managed services and cost-optimization programs, simpler networking. Multi-cloud avoids vendor lock-in and can improve resilience against a provider-wide outage or negotiating leverage on pricing, but multiplies operational complexity (different IAM models, networking primitives, and service behaviors per cloud), often forces you toward lowest-common-denominator services (or an abstraction layer like Kubernetes/Terraform to paper over differences) to actually get portability, and rarely delivers real cost savings once the added engineering overhead is accounted for — most organizations that claim "multi-cloud" actually run different workloads on different clouds for specific service advantages, rather than the same workload portable across both.
