# AWS & Cloud Fundamentals — DevOps Interview Questions

---

### 1. Explain the difference between EC2, ECS, EKS, and Lambda — when would you use each?
**EC2** — raw virtual machines; full control over the OS, maximum flexibility, most operational overhead (patching, scaling, orchestration all on you). **ECS** — AWS's own container orchestrator; simpler than Kubernetes, tightly integrated with other AWS services, good if you don't need Kubernetes' portability/ecosystem. **EKS** — managed Kubernetes control plane; use when you need Kubernetes specifically (portability across clouds, existing K8s tooling/expertise, complex workload orchestration needs). **Lambda** — serverless functions; no server management at all, scales to zero, billed per invocation/duration — ideal for event-driven, bursty, or infrequent workloads, less ideal for long-running processes (execution time limits) or workloads needing consistent low-latency warm state (cold starts).

### 2. What is the difference between an AWS Region and an Availability Zone (AZ)?
A Region is a geographic area (e.g., `us-east-1`) containing multiple, physically separate data centers called Availability Zones, each with independent power, cooling, and networking, connected to other AZs in the same region by low-latency links. Spreading resources across multiple AZs protects against a single data-center-level failure; spreading across Regions additionally protects against a region-wide event and reduces latency for geographically distant users, at the cost of significantly more complexity (data replication/consistency across regions, higher latency between them).

### 3. Explain a VPC and its key components: subnets, route tables, internet gateway, NAT gateway.
A VPC (Virtual Private Cloud) is an isolated virtual network within a cloud account. **Subnets** divide the VPC's IP range across AZs; a subnet is "public" if its route table sends `0.0.0.0/0` traffic to an **Internet Gateway** (allowing direct inbound/outbound internet access) or "private" if it doesn't. A **NAT Gateway** sits in a public subnet and lets instances in a *private* subnet initiate outbound internet connections (e.g., downloading packages) without being directly reachable from the internet inbound. **Route tables** determine how traffic leaving a subnet is directed (to the internet gateway, NAT gateway, VPC peering connection, on-prem VPN, etc.).

### 4. What's the difference between a Security Group and a Network ACL (NACL)?
Security Groups are stateful, instance/ENI-level firewalls — an allowed inbound request automatically allows its corresponding outbound response, and rules are "allow only" (no explicit deny rules). NACLs are stateless, subnet-level firewalls — you must explicitly allow both directions of traffic (including ephemeral response ports), and they support both allow and explicit deny rules, evaluated in numbered order. NACLs are typically used for broad subnet-level blocking (e.g., blocking a known-bad IP range for the entire subnet), while Security Groups do the fine-grained, per-application-tier access control.

### 5. Explain IAM: users, groups, roles, and policies — and the principle of least privilege.
IAM Users represent long-term identities (people or applications) with their own credentials. Groups are collections of users sharing the same policies (easier bulk management). Roles are identities *assumed* temporarily (by an EC2 instance, a Lambda function, another AWS account, or a federated/SSO user) that grant temporary credentials rather than permanent ones — the recommended way for workloads to get AWS permissions instead of embedding long-lived access keys. Policies (JSON documents) define exactly which actions on which resources are allowed/denied. Least privilege means granting only the specific permissions a role/user actually needs to do its job, nothing broader "just in case" — minimizing blast radius if credentials are ever compromised.

### 6. Why should EC2 instances/Lambda functions use IAM roles instead of hardcoded access keys?
Hardcoded long-lived access keys are a major security liability if leaked (in code, logs, or a compromised host) — they don't expire on their own and are easy to accidentally commit to source control. IAM roles provide short-lived, automatically-rotated temporary credentials delivered via the instance metadata service (or Lambda's execution environment) that the AWS SDK picks up automatically — nothing to store, nothing that persists if the instance/function is destroyed, and permissions can be scoped and revoked centrally without touching application code.

### 7. What is the AWS shared responsibility model?
AWS is responsible for "security *of* the cloud" — the physical infrastructure, hypervisor, and managed service internals. The customer is responsible for "security *in* the cloud" — how they configure their resources: IAM permissions, security group rules, data encryption choices, OS-level patching (for unmanaged compute like EC2), and application-level security. The exact dividing line shifts depending on the service — e.g., for Lambda, AWS manages the entire runtime and OS, while for EC2, the customer manages everything above the hypervisor.

### 8. Explain S3 storage classes and when you'd use each.
**Standard** — frequent access, low latency, highest cost per GB. **Standard-IA (Infrequent Access)** — cheaper storage, retrieval fee, for data accessed rarely but needing millisecond access when it is. **Glacier / Glacier Deep Archive** — very cheap long-term archival, retrieval takes minutes to hours, for compliance/backup data rarely if ever accessed. **Intelligent-Tiering** — automatically moves objects between access tiers based on observed access patterns, useful when access patterns are unpredictable and you don't want to manage lifecycle rules manually. Lifecycle policies automate transitions (e.g., move to IA after 30 days, Glacier after 90) to optimize cost without manual intervention.

### 9. What is S3 eventual consistency, and has this changed?
Historically, S3 offered "eventual consistency" for overwrite PUTs and DELETEs (a read immediately after an overwrite could return old *or* new data briefly) though new-object PUTs were always strongly consistent. As of December 2020, AWS S3 provides strong read-after-write consistency for all operations (PUTs and DELETEs, including overwrites) automatically, with no additional cost or configuration — a detail worth knowing since older documentation/answers may reference the old eventual-consistency behavior.

### 10. What's the difference between RDS, Aurora, and DynamoDB?
**RDS** — managed relational databases (Postgres, MySQL, etc.) — AWS handles patching, backups, failover, but it's still a "traditional" relational DB engine underneath. **Aurora** — AWS's own MySQL/Postgres-compatible relational engine with a re-architected storage layer decoupled from compute (storage auto-scales, replicates across AZs at the storage layer itself, faster failover, higher throughput) — a drop-in-compatible but higher-performance alternative to vanilla RDS. **DynamoDB** — fully managed NoSQL key-value/document store, single-digit millisecond latency at virtually any scale, but requires designing your access patterns around its partition-key model upfront (no ad-hoc joins/complex queries like a relational DB) — a fundamentally different data modeling approach, not just a "faster RDS."

### 11. Explain Auto Scaling Groups and how scaling policies work.
An Auto Scaling Group (ASG) maintains a desired number of EC2 instances, automatically replacing unhealthy ones and adjusting capacity based on scaling policies: target tracking (keep a metric like average CPU at X%, ASG computes needed instance count automatically), step scaling (add/remove specific instance counts based on which CloudWatch alarm threshold is breached), or scheduled scaling (predictable traffic patterns, e.g., scale up before a known daily peak). Combined with a Launch Template (instance config: AMI, instance type, user data) and typically attached to a load balancer's target group so new instances automatically start receiving traffic once healthy.

### 12. What is the difference between an ALB, NLB, and CLB?
**ALB** (Application Load Balancer) — Layer 7, HTTP/HTTPS-aware, supports path/host-based routing, WebSocket, and integrates with Lambda targets. **NLB** (Network Load Balancer) — Layer 4, extremely high throughput/low latency, preserves client source IP by default, handles millions of requests/sec, used for non-HTTP TCP/UDP traffic or when ultra-low latency/static IP support is required. **CLB** (Classic Load Balancer) — the legacy generation, largely deprecated in favor of ALB/NLB for new workloads, offering basic L4/L7 capability without the more advanced routing features.

### 13. Explain how CloudWatch works and the difference between metrics, logs, and alarms.
**Metrics** are numeric time-series data (CPU utilization, request count, custom application metrics via `PutMetricData`). **Logs** are text-based event streams (CloudWatch Logs, e.g., application/Lambda logs), which can also be parsed into metric filters to derive metrics from log patterns (e.g., counting "ERROR" occurrences). **Alarms** watch a metric against a threshold over a defined evaluation period and trigger an action (SNS notification, Auto Scaling action, Lambda invocation) when breached — the mechanism that turns passive monitoring data into active response.

### 14. What is the difference between synchronous and asynchronous Lambda invocation, and why does it matter for error handling?
Synchronous (e.g., API Gateway calling Lambda) — the caller waits for a response and gets the error directly if the function fails; retry logic (if any) is the caller's responsibility. Asynchronous (e.g., S3 event notifications, SNS) — AWS queues the event and invokes Lambda independently of any caller waiting; Lambda automatically retries a failed asynchronous invocation (by default twice, with delay), and after exhausting retries, sends the event to a configured Dead Letter Queue or (with newer functions) an On-Failure destination for later inspection/reprocessing rather than the error simply vanishing.

### 15. What is a Lambda cold start, and how do you mitigate it?
A cold start is the extra latency incurred when AWS must provision a new execution environment for a function (downloading code, initializing the runtime and any global/module-level initialization code) before it can process an invocation — noticeable for latency-sensitive synchronous workloads, especially with larger deployment packages, VPC-attached functions (historically slower, though AWS has significantly improved this), or infrequently-invoked functions. Mitigations: Provisioned Concurrency (keep a set number of environments pre-warmed at a cost), minimizing package size/dependencies, choosing a faster-starting runtime, and moving expensive initialization out of the hot path where possible (or doing it at module load time so it's amortized across many warm invocations of the same environment).

### 16. Explain the difference between SQS, SNS, and EventBridge.
**SQS** — a message queue; one message is typically consumed by one consumer (point-to-point), great for decoupling a producer from a worker pool that processes work at its own pace, with built-in visibility timeouts and dead-letter queue support for retry/failure handling. **SNS** — pub/sub; one message is fanned out to *multiple* subscribers (SQS queues, Lambda, HTTP endpoints, email) simultaneously — one-to-many. **EventBridge** — an event bus with rich content-based routing rules (route events to different targets based on event attributes/schema), schema registry, and easy integration with many AWS service events and third-party SaaS sources — suited for more complex event-driven architectures with many event types and routing logic than plain SNS fan-out.

### 17. What is an SQS visibility timeout, and what happens if it's set too short or too long?
When a consumer receives a message from SQS, that message becomes temporarily invisible to other consumers for the visibility timeout duration, giving the consumer time to process and delete it. If too short, the consumer might still be processing when the timeout expires — the message becomes visible again and another consumer could pick it up, causing duplicate processing (so consumers must be idempotent, or the timeout must be extended dynamically for long-running work via `ChangeMessageVisibility`). If too long, a message whose consumer actually crashed/failed sits invisible (effectively "stuck," undelivered to anyone else) for that whole duration before it can be retried.

### 18. What is Infrastructure as Code, and why prefer it over manually configuring cloud resources through the console?
IaC defines infrastructure declaratively in version-controlled files (Terraform, CloudFormation, Pulumi) instead of manual point-and-click console changes. Benefits: reproducibility (spin up identical environments for dev/staging/prod or disaster recovery), auditability/code review of infrastructure changes just like application code, drift detection (compare declared state against actual live state), and avoiding "snowflake" servers/environments whose exact configuration nobody can fully reconstruct because it accumulated through years of undocumented manual tweaks.

### 19. What is the difference between a public and private subnet, and where should a database typically live?
A public subnet's route table sends default (`0.0.0.0/0`) traffic to an Internet Gateway, meaning resources there *can* have a public IP and be directly internet-reachable. A private subnet has no such route (only, at most, a NAT Gateway route for outbound-only access). A database should almost always live in a private subnet — it has no legitimate reason to be directly reachable from the internet, and this drastically reduces attack surface even before considering security group rules as a second layer of defense.

### 20. Explain what a VPC Peering connection and a Transit Gateway are, and when you'd choose one over the other.
VPC Peering directly connects two VPCs' networking as if they were one network, but connections are point-to-point and don't transitively route (VPC A peered with B, and B peered with C, does not let A reach C without its own direct peering) — fine for a small number of VPCs. A Transit Gateway acts as a central hub that many VPCs (and on-prem networks via VPN/Direct Connect) attach to, with the Transit Gateway handling routing between all of them — far more manageable at scale (avoids the N² peering connections problem) and centralizes routing policy, at the cost of being a (highly available, but still) more centralized piece of infrastructure and additional cost per attachment/data processed.

### 21. What's the difference between vertical scaling and horizontal scaling in a cloud context, and their respective limits?
Vertical scaling (scaling up) — moving to a bigger instance type (more CPU/RAM). Simple, no application changes needed, but has a hard ceiling (the largest instance type available) and typically requires downtime/restart to resize, and a single larger instance is still a single point of failure. Horizontal scaling (scaling out) — adding more instances behind a load balancer. Effectively unlimited (bounded by account/region quotas and cost, not a hardware ceiling), improves fault tolerance (losing one of many instances is a small impact), but requires the application to be stateless (or externalize state to a shared store) since requests can land on any instance.

### 22. What is a Reserved Instance / Savings Plan vs. Spot Instance, and what workloads suit each?
Reserved Instances / Savings Plans offer significant discounts (up to ~70%) in exchange for a 1- or 3-year commitment to a baseline amount of compute usage — suited for predictable, steady-state workloads (always-on production services). Spot Instances offer even steeper discounts (up to ~90%) by using AWS's spare capacity, but can be reclaimed by AWS with only a short (2-minute) warning when that capacity is needed elsewhere — suited for fault-tolerant, interruptible workloads (batch processing, CI runners, stateless horizontally-scaled fleets that can absorb losing individual nodes, big-data processing with checkpointing).

### 23. How would you design a highly available, multi-AZ web application on AWS from scratch?
Application servers in an Auto Scaling Group spanning at least 2–3 AZs, behind an ALB that health-checks and only routes to healthy instances/AZs. Database as a managed RDS/Aurora instance with Multi-AZ enabled (synchronous standby replica in a different AZ, automatic failover). Static assets and uploads in S3, served via CloudFront for caching/global distribution. Session state externalized (e.g., to ElastiCache/DynamoDB) rather than kept in-memory on individual instances, so any instance can serve any request (statelessness enabling horizontal scaling and safe instance replacement). DNS via Route 53, potentially with health-check-based failover routing for multi-region DR. Infrastructure defined in Terraform/CloudFormation for reproducibility, with the whole setup deployable identically to a second region for disaster recovery if RTO/RPO requirements demand it.

### 24. What are AWS service quotas / limits, and why do they matter operationally?
Every AWS account has default limits on resource counts/rates per region (e.g., number of VPCs, EC2 instances of a type, API request rate for a service) to protect against runaway usage/billing and shared infrastructure abuse. They matter operationally because hitting an unexpected limit during a scaling event or migration can cause a production incident (e.g., Auto Scaling failing to launch new instances because the account's EC2 instance limit was reached) — proactively requesting limit increases for anticipated growth, and monitoring usage against quotas via CloudWatch/Trusted Advisor, avoids being surprised during exactly the high-traffic moment you need to scale.

### 25. Explain the concept of a "well-architected" pillar framework (at a high level) and why it's used in cloud architecture reviews.
AWS's Well-Architected Framework organizes architectural decision-making into pillars: operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability. It's used as a structured checklist/lens during architecture reviews to systematically evaluate tradeoffs (e.g., "this design is cost-optimized but weak on reliability — is that an acceptable tradeoff for this specific workload's requirements?") rather than optimizing any single dimension in isolation, since real systems constantly trade these concerns against each other.
