# Docker & Containers — DevOps Interview Questions

---

### 1. What is Docker, and how does a container differ from a VM? (see also Linux fundamentals Q26–27)
Docker is a platform for building, shipping, and running applications in containers — lightweight, isolated user-space environments that share the host kernel. Unlike a VM (full guest OS + hypervisor), a container starts in milliseconds, has near-zero overhead beyond the process itself, and many containers can share one host kernel — but isolation is weaker than a VM's hardware-level boundary.

### 2. Explain a Dockerfile's key instructions: `FROM`, `RUN`, `COPY` vs `ADD`, `WORKDIR`, `ENV`, `ARG`, `EXPOSE`, `CMD` vs `ENTRYPOINT`.
`FROM` — base image. `RUN` — executes a command at *build* time, creating a new layer. `COPY` — copies files from build context into the image (prefer this). `ADD` — like `COPY` but also auto-extracts local tar archives and can fetch remote URLs (surprising side effects, generally avoid unless you need those specific behaviors). `WORKDIR` — sets the working directory for subsequent instructions/runtime. `ENV` — sets environment variables persisted into the final image and runtime. `ARG` — build-time-only variable (not present at runtime, not persisted in the image; passed via `--build-arg`). `EXPOSE` — documentation/metadata about which port the container listens on (does not actually publish it — `-p` at `docker run` does that). `CMD` — default command/args for the container, easily overridden by args passed to `docker run`. `ENTRYPOINT` — the fixed executable a container runs; `CMD` (if also set) supplies default *arguments* to it — combining both (`ENTRYPOINT ["python", "app.py"]`, `CMD ["--port=8080"]`) gives a container that behaves like a configurable binary.

### 3. What are Docker image layers, and how does layer caching speed up builds?
Each Dockerfile instruction (`RUN`, `COPY`, `ADD`) creates a new, immutable, content-addressed layer stacked on the previous one (via a union/overlay filesystem). Docker caches layers by instruction + context hash; if an instruction and everything before it are unchanged, the cached layer is reused instead of re-executed. This is why Dockerfiles put rarely-changing steps first (installing OS packages, then dependency manifests + `npm install`/`pip install`) and copy application source code *last* — so an app code change only invalidates the cache from that layer onward, not the expensive dependency-install layer.

### 4. What is a multi-stage build, and why use one?
A Dockerfile can have multiple `FROM` stages; later stages can selectively `COPY --from=<earlier stage>` specific artifacts. This lets you use a large "builder" image with compilers/SDKs/dev dependencies to build the app, then copy only the final compiled binary/artifacts into a minimal runtime base image (e.g., `scratch`, `distroless`, or `alpine`) — dramatically reducing final image size and attack surface, since build tools and source never ship in the production image.

### 5. Why should you avoid running containers as root, and how do you fix it?
Root inside a container is still UID 0 — if a container-escape vulnerability is exploited, running as root gives an attacker root-equivalent capabilities on the host (or at least a much larger blast radius) rather than a constrained unprivileged user. Fix: create a dedicated user in the Dockerfile (`RUN adduser -D appuser`) and switch to it (`USER appuser`) before the final `CMD`/`ENTRYPOINT`; Kubernetes' `securityContext.runAsNonRoot: true` can enforce this at the cluster level.

### 6. Explain the difference between a Docker volume, a bind mount, and tmpfs.
A **volume** is storage managed entirely by Docker (lives under `/var/lib/docker/volumes/`), decoupled from any specific host path, portable, and the recommended way to persist data (databases, uploads) beyond a container's lifecycle. A **bind mount** maps a specific host filesystem path directly into the container — useful for local development (live-reloading source code) but couples the container to the host's exact filesystem layout, and the container can accidentally overwrite/be affected by host file permissions. **tmpfs** mounts store data only in host memory (RAM), never touching disk — fast, and automatically wiped when the container stops, good for secrets or ephemeral scratch data that shouldn't persist or hit disk.

### 7. What happens to data written inside a container's writable layer when the container is removed?
It's lost — a container's own filesystem layer is ephemeral and deleted along with the container (`docker rm`). Any data that needs to survive container restarts/replacement must be in a volume or bind mount attached to that path.

### 8. Explain Docker networking modes: bridge, host, none, and overlay.
**bridge** (default) — each container gets its own network namespace and a private IP on a virtual bridge network on the host; ports must be explicitly published (`-p`) to be reachable from outside. **host** — the container shares the host's network namespace directly (no isolation, no port mapping needed, but higher performance and a security/port-conflict tradeoff). **none** — no networking at all, fully isolated. **overlay** — spans multiple Docker hosts (used in Swarm, and conceptually similar to what CNI plugins provide in Kubernetes), letting containers on different physical/VM hosts communicate as if on the same L2 network, typically via VXLAN encapsulation.

### 9. How do containers on the same user-defined bridge network discover each other?
Docker's embedded DNS server resolves container names (and Compose service names) to their current IP automatically for containers on the same user-defined bridge network — you can simply connect to `http://api:8080` from another container named appropriately, rather than hardcoding IPs (which change on restart). This does *not* work on the legacy default `bridge` network, which is a common gotcha — always create/use a user-defined network.

### 10. What's the difference between `CMD ["executable", "arg"]` (exec form) and `CMD executable arg` (shell form)?
Exec form (`["executable", "arg1"]`) runs the process directly as PID 1 without a shell wrapping it — signals (like `SIGTERM` from `docker stop`) go straight to your process, letting it handle graceful shutdown. Shell form runs `/bin/sh -c "executable arg1"`, meaning the shell becomes PID 1 and your actual process is a child — signals go to the shell, which may not forward them properly to the child, causing `docker stop` to hang until the timeout and force-kill. Prefer exec form for anything that needs clean shutdown handling.

### 11. Why might a container not respond to `docker stop` and require the full timeout + `SIGKILL`?
Common causes: shell-form `CMD`/`ENTRYPOINT` not forwarding `SIGTERM` to the actual application process (see Q10); the application not having a `SIGTERM` handler at all (falls back to default behavior, which for many runtimes/languages is to terminate — but some frameworks or wrapper scripts swallow signals); or being PID namespace-isolated behind an init/wrapper process that doesn't propagate signals — using `--init` (or `tini` as the entrypoint) ensures a minimal init process correctly reaps zombies and forwards signals.

### 12. What is `.dockerignore` and why is it important?
Like `.gitignore`, it excludes files/patterns from being sent to the Docker daemon as part of the build context (e.g., `node_modules`, `.git`, local `.env` files, build artifacts). Important for build speed (smaller context uploads faster, especially to a remote daemon or BuildKit), avoiding cache invalidation from irrelevant file changes, and preventing accidental inclusion of secrets or large unnecessary files in the image.

### 13. How do you keep a Docker image small, and why does it matter?
Use a minimal base image (`alpine`, `distroless`, `scratch` for static binaries); use multi-stage builds to exclude build tools; combine related `RUN` commands with `&&` and clean up package manager caches in the *same* layer (`apt-get update && apt-get install -y x && rm -rf /var/lib/apt/lists/*` — cleaning in a later separate `RUN` doesn't shrink the layer that already has the cache baked in); avoid copying unnecessary files (`.dockerignore`). Smaller images mean faster pulls/pushes/deploys, smaller attack surface, and lower storage/bandwidth cost, especially significant at scale (thousands of deploys or nodes pulling the same image).

### 14. Explain image tags and why `:latest` is risky in production.
A tag is a mutable pointer to a specific image digest (immutable content hash). `:latest` is just a conventional default tag with no special meaning to Docker — it gets overwritten every time someone pushes without specifying a tag, so `docker pull myapp:latest` can silently fetch a *different* image tomorrow than it did today, breaking reproducibility and making rollbacks/debugging ambiguous ("which version is actually running?"). Production deployments should pin explicit, immutable versions (a semver tag or, even better, the image digest `myapp@sha256:...`) so the exact same bytes are guaranteed to run everywhere.

### 15. What is Docker Compose, and what problem does it solve?
Compose defines a multi-container application (services, networks, volumes, dependencies, environment config) declaratively in a single YAML file, and `docker compose up` creates/starts the whole stack with one command — solving the tedium and error-proneness of manually running many `docker run` commands with matching network/volume/env flags, primarily for local development and simple single-host deployments (not a replacement for an orchestrator like Kubernetes in production at scale).

### 16. How does `docker exec` differ from `docker attach`?
`docker exec -it <container> bash` starts a *new* process inside the container's namespaces (e.g., a debugging shell) alongside whatever is already running — the most common way to poke around a running container. `docker attach` connects your terminal to the *existing* main process's stdin/stdout/stderr (PID 1) — if that process isn't interactive (e.g., a web server), attaching mostly just streams its logs, and pressing Ctrl+C can send a signal that stops the container entirely, which is a common surprise.

### 17. How do you limit a container's CPU and memory usage, and what happens when it exceeds the memory limit?
`docker run --memory=512m --cpus=1.5 ...` (backed by cgroups, same mechanism as Kubernetes resource limits). If a container exceeds its memory limit, the kernel's OOM killer terminates a process inside that container's cgroup (visible as `OOMKilled: true` in `docker inspect`) — it does not get gracefully throttled the way CPU does (CPU limits throttle/share time rather than kill).

### 18. What's the difference between a container's "restart policy" options: `no`, `on-failure`, `always`, `unless-stopped`?
`no` (default) — never automatically restart. `on-failure[:max-retries]` — restart only if the container exits with a non-zero code, up to an optional retry cap. `always` — always restart regardless of exit status, including after a daemon/host reboot, and even if manually stopped it will restart on daemon restart unless explicitly stopped after that. `unless-stopped` — like `always`, but if the container was manually stopped, it stays stopped even across a daemon restart (avoids the surprise of a deliberately-stopped container coming back after a host reboot).

### 19. How do you securely pass secrets to a container (and why is `ENV` in a Dockerfile a bad way to do it)?
Baking a secret into the Dockerfile via `ENV` or `ARG` bakes it into the image layer history permanently — anyone with pull access to the image (or who inspects its layers) can extract it, and it can't be rotated without rebuilding. Better options: inject secrets at runtime via environment variables passed to `docker run -e`/orchestrator secret objects (still visible via `docker inspect`/`/proc/<pid>/environ`, so not ideal for very sensitive data), mount them as files from a secrets manager (Docker Swarm secrets, Kubernetes Secrets — ideally backed by an external vault with encryption at rest), or use BuildKit's `--secret` flag for build-time secrets (e.g., a private package registry token) that are available only during that specific `RUN` step and never persisted in a layer.

### 20. What is container image scanning, and why is it part of a secure CI/CD pipeline?
Image scanning (Trivy, Grype, Snyk, or cloud-native scanners like ECR/GCR scanning) inspects an image's OS packages and application dependencies against known CVE databases, flagging vulnerable versions before deployment. It's typically wired into CI as a gate (fail the build/block promotion on critical/high severity findings) and run periodically against already-deployed images too, since new CVEs are discovered continuously against unchanged image contents.

### 21. Explain the difference between `docker build` (legacy builder) and BuildKit.
BuildKit (now the default builder) parallelizes independent build stages/instructions instead of executing strictly sequentially, has smarter, more granular caching (including cache mounts for package manager caches across builds, `--mount=type=cache`), supports build secrets that never land in image layers, and can output directly to registries/other formats without an intermediate local image — generally faster and more secure than the legacy sequential builder.

### 22. A container works fine locally but fails in CI/production with "works on my machine." What are common causes?
Base image or dependency version drift (local image cached/built earlier than a since-changed `latest` tag upstream); architecture mismatch (Apple Silicon arm64 image vs. amd64 production hosts — `docker buildx build --platform` addresses this); environment variables/secrets present locally but not configured in the target environment; file permission differences (bind mounts inherit host UID/GID locally, which won't exist the same way in CI); resource limits in production (memory/CPU caps) not present in an unconstrained local run, causing an OOM kill that doesn't reproduce locally; and non-deterministic build steps (e.g., pulling `latest` of a dependency inside the Dockerfile instead of a pinned version).

### 23. What is a "distroless" image, and what's the tradeoff?
A distroless base image contains only an application and its runtime dependencies (e.g., the language runtime) — no shell, no package manager, no unnecessary OS utilities. This drastically reduces attack surface and image size, but the tradeoff is you can't `docker exec ... sh` into it to debug interactively (no shell exists), so debugging requires either an ephemeral debug container attached to the same namespaces (Kubernetes' `kubectl debug`), or shipping a separate debug-variant image for troubleshooting.

### 24. How would you debug a container that immediately exits after `docker run`?
`docker logs <container>` (or `docker logs --tail 100 <container>` if it already exited — the container object and its logs persist until removed) to see the actual error/stack trace. `docker inspect <container>` to check the exit code (`State.ExitCode`) — 0 is a legitimate clean exit (maybe the entrypoint script finished and had nothing to keep running), 137 typically indicates it was OOM-killed (128+9), 1 or other non-zero usually an application error. If logs are unhelpful, override the entrypoint to drop into a shell instead (`docker run -it --entrypoint sh <image>`) to interactively poke around and manually run the intended startup command to see the real error.

### 25. What is the container image manifest / multi-arch manifest list, and why does it matter for Apple Silicon / ARM deployments?
An image manifest describes an image's layers and config for one specific architecture/OS. A "manifest list" (multi-arch manifest) groups multiple architecture-specific images under one tag — when you `docker pull myimage:1.0` on an arm64 host vs. an amd64 host, the same tag resolves to the correct underlying image for that platform automatically. `docker buildx build --platform linux/amd64,linux/arm64 --push` builds and publishes both in one command, which matters increasingly with ARM-based cloud instances (AWS Graviton) and Apple Silicon dev machines needing to build images that also run correctly on amd64 production servers.
