# Scenario-Based & Troubleshooting Questions — DevOps Interview Questions

> These are the "walk me through how you'd debug X" questions common in senior/on-call-heavy interviews. Answers give a structured approach, not just a single command.

---

### 1. Production is down. Users are getting 500 errors. Walk me through your first 5 minutes.
Acknowledge the alert/page first (stop the escalation clock, signal you're on it). Check the top-level dashboard/golden signals (error rate, latency, traffic) to confirm scope and severity — is it all traffic or a subset (one region, one endpoint, one customer)? Check what changed recently — a deployment, a config change, a feature flag flip, an infra change — correlated with the start time (this is very often the actual cause). If a recent deploy correlates, the fastest safe mitigation is usually rolling it back *before* fully understanding root cause — restoring service comes before root-causing. Declare an incident/pull in help if it's not immediately obvious or if it's high severity, rather than debugging solo for too long.

### 2. Deploys have been fine all week, but this one specific deploy caused errors. How do you find the exact cause quickly?
Diff the deploy against the previous good one — code changes, config changes, dependency version bumps, database migrations included in the same release. Check the error messages/stack traces first — they often point directly at the new code path. If it's not obvious from the diff, and the deployment platform supports it, roll back immediately to restore service, then reproduce the issue in a staging/lower environment using the same rolled-back-from artifact, where you can debug without production time pressure or continued user impact. Check whether the new version has different resource requirements (a memory leak, higher CPU) that only becomes visible under real production load/data volume, which staging load testing may not have caught.

### 3. CPU usage across your fleet has been steadily climbing over the past two weeks with no obvious deploy correlated to when it started. How do you investigate?
Check if it correlates with organic traffic/data growth rather than a code change (plot CPU per-request rather than absolute CPU — if per-request cost is flat but total traffic grew, it's a capacity/scaling issue, not a regression). If per-request cost itself is rising, check for a slow memory/resource leak that increases CPU indirectly (e.g., GC pressure from a growing in-memory cache with no eviction), a slowly growing dataset causing a previously-fast code path (an unindexed query, an O(n) loop over a growing collection) to degrade, or a slow-burn issue introduced by a change two weeks ago that only manifests gradually (e.g., a cache that's slowly being evicted more due to a subtly wrong TTL). Use profiling (flamegraphs) on a representative instance to see exactly where CPU time is actually going now vs. historically if you have baseline profiles.

### 4. A specific customer reports intermittent failures, but you can't reproduce it and your dashboards look fine. How do you approach this?
Ask for exact details: timestamps, request IDs (if their client surfaces one), specific error messages/screenshots — vague "sometimes it fails" reports need to become concrete, searchable data points. Search logs/traces for that customer's specific requests around the reported times (their account/tenant ID as a filter) rather than relying on aggregate dashboards, which can easily hide a low-percentage or single-customer-specific issue (e.g., an edge case in their specific data shape, a regional routing quirk, or a rate limit they're intermittently hitting). Check if they're unusual in some dimension (much larger data volume than typical, a specific integration/API usage pattern others don't use, a specific geographic region) that could explain why it's not visible in overall aggregate metrics.

### 5. Your database's CPU is pegged at 100% and queries are timing out. Walk through your diagnosis.
Check currently running/slow queries (`SHOW PROCESSLIST` / `pg_stat_activity` or equivalent) to identify what's actually consuming CPU right now — a single expensive query (missing index causing a full table scan), a sudden spike in query volume, or lock contention (queries waiting on locks show as "active" but aren't actually making progress, which can look like CPU load but is really contention). Check recent schema/query changes and recent data growth (a query that was fine at 1M rows can become a full-table-scan disaster at 100M rows if an index wasn't added). If it's a single runaway query, consider killing it as immediate mitigation while investigating the underlying cause (missing index, a newly-introduced N+1 query pattern, a bad query plan from stale statistics).

### 6. Requests are succeeding, but latency has doubled for everyone. No errors, no CPU/memory spike. What do you check?
This pattern often points to I/O wait, lock contention, or a downstream dependency slowdown rather than a resource-exhaustion problem — check `iostat`/disk latency, database query latency specifically (not just app-level latency, to isolate whether the DB itself slowed down), and the latency of any external/downstream service calls (a third-party API, another internal microservice) via distributed traces, since app-level CPU/memory looking normal strongly suggests the app itself is just *waiting* on something rather than working harder. Also check for connection pool exhaustion (requests queueing for a DB connection that's not immediately available, adding wait time without necessarily causing errors if the pool eventually frees up) and network-level issues (increased packet loss/retransmits between services, even without outright failure).

### 7. A Kubernetes Pod keeps getting OOMKilled even though the application "shouldn't" be using that much memory. How do you investigate?
Confirm the actual container memory limit vs. what the app believes its available memory is — some language runtimes (older JVM versions, for instance) don't automatically respect cgroup limits and instead size their heap based on the *node's* total memory, over-allocating inside a much smaller container limit. Check for an actual memory leak (steadily climbing RSS over time via `kubectl top pod` history or a metrics dashboard, rather than a sudden spike) vs. a legitimate but underestimated peak usage (a batch/bulk operation that legitimately needs more headroom than the configured limit — check if OOM kills correlate with specific request types/times, like a large report-generation endpoint). Compare the configured `limits.memory` against realistic p99 usage with reasonable headroom, and check whether request/limit were set once early in the service's life and never revisited as usage patterns changed.

### 8. Your CI pipeline suddenly started failing for everyone on every branch, with no code changes involved. How do you approach this?
Since it's affecting all branches/PRs simultaneously with no code change common to all of them, suspect an external/environmental cause rather than application code: a CI provider outage or platform change, an expired credential/certificate used by the pipeline (API key, registry auth token), a third-party dependency/registry being unreachable or having published a breaking version that a non-pinned dependency now resolves to, a change to a shared CI configuration/reusable workflow, or an infrastructure change (a runner image update, a network/firewall change affecting the CI environment's connectivity). Check the CI provider's own status page first, then look at exactly what CI logs show failing (the specific step and error message) rather than assuming it's a "flaky CI" and re-running blindly.

### 9. After a routine dependency/library upgrade, tests pass in CI but the application crashes intermittently in production only under real load. Why might this happen, and how do you find it?
CI test suites often don't replicate production's concurrency level, data volume, or specific execution environment — a new library version might introduce a subtle behavior change that only manifests under concurrent access (a thread-safety regression, a connection pool behavior change) or with production-scale data (a changed default limit/buffer size that's fine for small test fixtures but overflows at real volume). Investigation: check the library's changelog/release notes between the old and new version for any behavioral (not just API-signature) changes; try to reproduce under load testing that mimics production concurrency rather than relying on CI's typically single-threaded/low-volume test execution; and check if rolling back just that dependency (while keeping everything else at the new deploy) resolves it, isolating it definitively as the cause before investigating further.

### 10. You need to roll out a database schema change that the application depends on, with zero downtime. Walk through your approach.
Use the expand-contract pattern (see CI/CD file, Q19): first deploy a migration that only *adds* the new structure (new column/table) without removing/renaming anything the current code still uses, so old and new application versions can coexist during the rollout. Deploy application code that writes to both old and new structures (or just the new one, if it's purely additive) while still being able to read the old one if needed for rollback safety. Backfill existing data into the new structure (ideally in batches, off-peak, monitoring for load impact — a naive single massive `UPDATE` can lock the table or overwhelm replication). Deploy code that fully switches to using only the new structure. Only after that version has been running successfully for a safe period (long enough that rolling back application code is no longer a realistic need) does a final, separate migration remove the old, now-unused structure.

### 11. You're asked to reduce cloud costs by 30% without degrading reliability. What's your approach?
Start with visibility — cost allocation tags/dashboards to see where spend actually concentrates (often a small number of services/resources dominate total cost — the "80/20" is real here). Look for clear waste first (idle/oversized resources — unattached volumes, over-provisioned instances running well below utilization, forgotten dev/test environments left running, redundant data stored in expensive tiers that could move to cheaper storage classes with lifecycle policies). Then look at pricing model optimization (Reserved Instances/Savings Plans for steady-state predictable workloads, Spot for fault-tolerant/batch workloads) before touching architecture. Only after those are exhausted consider actual architectural changes (right-sizing based on real utilization data, not guesswork; more aggressive autoscaling; caching to reduce expensive downstream calls/database load) — and validate every change against reliability metrics (error rate, latency, SLO burn) before and after, since the easiest way to "save 30%" badly is to under-provision and cause an outage, which costs far more than the savings.

### 12. Two engineers deployed to production around the same time and now something's broken — how do you figure out which change (or interaction between both) is responsible, and what process gap does this expose?
Check the exact deployment timestamps against when the issue actually started (correlate precisely, not just "recently") — if only one deploy's timing lines up, investigate that one first; if the issue started only after *both* were live, suspect an interaction between them (e.g., one changed an API contract the other's new code assumed the old version of) rather than either being independently broken. This scenario itself is a signal of a process gap worth raising afterward regardless of root cause: deployments to production ideally shouldn't overlap without coordination (a deployment lock/queue, or at minimum visibility into "someone else is also deploying right now"), and if the two changes had been deployed one at a time with a health-check pause between them, attribution would have been immediate instead of requiring investigation.

### 13. A load balancer health check is marking all your instances unhealthy simultaneously, but the application itself seems to be running fine when you check manually. What would you look at?
Check the health check configuration itself against what actually changed recently — the health check endpoint's expected response code/body, the timeout value (if the app's health endpoint got slower, e.g. because it now checks a downstream dependency, it might now exceed a timeout that was fine before), or the health check path/port (a misconfigured deploy pointing it at the wrong port/path). Check if the health check endpoint specifically (as opposed to the app generally) depends on something currently failing — a common design mistake is a health check that checks downstream dependencies (DB, cache) rather than just "is this process alive," so a downstream blip marks otherwise-perfectly-fine app instances as unhealthy and can cause a self-inflicted total outage when a partial degradation (like a slow-but-working DB) triggers a full removal from the load balancer pool.

### 14. How would you approach an incident where you suspect the root cause but fixing it requires a risky change, and you're not 100% sure the fix is correct?
Weigh the cost of being wrong each direction: does the current impact justify the risk of an imperfect fix, or is a safer, even if slower, path available (e.g., mitigating impact first — routing around the problem, rate limiting, feature-flagging off the affected path — buying time to verify the fix more confidently before applying it)? If the risky change must be made, make it as reversible as possible (deploy to a small canary/subset first if at all feasible even during an incident, keep the previous state readily restorable) and communicate the uncertainty and reasoning clearly to the incident channel/IC rather than presenting a guess as certainty — a well-communicated, monitored, reversible calculated risk is very different from a silent gamble.

### 15. How do you differentiate between "this is a real capacity/scaling problem" and "this is a bug causing resource waste" when a service is struggling under load?
Compare current per-unit resource cost (CPU/memory/DB-time per request) against a historical baseline at similar traffic levels — if per-request cost is roughly flat and total traffic genuinely grew beyond provisioned capacity, it's a scaling/capacity problem (the fix is more capacity/better autoscaling). If per-request cost itself has increased (the same kind of request now costs meaningfully more resources than it used to at equivalent traffic), that points to a regression/bug (a newly introduced inefficient query, a cache that stopped being effective, a leak) — throwing more capacity at a per-request regression treats the symptom and gets progressively more expensive as the underlying inefficiency compounds, whereas throwing more capacity at genuine organic growth is the correct, expected response.
