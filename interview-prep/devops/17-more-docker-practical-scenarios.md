# More Docker Questions — Practical Commands & Scenario Debugging

> Sourced/topic-checked against GeeksforGeeks' and KodeKloud's Docker interview question lists. Supplements `04-docker-containers.md` with command-level and scenario-based questions.

---

### 1. What's the difference between `docker save`/`docker load` and `docker export`/`docker import`?
`docker save` exports a full image (including all its layers and metadata/history) to a tar archive, restorable with `docker load` as a complete image with its original layer structure and tags intact. `docker export` exports a *container's* current filesystem as a flat tar archive (no layer history, no image metadata) — restorable with `docker import` as a brand-new single-layer image with no relationship to the original image it came from. Use `save`/`load` to move an actual image (with history/tags) between environments (e.g., air-gapped systems without registry access); use `export`/`import` when you specifically want to flatten a container's current filesystem state into a fresh, minimal-layer image (discarding history) or need to move a container's contents where full image fidelity doesn't matter.

### 2. What are the possible states of a Docker container, and how do you transition between them?
**Created** — the container exists (from `docker create`) but hasn't started running. **Running** — actively executing. **Paused** — execution is frozen (via `docker pause`, using cgroup freezer) without stopping the process, useful for a brief consistent snapshot without a full restart. **Stopped/Exited** — the main process has terminated (`docker stop` sends SIGTERM then SIGKILL after a grace period; the process can also exit on its own). **Deleted** — removed entirely via `docker rm` (must be stopped first, unless using `docker rm -f` which force-stops then removes). Understanding these states matters for scripting cleanup/automation correctly (e.g., you can't `docker rm` a running container without `-f`, and a paused container also can't be removed until unpaused or force-removed).

### 3. Why might your code changes not show up after rebuilding a Docker image?
Most common cause: Docker's build cache reused a stale layer because the layer *before* your code-copy instruction didn't change (from Docker's perspective) even though your actual source changed — this happens if your `.dockerignore` accidentally excludes the changed files, or if you're mounting a volume over the code directory at *runtime* that's shadowing the newly-built image's baked-in code with an old version from disk. Also check you're actually running a container from the newly-built image tag and not an old cached container/image still tagged the same way (`docker images` to check the image's actual build timestamp, or use `--no-cache` to force a full rebuild as a diagnostic step to rule out caching as the cause).

### 4. A container was killed with exit code 137. What does this mean, and how do you confirm the cause?
Exit code 137 = 128 + 9, meaning the process received `SIGKILL` (signal 9) — almost always because it was OOM-killed (exceeded its memory limit) or manually force-killed. Confirm via `docker inspect <container>` and check the `State.OOMKilled` field (`true` confirms it was memory-related) — if `OOMKilled` is `false` despite exit 137, something external explicitly sent SIGKILL (a script, an orchestrator, or a manual `docker kill`) rather than the kernel's OOM killer, pointing your investigation in a different direction (check what else was managing that container, e.g., a Kubernetes liveness-probe-triggered kill would show up differently — check `kubectl describe pod` in that case instead).

### 5. Data written inside a container disappeared after `docker rm`. Why, and how do you prevent it?
A container's own writable layer is ephemeral — removing the container deletes that layer along with any data written directly to the container's filesystem, unless that specific path was backed by a volume or bind mount (see the main Docker file's Q6). Prevention: identify every path that needs to survive container replacement (databases, uploads, logs meant to persist) and explicitly mount a named volume or bind mount at that path *before* the container ever runs — this needs to be planned upfront, since retroactively "recovering" data from an already-removed container's writable layer generally isn't possible (a stopped-but-not-removed container's layer can still be inspected/copied via `docker cp`, but once `rm`'d, it's gone).

### 6. Two containers on the same Docker network can't reach each other by name. What's likely going on?
Most common cause: they're on the *default* bridge network rather than a user-defined bridge network — Docker's embedded DNS-based name resolution only works on user-defined networks (see the main Docker file's Q9), so containers on the default `bridge` network must communicate by IP (which isn't a great practice anyway) or need to be reattached to a shared user-defined network (`docker network create`, then `docker network connect`). Other causes: a typo in the container/service name being used to connect, the target container not actually being on the same network (check `docker network inspect <network> `for member containers), or the target application inside the container only listening on `127.0.0.1` instead of `0.0.0.0` (meaning it only accepts connections from within its own container's loopback, not from other containers on the shared network).

### 7. Why does `docker stop` sometimes take about 10 seconds, and how do you fix it?
`docker stop` sends `SIGTERM`, waits for a grace period (default 10 seconds), and only sends `SIGKILL` if the container hasn't exited by then — if it's consistently taking the full 10 seconds, the container's main process isn't handling/responding to `SIGTERM` at all (see the main Docker file's Q10-11: often caused by shell-form `CMD`/`ENTRYPOINT` not forwarding the signal, or the application code simply lacking a signal handler) and Docker is just waiting out the full timeout before force-killing it. Fix: use exec-form `CMD`/`ENTRYPOINT`, implement a proper `SIGTERM` handler in the application for graceful shutdown, and/or use `--init` (or `tini`) as a lightweight init process to ensure correct signal forwarding.

### 8. Your image is over a gigabyte and builds slowly. How do you diagnose and shrink it?
Diagnose with `docker history <image>` (shows each layer's size, revealing which instruction added the most bloat) or `dive <image>` (a dedicated tool for interactively exploring layer contents). Common fixes: switch to a smaller base image (`alpine` or `distroless` instead of a full `ubuntu`/`debian`), use multi-stage builds to exclude build-time-only tools/dependencies from the final image, combine `RUN` commands and clean up package manager caches within the *same* layer, and check `.dockerignore` is actually excluding unnecessary files (large local directories like `.git`, `node_modules`, or build artifacts accidentally being copied into the build context and then into the image).

### 9. What is a dangling image, and how do you clean them up?
A dangling image is one with no tag and not referenced by any container — typically leftover intermediate layers/results from repeated builds (each time you rebuild with the same tag, the previous image with that tag becomes untagged/dangling rather than being deleted, since removing it might break something still referencing it). `docker images -f dangling=true` lists them, and `docker image prune` removes them (add `-a` to `docker system prune -a` to also remove unused-but-tagged images, and `--volumes` to also remove unused volumes) — a routine cleanup step to prevent local disk (or a CI runner's disk) from silently filling up over many build iterations.

### 10. What is the `HEALTHCHECK` instruction in a Dockerfile, and how does it interact with orchestration?
`HEALTHCHECK CMD curl -f http://localhost/health || exit 1` defines a command Docker runs periodically inside the container to determine if it's actually healthy (not just "running," which only tells you the main process hasn't exited) — `docker ps` then shows a `healthy`/`unhealthy`/`starting` status. This is conceptually the same idea as a Kubernetes liveness/readiness probe (see the Kubernetes file) but defined at the image level rather than the orchestrator level — in plain Docker/Compose setups without Kubernetes, it's how `depends_on: condition: service_healthy` in Compose knows a dependency is actually ready, not just started.

### 11. What is Docker Swarm, and how does it differ from Kubernetes?
Docker Swarm is Docker's own built-in, simpler container orchestrator — clustering multiple Docker hosts, scheduling containers ("services") across them, with built-in load balancing and rolling updates, using the same Docker CLI/API developers already know. It differs from Kubernetes in scope and adoption: Swarm is much simpler to set up and reason about (fewer concepts, faster to learn) but has a smaller feature set (less sophisticated scheduling, autoscaling, and a much smaller ecosystem/plugin base) and has seen declining industry adoption in favor of Kubernetes, which — despite being significantly more complex — has become the de facto standard with a vastly larger ecosystem (Helm, Operators, service meshes, cloud-managed offerings) that most organizations standardize on even at the cost of Swarm's relative simplicity.

### 12. What's the difference between daemon-level logging and container-level logging in Docker, and why does it matter for log volume/retention?
Each container's stdout/stderr is captured by a logging *driver* configured at the Docker daemon level (default is `json-file`, writing to a local file per container; alternatives include forwarding directly to `syslog`, `journald`, or a centralized logging backend like Fluentd/AWS CloudWatch Logs). Without an explicit log rotation/size limit configured on the daemon (`log-opts` like `max-size`/`max-file`), the default `json-file` driver can grow unbounded and fill the host's disk over time for a long-running, chatty container — a genuinely common production incident cause, distinct from and often overlooked next to application-level log rotation (see the Linux file's `logrotate` question), since container logs bypass traditional `/var/log`-based logrotate entirely unless specifically configured to interact with it.

### 13. What's the difference between the Docker Community Edition (CE) and Enterprise Edition (EE) / Docker Business, practically speaking?
Docker CE (now largely just "Docker Engine," open source) provides the core container runtime/CLI functionality for free. Enterprise/Business tiers add centralized management, enhanced security scanning, support SLAs, and enterprise-focused features (e.g., Docker Scout for advanced vulnerability management, Docker Desktop licensing requirements for larger organizations) — the practical interview-relevant point is knowing that "Docker" as most engineers use it day-to-day is the free/open engine, while paid tiers are about organizational tooling/support/compliance on top of the same underlying container runtime, not a functionally different way of running containers.

### 14. How would you limit a container's resource usage, and what happens on the CPU side vs. the memory side when a container hits its limit?
`docker run --memory=512m --cpus=1.5 <image>` (backed by cgroups). On the memory side, exceeding the limit triggers the kernel OOM killer to terminate a process in that container's cgroup (hard kill, exit code 137 — see Q4). On the CPU side, exceeding the limit doesn't kill anything — the container is *throttled* (its processes are allowed to use CPU only up to the configured quota within each scheduling period, then made to wait), which can silently degrade performance/latency without any obvious error, making CPU throttling a notoriously easy-to-miss root cause of "the app just feels slow" complaints unless you specifically check for throttling metrics (see the same CPU-throttling gotcha discussed for Kubernetes in the main Kubernetes file).

### 15. Explain how Docker's build cache actually decides whether to reuse a layer.
For each instruction, Docker checks if there's an existing cached layer built from the *exact same preceding layer* plus the *exact same instruction* (and, for `COPY`/`ADD`, a checksum of the actual files being copied — not just the instruction text) — if all of that matches, the cached result is reused with no re-execution; if anything differs, that layer and every layer after it must be rebuilt (cache invalidation "cascades" downward through the rest of the Dockerfile), which is precisely why instruction *ordering* matters so much for build speed (put rarely-changing steps first, frequently-changing steps, like copying application source, last).
