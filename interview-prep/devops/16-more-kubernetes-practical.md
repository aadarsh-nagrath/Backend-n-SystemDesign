# More Kubernetes Questions — Practical & Storage/Scheduling Deep Dive

> Sourced/topic-checked against GeeksforGeeks' and KodeKloud's Kubernetes interview question lists. Supplements `05-kubernetes.md` with storage, scheduling, and operational questions not covered there.

---

### 1. What is a Static Pod, and how does it differ from a normal Pod managed by the API server?
A Static Pod is managed directly by the `kubelet` on a specific node, defined by manifest files placed in a watched directory on that node (not created via the API server) — the kubelet itself creates a mirror Pod object in the API server so it's visible via `kubectl get pods`, but that mirror is read-only from the API server's perspective (you can't edit/delete it through `kubectl`; you must edit the actual manifest file on the node). Static Pods are how Kubernetes bootstraps its own control-plane components (`kube-apiserver`, `kube-scheduler`, `etcd` are frequently run as Static Pods on control-plane nodes) — solving the chicken-and-egg problem of running the API server itself as a Pod when there's no API server yet available to schedule it.

### 2. Explain the Sidecar, Ambassador, and Adapter multi-container Pod patterns.
**Sidecar** — a helper container extending/enhancing the main container's functionality (a log shipper, a service mesh proxy) without the main container needing to know about it. **Ambassador** — a proxy container that simplifies the main container's view of the outside world (e.g., an ambassador container that the main app talks to on `localhost`, which then handles the complexity of connecting to a sharded/clustered external database, hiding that complexity from the app). **Adapter** — a container that standardizes/transforms the main container's output into a uniform format expected by external tooling (e.g., an adapter that reformats an app's non-standard log/metrics output into a standard format a monitoring system expects), without modifying the main application itself.

### 3. Explain PersistentVolume (PV), PersistentVolumeClaim (PVC), and StorageClass, and how they relate.
A **PersistentVolume** represents an actual piece of storage in the cluster (provisioned by an admin or dynamically), independent of any Pod's lifecycle. A **PersistentVolumeClaim** is a request for storage made by a user/Pod (e.g., "I need 10Gi, ReadWriteOnce") — Kubernetes binds it to a matching available PV. A **StorageClass** defines a "class" of storage (e.g., "fast-ssd," "standard-hdd") with a specific provisioner and parameters, enabling *dynamic* provisioning — instead of an admin manually pre-creating PVs, a PVC referencing a StorageClass automatically triggers on-demand creation of a matching PV. Together: StorageClass (how to provision) → PV (the actual provisioned storage) → PVC (a Pod's request for and binding to that storage).

### 4. What are PVC access modes, and what do ReadWriteOnce, ReadOnlyMany, and ReadWriteMany mean?
**ReadWriteOnce (RWO)** — the volume can be mounted as read-write by a single node at a time (most block-storage-backed volumes, like AWS EBS/GCP Persistent Disk, only support this). **ReadOnlyMany (ROX)** — can be mounted read-only by many nodes simultaneously. **ReadWriteMany (RWX)** — can be mounted read-write by many nodes simultaneously (requires a storage backend that supports concurrent multi-node writes, like NFS, EFS, or a distributed filesystem — not typically supported by simple block storage). Choosing the wrong access mode for your storage backend/workload (e.g., expecting RWX from EBS) is a common source of Pod scheduling/mounting failures, since a Pod needing RWX can't be scheduled if the bound PV only supports RWO and is already mounted read-write elsewhere.

### 5. What is CSI (Container Storage Interface), and why was it introduced?
CSI is a standard interface allowing storage vendors to write drivers that work with Kubernetes (and other container orchestrators) without their code needing to live *in-tree* (built directly into Kubernetes' own codebase). Before CSI, adding support for a new storage backend required changes to Kubernetes core itself, tightly coupling storage-vendor release cycles to Kubernetes' own release cycle. CSI decouples this — vendors ship and version their own CSI driver independently, and Kubernetes only needs to know how to talk to any CSI-compliant driver generically, dramatically simplifying how new storage systems get supported.

### 6. What is an ephemeral volume, and when would you use one instead of a PersistentVolume?
An ephemeral volume's lifecycle is tied directly to its Pod — created when the Pod starts and destroyed when the Pod is removed, with no independent existence or ability to be reused by a different Pod (unlike a PV, which persists independently). Use cases: scratch space for temporary computation, a cache that doesn't need to survive a Pod restart, or injecting configuration/secrets as a volume (which are technically a form of ephemeral volume) — anywhere persistence beyond the Pod's own lifetime isn't actually needed, avoiding the overhead/complexity of provisioning and cleaning up real persistent storage for data that's fine to lose.

### 7. What is a ResourceQuota, and how does it differ from a Pod's own resource requests/limits?
A ResourceQuota is a namespace-level constraint capping the *total* aggregate resource consumption (CPU, memory, object counts like number of Pods/Services) across all workloads within that namespace — used by cluster administrators to prevent one team/namespace from consuming disproportionate shared cluster resources. This is distinct from a Pod's own `resources.requests`/`resources.limits` (which cap what one individual Pod can use) — a ResourceQuota effectively requires every Pod in its namespace to *have* requests/limits defined at all (since it needs something to sum against the quota), and will reject new Pod creation if it would exceed the namespace's total quota even if individual Pods each look reasonably sized.

### 8. What is CoreDNS, and what role does it play in Kubernetes networking?
CoreDNS is the default in-cluster DNS server that provides service discovery — resolving a Service's name (e.g., `my-service.my-namespace.svc.cluster.local`) to its ClusterIP, so Pods can reach other Services by a stable name rather than needing to know/track ever-changing IPs directly. It runs as a Deployment inside the cluster itself (typically in `kube-system`), watches the API server for Service/Endpoint changes, and updates its DNS records accordingly — if CoreDNS is unhealthy or misconfigured, Pods typically can still reach each other by IP, but any code relying on service-name-based discovery (the overwhelming majority of real applications) will fail to resolve names, a common and sometimes confusing root cause during cluster-networking incidents.

### 9. What are Cordon, Drain, and Uncordon, and when would you use each?
`kubectl cordon <node>` marks a node as unschedulable — no *new* Pods will be placed on it, but existing Pods keep running there undisturbed. `kubectl drain <node>` cordons the node AND evicts its existing Pods (respecting PodDisruptionBudgets), letting their controllers reschedule replacements elsewhere — used before taking a node down for maintenance/decommissioning. `kubectl uncordon <node>` reverses cordon, making the node schedulable again — used after maintenance completes to bring the node back into rotation. The typical maintenance sequence is: drain (empties the node safely) → perform maintenance → uncordon (node accepts new work again).

### 10. What does it mean for a Pod to be "Evicted," and what commonly causes it?
Eviction is Kubernetes proactively terminating a Pod (distinct from a crash or a normal deletion) usually due to node-level resource pressure — the kubelet detects the node is running low on a resource (memory, disk, PIDs) and evicts lower-priority/BestEffort-QoS Pods first (see the QoS classes discussion in the main Kubernetes file) to reclaim resources and protect node stability, rather than letting the whole node become unresponsive. `kubectl describe pod` on an evicted Pod shows the specific reason (e.g., `The node was low on resource: memory`) — a recurring pattern of evictions on a node points to genuine capacity planning issues (see the AWS/scaling files) rather than a one-off blip.

### 11. What is an ExternalName Service, and how does it differ from other Service types?
Unlike ClusterIP/NodePort/LoadBalancer (which all route traffic to Pods matched by a label selector), an ExternalName Service does no proxying at all — it's purely a DNS-level CNAME record mapping an in-cluster service name to an external DNS name (e.g., mapping `legacy-db.default.svc.cluster.local` to `legacy-db.mycompany.com`). It's used to let in-cluster applications refer to an external dependency (a database not yet migrated into the cluster, a third-party API) via the same consistent in-cluster service-naming convention they'd use for any other service, making a later migration (swapping the ExternalName for a real in-cluster Service) transparent to consuming application code.

### 12. How do you check node resource utilization in a cluster, and why might `kubectl top node` not be available?
`kubectl top node` (and `kubectl top pod`) show current CPU/memory usage, but require the Metrics Server to be installed and running in the cluster — it's not a built-in API server feature. If `kubectl top` returns an error, check whether Metrics Server is deployed (`kubectl get pods -n kube-system | grep metrics-server`) — this is a very common "gotcha" on freshly-created or minimal/local clusters (kind, minikube without the metrics-server addon enabled) that trips people up expecting `top` to work out of the box the way it does on managed cloud Kubernetes offerings that install it by default.

### 13. Explain the difference between `Role`/`RoleBinding` and `ClusterRole`/`ClusterRoleBinding` with a concrete scenario.
(See also the RBAC question in the main Kubernetes file.) Concrete scenario: you want a CI service account to be able to deploy only within the `staging` namespace — create a `Role` in the `staging` namespace granting the needed verbs on Deployments/Services, and a `RoleBinding` in that same namespace binding it to the service account; that identity has zero permissions in any other namespace. Contrast: a monitoring agent that needs to read Pod metrics across *every* namespace in the cluster needs a `ClusterRole` (defining the read permissions) bound via a `ClusterRoleBinding` (applying cluster-wide) — a `RoleBinding` referencing a `ClusterRole` is also a valid, common pattern: it grants that ClusterRole's permissions, but scoped to just the one namespace the RoleBinding lives in, useful for reusing a common permission-set definition across many namespaces without redefining the Role in each one.

### 14. What is the difference between a Kubernetes "container pattern" question interviewers ask about — init containers vs. sidecar containers — in terms of when they run?
Init containers run to completion, in sequence, *before* any of the Pod's main containers start — used for setup/prerequisite work (waiting for a dependency to be ready, running a one-time database migration, populating a shared volume with initial data) that must finish before the app starts. Sidecar containers run *alongside* the main container for the Pod's entire lifetime, concurrently (not sequentially, and not blocking startup) — used for ongoing supporting functionality (log shipping, a service mesh proxy) rather than one-time setup. A common mistake is trying to use an init container for something that needs to run continuously (it will simply exit and not restart, since init containers are expected to complete) — the pattern choice depends entirely on whether the helper task is a one-time prerequisite or an ongoing concern.

### 15. How would you find detailed information about why a specific Pod is behaving unexpectedly, beyond just `kubectl get pods`?
`kubectl describe pod <name>` — shows the Pod's full spec, current status, container statuses (including restart counts and last termination reason), resource requests/limits, and — critically — the Events section at the bottom, which is almost always the fastest path to a root cause (scheduling failures, probe failures, image pull errors, volume mount failures) since it's a chronological log of everything the control plane and kubelet did/attempted for that specific Pod, in plain language (see the scenario-troubleshooting file's dedicated `CrashLoopBackOff`/`Pending`/`ImagePullBackOff` questions for how to interpret specific Event messages).
