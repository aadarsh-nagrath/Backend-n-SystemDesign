# Monitoring, Logging & Observability — DevOps Interview Questions

---

### 1. What's the difference between monitoring and observability?
Monitoring tells you *whether* a system is healthy against predefined checks/dashboards you thought to set up in advance (known-unknowns — "is CPU high," "is the error rate up"). Observability is the broader property of being able to ask *new* questions about a system's internal state from its external outputs (logs/metrics/traces) *without shipping new code* to answer them — letting you debug unanticipated failure modes (unknown-unknowns) by exploring high-cardinality, richly-tagged telemetry rather than only checking pre-built dashboards.

### 2. Explain the three pillars of observability: metrics, logs, and traces.
**Metrics** — numeric, aggregated time-series data (request rate, error count, latency percentiles) — cheap to store/query at scale, great for dashboards/alerting/trends, but low-cardinality/detail (you lose the "which specific request" context). **Logs** — discrete, timestamped, often unstructured or semi-structured event records — rich detail per event, but expensive to store/search at high volume and harder to aggregate meaningfully across many instances. **Traces** — represent the path of a single request as it flows through multiple services, broken into spans, revealing exactly where time is spent across a distributed call chain — essential for debugging latency in microservices architectures where a single log line or metric can't show the whole request's journey.

### 3. What is a distributed trace, and what is a "span"?
A distributed trace represents one logical request/transaction's full journey across multiple services. It's composed of "spans," each representing one unit of work (e.g., one service's handling of the request, or one specific DB query within it), with a start/end time and metadata (tags, logs), linked together in a parent-child hierarchy via a shared trace ID that's propagated (usually via HTTP headers, e.g. W3C Trace Context) across every service call in the chain — letting you visualize the entire request as a single waterfall/flamegraph showing exactly which downstream call was slow.

### 4. Explain the RED method and the USE method for choosing what to monitor.
**RED** (for request-driven services): Rate (requests per second), Errors (failed requests per second), Duration (latency distribution, typically percentiles) — a compact, practical starting set of metrics for any service handling requests. **USE** (for resources — CPU, memory, disk, network): Utilization (% time the resource was busy), Saturation (how much extra work is queued waiting for the resource), Errors (count of error events for that resource) — a systematic checklist for diagnosing infrastructure/resource-level bottlenecks.

### 5. What are Google SRE's "Four Golden Signals"?
Latency (time to service a request — distinguishing successful vs. failed request latency, since failures often return fast and can mask a slow-but-successful-request problem if averaged together), Traffic (demand on the system, e.g. requests/sec), Errors (rate of failed requests), Saturation (how "full" the system is — how close to its capacity limits, often the best leading indicator before things actually break). Together they form a minimal, broadly applicable set of things worth alerting on for almost any service.

### 6. Why should alerts be based on percentiles (p95/p99) rather than averages?
An average can hide serious problems: if 95% of requests are fast (10ms) and 5% are catastrophically slow (10 seconds), the average might look acceptable (~510ms) while a meaningful fraction of real users have a terrible experience. Percentiles (p95, p99) directly answer "what's the experience of the worst-affected X% of requests," which is what users and SLOs actually care about — a single slow outlier user matters even if it doesn't move the average.

### 7. What is an SLI, SLO, and SLA, and how do they relate?
**SLI** (Service Level Indicator) — an actual measured metric of behavior (e.g., "% of requests served in under 200ms," "% of successful requests"). **SLO** (Service Level Objective) — an internal target for that SLI over a time window (e.g., "99.9% of requests succeed within 200ms, measured over 30 days") — the goal a team designs and operates the system to meet. **SLA** (Service Level Agreement) — an external, often contractual commitment to customers, usually a looser/more conservative version of the SLO with defined consequences (credits/penalties) if breached — you set SLOs stricter than your SLA so you have room to notice and fix a problem internally before it ever breaches the customer-facing contractual commitment.

### 8. What is an error budget, and how does it change how a team makes tradeoffs?
If your SLO is 99.9% availability, your error budget is the remaining 0.1% — the amount of "acceptable failure" you're allowed before breaching the objective. As long as budget remains, the team can take calculated risks (ship faster, deploy more frequently, take planned maintenance) since some failure is expected and budgeted for; once the budget is exhausted (too many incidents/errors in the window), the team shifts focus to reliability work and slows down risky changes until the budget recovers — replacing subjective "should we be more careful?" debates with an objective, pre-agreed threshold.

### 9. Explain the difference between white-box and black-box monitoring.
White-box monitoring instruments the system internally (metrics/logs emitted by the application itself, exposing internal state like queue depth, cache hit rate, or specific business logic outcomes). Black-box monitoring observes the system from the outside, exactly as a user/client would (synthetic HTTP checks, uptime pings) — it can catch issues invisible to internal instrumentation (a DNS misconfiguration, a broken load balancer, a certificate expiring) precisely because it doesn't assume anything about internals, but it can't tell you *why* something is failing the way rich white-box telemetry can.

### 10. What is cardinality in the context of metrics systems (e.g., Prometheus), and why does high cardinality cause problems?
Cardinality is the number of unique label/tag combinations a metric can take (e.g., a metric labeled by `user_id` could have millions of unique series). Time-series databases store and index each unique label combination as a separate series — extremely high-cardinality labels (raw user IDs, full URLs with query params, request IDs) can explode memory usage and query performance, sometimes to the point of taking down the monitoring system itself ("cardinality explosion") — a very common real-world Prometheus operational incident, mitigated by avoiding unbounded-cardinality labels on metrics (put that detail in logs/traces instead, which are built for high-cardinality data).

### 11. Explain how Prometheus's pull model works, and contrast it with a push-based system (e.g., StatsD).
Prometheus periodically *scrapes* (HTTP GET) a `/metrics` endpoint that each monitored target exposes, on a configured interval — the monitoring system controls timing/frequency centrally, and a target simply needs to be reachable and expose current-state metrics when asked (no need for the target to know where to send data or handle backpressure). Push-based systems (StatsD, and Prometheus's own Pushgateway for exceptions) have the application actively send metric updates to a collector — necessary for short-lived jobs that won't exist long enough to be scraped (e.g., a batch job), but requires the collector to handle inbound load from potentially many simultaneous pushers and makes "is this target even alive" harder to infer (a target that stops pushing looks the same as one with genuinely nothing new to report).

### 12. What is a PromQL example for "the 99th percentile request latency over the last 5 minutes," and what does `rate()` do generally?
`histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))`. `rate()` calculates the per-second average rate of increase of a counter over a time window — necessary because raw counters only ever increase (and reset on restart), so you can't meaningfully graph or alert on their raw value; `rate()` converts that into a meaningful "how fast is this happening right now" number, correctly handling counter resets.

### 13. What's the difference between a counter, a gauge, and a histogram (metric types)?
**Counter** — a cumulative value that only increases (or resets to zero on restart) — e.g., total requests served. **Gauge** — a value that can go up or down arbitrarily — e.g., current memory usage, number of active connections. **Histogram** — samples observations (like request durations) into configurable buckets, letting you compute percentiles/distributions after the fact server-side (via `histogram_quantile`), at the cost of some accuracy from bucketing — an alternative, "Summary," computes quantiles client-side at collection time (more accurate but can't be aggregated across instances the way histogram buckets can).

### 14. Explain structured logging and why it's preferred over plain-text log lines in production systems.
Structured logging emits logs as machine-parseable key-value data (typically JSON) — `{"level":"error","msg":"payment failed","user_id":123,"order_id":456,"latency_ms":340}` — rather than a free-text sentence. This lets log aggregation systems (ELK, Loki, Datadog) index and query on specific fields precisely and cheaply ("show me all errors for user 123" or "p99 latency_ms grouped by endpoint") instead of relying on fragile regex parsing of inconsistent free-text formats, and it makes correlating logs with metrics/traces (via shared trace/request IDs as structured fields) far more reliable.

### 15. What is a correlation ID (or trace ID/request ID), and why must it be propagated across services?
A correlation ID is a unique identifier generated when a request first enters a system (e.g., at the edge/API gateway) and passed along (via a header, e.g. `X-Request-ID` or a full trace context) to every downstream service call that request triggers. Without it, in a microservices architecture, correlating log lines and understanding one user's request as it hops across a dozen services is nearly impossible — with it, you can query "show me every log line and span across every service for this one request" in seconds, which is often the fastest way to diagnose a specific user's reported issue.

### 16. What's the difference between the ELK/EFK stack and a service like Loki, in terms of indexing approach?
ELK/EFK (Elasticsearch + Logstash/Fluentd + Kibana) fully indexes the *content* of every log line (full-text search on any field/word) — powerful querying, but expensive to store and index at scale. Loki (paired with Grafana) only indexes metadata/labels (like Prometheus does for metrics) and stores log content compressed, unindexed — queries filter first by labels (cheap) then grep through the matching, much smaller set of raw log content — dramatically cheaper at scale, at the cost of not being able to efficiently do an ad-hoc full-text search across labels you didn't think to index in advance.

### 17. What's the difference between alerting on a symptom vs. a cause, and why do SRE practices favor symptom-based alerting?
Cause-based alerting fires on internal conditions that *might* lead to a problem (e.g., "CPU > 80%," "queue depth > 1000") — often noisy, since many such conditions are transient or don't actually impact users, leading to alert fatigue. Symptom-based alerting fires on user-visible impact (e.g., "error rate > 1%," "p99 latency > SLO threshold") — every symptom-based alert represents something that actually matters to a user, and cause-based signals are then used as supporting context/dashboards *during* investigation of a symptom-based page, rather than as the primary trigger for waking someone up.

### 18. What is alert fatigue, and how do you design alerting to avoid it?
Alert fatigue is when responders receive so many low-value/non-actionable alerts that they start ignoring or delaying response to all alerts, including real ones — a serious reliability risk in itself. Mitigations: alert only on symptoms that require *human action* (if nothing needs to be done, it shouldn't page — route it to a dashboard/ticket instead), tune thresholds against real historical noise, require sustained breach over a window rather than firing on single-sample spikes, deduplicate/group related alerts (one page for "the whole service is down," not fifty pages for fifty failing instances), and regularly review/prune alerts that fire often but rarely lead to real action.

### 19. What is a runbook, and what should a good one contain?
A runbook is a documented, step-by-step procedure for responding to a specific known alert/incident type, usually linked directly from the alert itself. A good runbook contains: what the alert means and its likely causes/context, exact diagnostic commands/dashboards to check first, concrete mitigation steps (in priority order, e.g., "if X, do Y" branches), who to escalate to and when, and links to related past incidents/postmortems — the goal is that even an on-call engineer unfamiliar with that specific service can follow it to a safe mitigation without needing to page a specialist immediately.

### 20. Explain what a "flamegraph" is and what it's used for.
A flamegraph visualizes stack traces collected via profiling (or distributed tracing spans) as stacked, width-proportional-to-time horizontal bars — each bar is a function call (or a trace span), stacked bars beneath show what it called, and width shows how much total time was spent in it (including children). It's the standard way to visually spot performance hotspots at a glance (the widest bars are where the most time is spent) in CPU profiling or in understanding which part of a distributed request's trace dominates its total latency.

### 21. How would you set up monitoring and alerting for a brand-new microservice from scratch?
Instrument the RED metrics (request rate, error rate, latency histogram) at minimum, exposed for scraping (Prometheus client library) or pushed to your metrics backend. Emit structured logs with a propagated correlation/trace ID, shipped to the central logging system. Add distributed tracing instrumentation (via an OpenTelemetry SDK, typically auto-instrumented for common frameworks) so it participates in existing traces rather than being a black hole in them. Define SLOs based on the RED metrics and set up symptom-based alerts on SLO burn rate (not just static thresholds). Add a dashboard covering the golden signals plus any service-specific critical metrics (e.g., queue depth for a worker service), and write a basic runbook for the most likely failure modes before it goes to production, not after the first incident.

### 22. What is OpenTelemetry, and what problem does it solve?
OpenTelemetry (OTel) is a vendor-neutral, open-source standard (APIs, SDKs, and a collector) for generating and exporting metrics, logs, and traces from applications. Before it, each observability vendor (Datadog, New Relic, Jaeger, Zipkin) required its own proprietary instrumentation libraries, locking application code into a specific backend and making it painful to switch vendors or aggregate telemetry across tools using different agents. OTel decouples instrumentation from the backend — instrument once, and export to any OTel-compatible backend (or several simultaneously), and switch/add backends later without re-instrumenting application code.
