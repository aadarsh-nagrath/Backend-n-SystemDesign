# Networking, DNS & HTTP — DevOps Interview Questions

---

### 1. Explain the OSI model layers and give a protocol example for each.
1. Physical (bits on wire/fiber/radio) — Ethernet cabling, Wi-Fi radio. 2. Data Link (framing, MAC addressing, switching) — Ethernet, ARP. 3. Network (logical addressing, routing) — IP, ICMP. 4. Transport (end-to-end delivery, ports) — TCP, UDP. 5. Session (establishing/managing sessions) — often folded into TCP/TLS in practice. 6. Presentation (encoding/encryption) — TLS, character encoding. 7. Application — HTTP, DNS, SSH, SMTP. In practice, most day-to-day debugging happens at layers 3/4 (routing, ports, firewalls) and 7 (HTTP behavior).

### 2. What happens, step by step, when you type a URL into a browser and hit enter?
1) Browser checks its cache, then OS cache, for a DNS record; if absent, queries the resolver (recursive → root → TLD → authoritative nameservers) to get an IP. 2) Browser opens a TCP connection to that IP on port 443 (three-way handshake). 3) TLS handshake negotiates encryption (cert validation, key exchange — TLS 1.3 does this in one round trip). 4) Browser sends an HTTP request; server processes it (routing, app logic, DB queries) and returns a response. 5) Browser parses HTML, discovers additional resources (CSS/JS/images), fetches them (often in parallel over the same connection via HTTP/2 multiplexing), and renders the page.

### 3. Explain DNS record types: A, AAAA, CNAME, MX, TXT, NS, SOA, PTR.
**A** — hostname to IPv4 address. **AAAA** — hostname to IPv6 address. **CNAME** — alias, hostname points to another hostname (cannot coexist with other records at the same name, notably not at a zone apex/root domain on strict resolvers). **MX** — mail exchange server(s) with priority. **TXT** — arbitrary text, used for domain verification, SPF/DKIM/DMARC email authentication. **NS** — delegates a zone to specific nameservers. **SOA** — start of authority: zone's primary nameserver, admin contact, serial number, and refresh/retry/expire/TTL timings for zone transfers. **PTR** — reverse DNS, IP to hostname.

### 4. What is a CNAME flattening / ALIAS record, and why is it needed?
DNS rules forbid a CNAME at the zone apex (e.g. `example.com`, as opposed to `www.example.com`) because the apex must also hold NS/SOA/MX records, and a name can't have a CNAME alongside other record types. "CNAME flattening" (or an ALIAS/ANAME record, a vendor-specific extension) lets a provider resolve the target on the DNS server side and serve an A/AAAA record for the apex, so you can point your bare domain at, e.g., a load balancer or CDN that only publishes a hostname.

### 5. Explain DNS TTL and how it affects deployments/rollbacks.
TTL (time to live) tells resolvers how long to cache a record before re-querying. Low TTLs (e.g. 60s) allow fast propagation of changes (useful before a planned DNS cutover, like a blue/green switch or disaster-recovery failover) at the cost of more DNS query load; high TTLs reduce load/latency but mean a bad record change takes longer to fully propagate — and some resolvers/ISPs ignore very low TTLs and cache longer anyway, so DNS should never be the *only* mechanism you rely on for an urgent rollback.

### 6. What's the difference between recursive and authoritative DNS servers?
A recursive resolver (e.g. your ISP's resolver, or public ones like 8.8.8.8/1.1.1.1) does the work of walking the DNS hierarchy on behalf of the client and caches results. An authoritative server holds the actual source-of-truth records for a zone and answers queries about it directly — it doesn't perform recursive lookups for other zones.

### 7. Explain the difference between HTTP/1.1, HTTP/2, and HTTP/3.
HTTP/1.1: text-based, one request per TCP connection at a time without pipelining issues (head-of-line blocking), mitigated in practice by opening multiple parallel connections. HTTP/2: binary framing, true multiplexing of many requests over a single TCP connection, header compression (HPACK), server push — but still suffers TCP-level head-of-line blocking (one lost packet stalls all streams on that connection). HTTP/3: runs over QUIC (built on UDP) instead of TCP, so each stream is independently ordered and a lost packet only stalls its own stream; also folds in TLS 1.3 and reduces connection-establishment round trips, especially valuable on lossy/mobile networks.

### 8. Explain the meaning of key HTTP status codes: 200, 201, 204, 301 vs 302, 304, 400, 401 vs 403, 404, 409, 429, 500, 502, 503, 504.
200 OK; 201 Created; 204 No Content (success, no body). 301 Moved Permanently (cache the redirect, update bookmarks/SEO) vs 302 Found (temporary, don't cache). 304 Not Modified (conditional GET, use cached copy). 400 Bad Request (malformed request); 401 Unauthorized (not authenticated) vs 403 Forbidden (authenticated but not allowed); 404 Not Found; 409 Conflict (e.g. version/state conflict); 429 Too Many Requests (rate limited). 500 Internal Server Error (unhandled app failure); 502 Bad Gateway (upstream/proxy got an invalid response from the backend); 503 Service Unavailable (server overloaded/down for maintenance, often with `Retry-After`); 504 Gateway Timeout (upstream took too long to respond).

### 9. A user reports 502s. How do you narrow down where the problem is?
502 means the reverse proxy/load balancer (nginx, ALB, etc.) got an invalid/no response from the upstream. Check: is the backend process actually running and listening (`ss -tulnp`)? Are health checks passing? Check proxy logs for the specific upstream error (connection refused vs. reset vs. malformed response — nginx logs the `upstream` address and error). Check backend application logs/crash logs for the same timestamp — a common cause is the backend crashing or restarting (OOM kill, unhandled exception) exactly when the request came in. Also check timeouts: if the backend closes idle keep-alive connections faster than the proxy expects, the proxy can get connection-reset errors that surface as 502s.

### 10. Difference between 502, 503, and 504 in terms of root cause.
502 — proxy reached the upstream but got a broken/invalid response (upstream crashed mid-request, wrong protocol, connection reset). 503 — the server itself (or the proxy, if it has no healthy upstreams) is deliberately signaling it can't handle the request right now (overloaded, maintenance mode, no backend passed health checks). 504 — the proxy successfully connected to upstream but the upstream never responded within the timeout (slow query, deadlock, downstream dependency hanging).

### 11. What is a load balancer, and what's the difference between L4 and L7 load balancing?
A load balancer distributes incoming traffic across multiple backend instances for scalability and availability. L4 (transport layer) balances based on IP/port/TCP-UDP info without inspecting application content — fast, protocol-agnostic, but can't route based on URL path or headers. L7 (application layer) understands HTTP — can route based on path/host/headers/cookies, do content-based routing, TLS termination, and richer health checks, at the cost of more CPU overhead and being HTTP-specific.

### 12. Explain common load balancing algorithms.
Round robin (cycle through backends evenly); weighted round robin (some backends get more traffic, e.g. by capacity); least connections (send to the backend with fewest active connections — good for long-lived/variable-duration requests); IP hash / consistent hashing (same client consistently routed to the same backend — useful for session affinity or cache locality); random with two choices (pick 2 backends at random, send to the less loaded — a good balance of simplicity and even load, popular in modern systems).

### 13. What is a health check, and what's the difference between a liveness and a readiness check (as in Kubernetes)?
A health check is an endpoint/mechanism a load balancer or orchestrator polls to decide if an instance should receive traffic. **Liveness** answers "is this process still functioning, or should it be restarted" (e.g., deadlocked event loop) — failing it triggers a restart. **Readiness** answers "is this instance currently able to serve traffic" (e.g., still warming up a cache, or a downstream dependency is down) — failing it just removes the instance from the load-balancing pool without restarting it. Conflating the two is a common cause of restart-loop incidents: a service that's merely *busy* (not broken) shouldn't fail its liveness check.

### 14. Explain what a CDN does and why it improves performance.
A CDN (Content Delivery Network) caches content at edge locations geographically close to users, reducing latency (shorter round trip) and origin load (fewer requests hit your servers directly). It also absorbs traffic spikes and some classes of DDoS attacks, and can serve static assets even during origin outages (stale-while-revalidate style). Cache invalidation/purging and correct `Cache-Control` headers are the operational complexity that comes with it.

### 15. Explain `Cache-Control` directives: `no-cache`, `no-store`, `max-age`, `private`/`public`, `stale-while-revalidate`.
`no-store` — never cache at all, anywhere. `no-cache` — can be cached, but must revalidate with the origin (via ETag/Last-Modified) before using the cached copy, even if not expired. `max-age=N` — cacheable for N seconds without revalidation. `public`/`private` — whether shared caches (CDNs/proxies) may store it, vs. only the end-user's browser. `stale-while-revalidate=N` — serve the stale cached response immediately while asynchronously refetching in the background, hiding latency from the user.

### 16. What is TLS, and briefly explain a TLS 1.3 handshake.
TLS (Transport Layer Security) provides encryption, integrity, and authentication for data in transit over TCP. In TLS 1.3: client sends supported cipher suites and a key share (`ClientHello`); server responds with its chosen cipher, its own key share, and its certificate, and both sides derive session keys — completing the handshake in one round trip (vs. two in TLS 1.2), reducing latency, especially noticeable on mobile/high-latency links. Session resumption (0-RTT) can skip even that round trip for repeat connections, though 0-RTT data has replay-attack caveats.

### 17. What is mTLS (mutual TLS) and where is it used?
In normal TLS, only the server presents a certificate and the client verifies it. In mTLS, the client *also* presents a certificate that the server verifies — both sides authenticate each other cryptographically. Common in service-to-service communication inside a service mesh (Istio, Linkerd), zero-trust architectures, and B2B API integrations, replacing or supplementing API keys with strong, revocable, certificate-based identity.

### 18. What is a reverse proxy vs. a forward proxy?
A forward proxy sits in front of clients, making requests on their behalf to the internet (hides the client from the server; used for content filtering, caching, or anonymization). A reverse proxy sits in front of servers, receiving requests from clients "as if" it were the server (hides backend topology, does TLS termination, load balancing, caching, WAF). Nginx and HAProxy are commonly used as reverse proxies; Squid is a classic forward proxy example.

### 19. Explain what NAT is and why most home/cloud private networks use it.
Network Address Translation rewrites private IP addresses (RFC 1918 ranges like 10.0.0.0/8, 192.168.0.0/16) to a shared public IP as traffic leaves the network, and reverses the mapping for return traffic — this conserves scarce public IPv4 addresses and hides internal topology. In cloud VPCs, a NAT gateway lets instances in private subnets reach the internet outbound (e.g., for package downloads) without being directly reachable from the internet inbound.

### 20. What is a subnet, and how do you calculate the number of usable hosts from a CIDR block?
A subnet is a logical subdivision of an IP network. CIDR notation `/n` specifies how many bits are the network prefix; the remaining `32-n` bits (IPv4) address hosts. Usable hosts = 2^(32-n) − 2 (subtracting network and broadcast addresses) for traditional subnets — e.g. a `/24` has 2^8 − 2 = 254 usable hosts. Cloud VPC subnets typically also reserve a few extra addresses (AWS reserves 5 per subnet) for internal networking purposes.

### 21. Explain what a firewall/security group does, and stateful vs. stateless filtering.
A firewall filters traffic based on rules (source/destination IP, port, protocol). Stateful firewalls (e.g. AWS Security Groups, iptables conntrack) track connection state, so you only need an inbound rule — the corresponding outbound *reply* traffic is automatically allowed. Stateless filters (e.g. AWS Network ACLs) evaluate each packet independently, so you must explicitly allow both directions (inbound rule for the request, outbound rule for the ephemeral-port response), which is a common source of "why can't my instance respond" bugs.

### 22. What is BGP and why does it matter for large-scale internet routing/outages?
BGP (Border Gateway Protocol) is the protocol autonomous systems (ASes — ISPs, cloud providers, large companies) use to exchange routing information about which IP prefixes are reachable through them, forming the internet's global routing table. Misconfigured BGP announcements ("route leaks" or hijacks) — accidentally or maliciously announcing routes for IP space you don't own — can redirect or blackhole traffic for large swaths of the internet, and have caused several major real-world outages.

### 23. What's the difference between a proxy ARP, ARP, and MAC address, at a practical level?
ARP (Address Resolution Protocol) resolves an IP address to a MAC address within a local network segment (needed because Ethernet frames are addressed by MAC, not IP). A MAC address is the hardware address burned into (or virtually assigned to) a network interface. This matters practically in virtualized/cloud networking (overlay networks, VXLAN) where ARP resolution and MAC learning determine whether packets can reach a newly created VM/pod on the same subnet.

### 24. How would you debug intermittent packet loss between two servers?
`mtr host` (combines ping + traceroute, shows loss % per hop over time — a loss appearing consistently at one hop but not subsequent ones is often that router being deprioritized for ICMP, not real loss; loss that *persists* through to later hops is real). `ping -i 0.2 -c 1000 host | grep -c "bytes from"` for a raw loss percentage. Check both ends' NIC error counters (`ethtool -S`, `ip -s link`) for CRC errors/drops. Check for MTU mismatches causing fragmentation issues (`ping -M do -s 1472 host` to test without fragmentation). Check if it correlates with load (bandwidth saturation) or specific times (scheduled jobs, backups).

### 25. What is a WebSocket, and how does it differ from long-polling and Server-Sent Events (SSE)?
WebSocket upgrades an HTTP connection (via the `Upgrade: websocket` header) into a persistent, full-duplex TCP-like channel — both client and server can push messages at any time with low overhead per message, ideal for chat, live collaboration, gaming. Long-polling is a workaround using plain HTTP: the client holds a request open until the server has data (or a timeout), then immediately reopens another — simpler infrastructure requirements but higher overhead/latency. SSE is server-to-client only, over a single long-lived HTTP connection, with automatic reconnection built into the browser API — simpler than WebSockets when you only need server push (e.g., live notifications, streaming logs) and don't need the client to send messages on the same channel.

### 26. Explain rate limiting algorithms: token bucket, leaky bucket, fixed window, sliding window.
**Token bucket** — tokens are added at a fixed rate up to a cap; each request consumes a token; allows short bursts up to the bucket size while enforcing a long-term average rate. **Leaky bucket** — requests queue and are processed at a fixed rate, smoothing bursts into a steady output rate (no burst allowance). **Fixed window** — count requests per fixed time window (e.g. per minute); simple but allows up to 2x the limit right at a window boundary (burst at the end of one window + burst at the start of the next). **Sliding window** (log or counter-based) — considers a rolling time window, giving smoother, more accurate limiting without the boundary-burst problem, at the cost of more memory/computation.

### 27. What is DNS-based service discovery vs. a service registry (like Consul/etcd)?
DNS-based discovery (e.g. Kubernetes' internal DNS, `SRV` records) resolves a service name to instance IP(s), often integrated with health checks so unhealthy instances are removed from the response — simple and universally supported by any client that can do a DNS lookup. A dedicated service registry (Consul, etcd, Zookeeper) offers richer metadata, real-time push-based updates (vs. DNS's TTL-based caching lag), health-check integration, and key-value storage for configuration — commonly paired with a service mesh or client-side load-balancing library.

### 28. Explain what an Anycast IP is and why it's used for DNS/CDNs.
Anycast advertises the *same* IP address from multiple physical locations via BGP; routers naturally direct a client's traffic to the topologically/BGP-nearest location announcing that IP. This is how public DNS resolvers (8.8.8.8, 1.1.1.1) and CDN edge networks achieve low latency globally with a single IP, and it also provides built-in DDoS resilience (attack traffic is spread across many points of presence instead of concentrating on one).

### 29. What is the difference between IPv4 and IPv6, and why hasn't IPv6 fully replaced IPv4?
IPv4 uses 32-bit addresses (~4.3 billion, exhausted); IPv6 uses 128-bit addresses (effectively unlimited), simplifies header processing, and has built-in support for features NAT made unnecessary-but-common workarounds for. Adoption has been slow due to backward-incompatibility (needs dual-stack or translation to talk to IPv4-only hosts), the fact that NAT successfully papered over IPv4 exhaustion for decades, and the operational cost/complexity of migrating existing infrastructure, tooling, and security policies.

### 30. How would you troubleshoot high latency (not downtime) reported by users in a specific region?
Check CDN/edge presence in that region and cache hit ratio there. Run synthetic checks (or ask users to run `mtr`/traceroute) from that region to identify where latency is introduced — an inefficient network path, a distant origin server, or an intermediate ISP peering issue. Check whether DNS is resolving to the geographically nearest endpoint (GeoDNS/latency-based routing misconfiguration is a common cause). Check application-level latency from that region's traffic specifically (it might be a downstream dependency — e.g. a database in a different region than that user's traffic is routed to — rather than network transport at all).

### 31. Explain `curl -v` output at a high level and what you'd look for when debugging an API call.
`curl -v` shows the full request lifecycle: DNS resolution and connection details (`* Trying <ip>...`), the TCP/TLS handshake (cert chain, negotiated TLS version/cipher — useful for diagnosing TLS version mismatches or expired certs), the exact request line and headers sent (`>`), and the response status line and headers received (`<`). Look for: unexpected redirects, wrong `Content-Type`, missing/incorrect auth headers actually being sent, TLS verification failures, and the timing breakdown (`curl -w` with `time_namelookup`/`time_connect`/`time_starttransfer` pinpoints whether delay is DNS, connect, TLS, or server processing).

### 32. What's the difference between an API Gateway and a plain reverse proxy/load balancer?
A reverse proxy/load balancer routes and balances traffic. An API Gateway does that plus API-specific concerns: authentication/authorization enforcement, rate limiting per client/key, request/response transformation, protocol translation (e.g. REST to gRPC), aggregating multiple backend calls into one client-facing response, and centralized API versioning/documentation — acting as a single, policy-enforcing front door for a set of backend services, especially in a microservices architecture.
