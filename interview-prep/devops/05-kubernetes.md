# Kubernetes — DevOps Interview Questions

---

### 1. Explain the core Kubernetes architecture: control plane vs. worker nodes.
**Control plane**: `kube-apiserver` (the front door — all components, including `kubectl`, talk only to it; validates/persists API objects), `etcd` (distributed key-value store, the cluster's single source of truth for all state), `kube-scheduler` (assigns newly created Pods to nodes based on resource requests, affinity rules, taints), `kube-controller-manager` (runs reconciliation control loops — Deployment, ReplicaSet, Node controllers, etc. — that continuously drive actual state toward desired state). **Worker nodes**: `kubelet` (agent that ensures containers described in PodSpecs assigned to its node are running and healthy), `kube-proxy` (implements Service networking rules, typically via iptables/IPVS), and the container runtime (containerd/CRI-O).

### 2. What is a Pod, and why is it the smallest deployable unit instead of a container?
A Pod is one or more containers that are always scheduled together on the same node, sharing a network namespace (same IP, can reach each other via `localhost`) and optionally storage volumes. It models the reality that some containers are tightly coupled and must co-locate — e.g., a main app container plus a sidecar (log shipper, service mesh proxy) that needs to share the app's network/filesystem. Most Pods run a single container, but the abstraction accommodates multi-container patterns without conflating "unit of scheduling/networking" with "unit of the application."

### 3. Explain the reconciliation/controller pattern that underlies Kubernetes.
Nearly everything in Kubernetes works via control loops: a controller continuously watches the *desired state* (what's declared in the API, e.g. "3 replicas of this Deployment") and the *actual observed state* (what's really running), and takes actions to reconcile any difference (create/delete Pods) — repeatedly, indefinitely, self-healing from any divergence (a node dying, a Pod crashing) without anyone intervening. This declarative, level-triggered (not edge-triggered) design is why Kubernetes is resilient to missed events or a controller restarting mid-reconciliation.

### 4. Difference between a Deployment, a ReplicaSet, and a StatefulSet.
A **ReplicaSet** ensures a specified number of identical Pod replicas are running at all times (low-level, rarely managed directly). A **Deployment** manages ReplicaSets on top of that, adding rolling updates, rollback history, and declarative version management (you rarely touch ReplicaSets directly — you edit the Deployment, and it creates a new ReplicaSet and scales the old one down). A **StatefulSet** is for stateful workloads needing stable, unique network identities (`pod-0`, `pod-1`, ...) and stable per-Pod persistent storage that survives rescheduling — Pods are created/scaled/deleted in strict order, unlike a Deployment's Pods which are interchangeable.

### 5. What is a DaemonSet, and when would you use one?
A DaemonSet ensures exactly one copy of a Pod runs on every (or a selected subset of) node in the cluster, automatically adding/removing Pods as nodes join/leave. Used for node-level infrastructure: log collectors (Fluent Bit), monitoring agents (node-exporter), network plugins (CNI daemons), or storage drivers — anything that needs to exist on every node rather than be scaled independently.

### 6. Explain a Kubernetes Service and the different `type`s.
A Service provides a stable virtual IP/DNS name that load-balances traffic to a dynamic set of Pods (selected by label selector), decoupling clients from ever-changing Pod IPs. **ClusterIP** (default) — reachable only within the cluster. **NodePort** — additionally exposes the service on a static port on every node's IP. **LoadBalancer** — provisions an external cloud load balancer (on supported cloud providers) pointing at the service. **ExternalName** — a DNS-level CNAME alias to an external name, no proxying involved.

### 7. How does a Service actually route traffic to the right Pods (kube-proxy)?
`kube-proxy` watches Services and Endpoints/EndpointSlices (the actual healthy Pod IPs currently matching a Service's selector) and programs the node's networking (iptables rules or IPVS virtual server entries) so that traffic to the Service's ClusterIP gets DNAT'd to one of the backing Pod IPs, typically round-robin or random. It's the mechanism that makes a Service's IP "virtual" — no single process is actually listening on it; the kernel rewrites the destination per packet/connection.

### 8. What is an Ingress, and how does it differ from a Service?
Ingress is an L7 (HTTP/HTTPS) routing configuration — host/path-based rules mapping external requests to backend Services, plus TLS termination — implemented by an Ingress Controller (nginx-ingress, Traefik, cloud-provider controllers) that actually watches Ingress objects and configures a real reverse proxy/load balancer accordingly. A Service alone (even `LoadBalancer` type) typically provisions one L4 load balancer per Service; Ingress lets many hostnames/paths share a single external entry point/load balancer, with more HTTP-aware routing capability.

### 9. Explain liveness, readiness, and startup probes.
**Liveness** — "is this container still healthy, or should it be restarted" (a failing liveness probe triggers a container restart). **Readiness** — "is this container currently ready to receive traffic" (a failing readiness probe removes the Pod from Service endpoints without restarting it). **Startup** — for slow-starting apps, delays liveness/readiness checks from running (and potentially killing a still-initializing container) until the startup probe itself succeeds — prevents a legitimately slow-starting app from being killed in a restart loop before it ever finishes booting.

### 10. What are resource `requests` and `limits`, and how do they affect scheduling and QoS?
`requests` is the amount of CPU/memory a Pod is guaranteed and what the scheduler uses to decide which node has room for it (bin-packing based on requests, not limits). `limits` caps the maximum a container can use — exceeding a memory limit gets the container OOM-killed; exceeding a CPU limit results in throttling, not killing. QoS classes derive from these: **Guaranteed** (requests == limits for all resources, all containers) gets the highest eviction priority protection; **Burstable** (requests set, limits higher or unset) is next; **BestEffort** (neither set) is evicted first under node pressure.

### 11. Why might a Pod be CPU-throttled even though the node has spare CPU capacity?
CPU limits are enforced per-container via cgroup CFS quota over fixed time slices (e.g., a 100ms period) regardless of whether other cores/processes on the node are idle — if a container bursts and consumes its entire quota for a period, it's throttled until the next period even if 90% of the node's other cores sit idle. This is a well-known Kubernetes gotcha, especially with multi-threaded runtimes (Go, Java) that can burst across many cores briefly; the practical mitigations are setting limits generously above realistic peak usage or, in some cases, not setting a CPU limit at all (only a request) and relying on the node's overall capacity/other controls instead.

### 12. What is a ConfigMap vs. a Secret, and how are they actually secured?
Both inject configuration into Pods (as environment variables or mounted files), decoupling config from the container image. A ConfigMap is for non-sensitive data; a Secret is intended for sensitive data (credentials, tokens, certs). Critically, out of the box a Secret is only base64-*encoded*, not encrypted, in `etcd` — anyone with `etcd` access or sufficient RBAC permissions to read Secrets can trivially decode it. Real protection requires enabling encryption-at-rest for `etcd` (`EncryptionConfiguration`), tight RBAC on `secrets` resources, and often an external secrets manager (Vault, AWS Secrets Manager via the External Secrets Operator) as the actual source of truth.

### 13. Explain Kubernetes namespaces and what they do/don't isolate.
Namespaces partition cluster objects into logically separate groups (useful for multi-team/multi-environment clusters, applying separate RBAC/quotas/network policies per namespace, and avoiding naming collisions). They do **not** provide node-level or kernel-level isolation (Pods in different namespaces can still land on the same node and, without a NetworkPolicy, can reach each other over the network by default) — namespaces are an API-level/organizational boundary, not a security boundary by themselves.

### 14. What is a NetworkPolicy, and what's true by default without one?
By default, Kubernetes networking is "flat" — any Pod can reach any other Pod across the entire cluster (subject to the CNI plugin supporting policy enforcement at all). A NetworkPolicy is a namespace-scoped, label-selector-based firewall rule restricting which Pods can talk to which, on which ports (ingress and/or egress) — but it only takes effect if the cluster's CNI plugin implements NetworkPolicy enforcement (not all do by default; e.g. plain `kubenet` doesn't, Calico/Cilium/Weave do). Without any NetworkPolicy at all selecting a Pod, that Pod remains fully open.

### 15. Explain how a rolling update works and how to control its behavior.
A Deployment's rolling update incrementally replaces old-ReplicaSet Pods with new-ReplicaSet Pods, controlled by `maxSurge` (how many extra Pods above the desired count can be created during the rollout) and `maxUnavailable` (how many Pods can be unavailable at once) — tuning these trades rollout speed against risk/capacity headroom. Combined with readiness probes, a new Pod only starts receiving traffic once it passes its readiness check, and the rollout only proceeds to replace more old Pods once enough new ones are Ready — so a broken new version that never becomes Ready will halt the rollout rather than take down the whole service.

### 16. How do you roll back a bad Deployment?
`kubectl rollout undo deployment/<name>` reverts to the previous ReplicaSet revision (Deployments keep a configurable history of prior ReplicaSets via `revisionHistoryLimit`); `kubectl rollout undo deployment/<name> --to-revision=N` targets a specific earlier revision. `kubectl rollout history deployment/<name>` lists revisions, and `kubectl rollout status deployment/<name>` watches a rollout (or rollback) to completion — useful in CI/CD to gate on successful rollout rather than assuming success.

### 17. What is a PodDisruptionBudget (PDB), and what problem does it solve?
A PDB declares the minimum number/percentage of Pods (`minAvailable`) or maximum that can be unavailable (`maxUnavailable`) for a given workload during *voluntary* disruptions — node drains for upgrades, cluster autoscaler scale-downs, `kubectl drain`. It prevents an operator (human or automated) from accidentally taking down too many replicas of a critical service at once during routine maintenance; it does not protect against *involuntary* disruptions like a node crashing unexpectedly.

### 18. Explain node affinity, Pod affinity/anti-affinity, and taints/tolerations.
**Node affinity** — schedule a Pod only onto (or preferentially onto) nodes matching certain labels (e.g., a specific instance type or availability zone), with `required` (hard constraint) or `preferred` (soft) variants. **Pod affinity/anti-affinity** — schedule a Pod relative to *other Pods'* labels — e.g., anti-affinity to spread replicas of the same app across different nodes/zones for resilience, or affinity to co-locate a cache with the app that uses it for latency. **Taints/tolerations** — a taint on a node repels Pods unless they explicitly "tolerate" it (e.g., dedicating GPU nodes to only GPU workloads by tainting them, and only GPU Pods carry the matching toleration) — the inverse relationship of affinity (nodes push away by default; tolerations opt a Pod back in).

### 19. What happens, step by step, when a node becomes unresponsive (NotReady)?
The node's `kubelet` stops sending heartbeats; after `node-monitor-grace-period` (default 40s) the node controller marks it `NotReady`. After `pod-eviction-timeout` (default 5 minutes) the controller starts evicting Pods from that node so their controllers (ReplicaSets, etc.) can recreate them elsewhere — but any Pod using node-local (non-network) storage, or a StatefulSet Pod, may not be immediately reschedulable since Kubernetes can't be sure the old Pod is truly dead (it might just be network-partitioned, still running, and could conflict/write data if a StatefulSet Pod with the same identity/volume started elsewhere) — hence StatefulSet Pods sometimes need manual force-deletion in a confirmed-dead-node scenario.

### 20. Explain how you'd debug a Pod stuck in `Pending`.
`kubectl describe pod <name>` shows Events at the bottom, which almost always name the exact reason: insufficient CPU/memory on all nodes matching constraints, unsatisfied node/pod affinity or taints, no PersistentVolume available matching a PVC's storage class/size/access mode, or (for a new node needed) the cluster autoscaler still provisioning capacity. Check `kubectl get nodes` for capacity/`Ready` status, and `kubectl describe node <candidate>` for `Allocatable` vs. already-requested resources if it looks like a bin-packing/capacity issue.

### 21. Explain how you'd debug a Pod stuck in `CrashLoopBackOff`.
`kubectl logs <pod> --previous` (crucial — the *current* container has already crashed and restarted, so plain `logs` may show nothing or the new attempt's brief startup output; `--previous` shows the crashed instance's actual output/stack trace). `kubectl describe pod` for the exit code and OOMKilled status. Common causes: application error/unhandled exception on startup, missing/misconfigured environment variable or config, failing to connect to a required dependency (DB, another service) with no retry/backoff, or a liveness probe configured too aggressively (killing a slow-starting-but-healthy app before it's ready) — check whether it's an app crash vs. a probe-induced restart via `describe`'s Events.

### 22. What is `ImagePullBackOff` and its common causes?
The kubelet failed to pull the specified container image and is backing off before retrying. Causes: typo in image name/tag, the tag/image genuinely doesn't exist in the registry, missing or incorrect `imagePullSecrets` for a private registry, registry rate limiting (notably Docker Hub's anonymous pull limits), or a network/DNS/firewall issue between the node and the registry.

### 23. What are Custom Resource Definitions (CRDs) and Operators?
A CRD extends the Kubernetes API with your own custom object types (e.g., a `PostgresCluster` resource), so you can `kubectl get postgresclusters` and manage them declaratively just like built-in objects. An Operator is a custom controller that watches instances of a CRD and implements the domain-specific logic to reconcile them — e.g., a Postgres Operator watching `PostgresCluster` objects and actually provisioning Pods/PVCs/Services, handling failover, backups, and version upgrades — effectively packaging human operational expertise for a specific piece of software into automated, Kubernetes-native code.

### 24. Explain Helm and what problem it solves.
Helm is a package manager for Kubernetes: a "chart" bundles a set of Kubernetes manifest templates plus a `values.yaml` for configurable parameters, so you can install/upgrade/rollback a complex multi-object application (e.g., a full monitoring stack with a dozen resources) as one versioned unit (`helm install`, `helm upgrade`, `helm rollback`) instead of hand-managing many raw YAML files and their inter-dependencies and templating by hand.

### 25. What is Horizontal Pod Autoscaling (HPA) vs. Vertical Pod Autoscaling (VPA) vs. Cluster Autoscaler?
**HPA** adjusts the *number* of Pod replicas based on observed metrics (CPU/memory utilization, or custom/external metrics like queue depth via metrics adapters). **VPA** adjusts the *resource requests/limits* of existing Pods (recommending or automatically applying different CPU/memory allocations) — usually not run in "auto" mode simultaneously with HPA on CPU/memory (they can fight each other) without careful configuration. **Cluster Autoscaler** adjusts the *number of nodes* in the cluster, adding nodes when Pods are Pending due to insufficient capacity, and removing underutilized nodes (after safely draining/rescheduling their Pods elsewhere, subject to PDBs).

### 26. Explain RBAC in Kubernetes: Role, ClusterRole, RoleBinding, ClusterRoleBinding.
A **Role** defines a set of permissions (verbs like get/list/watch/create/delete on specific resource types) scoped to a single namespace. A **ClusterRole** is the same but cluster-scoped (applies cluster-wide, or can be bound within a specific namespace too, useful for reusable permission sets). A **RoleBinding** grants a Role (or ClusterRole) to a user/group/ServiceAccount within one namespace. A **ClusterRoleBinding** grants a ClusterRole across the entire cluster. This is how you implement least-privilege — e.g., a CI ServiceAccount getting a Role that only permits deploying to its own namespace, not cluster-wide admin access.

### 27. What is a ServiceAccount, and how do Pods authenticate to the Kubernetes API?
A ServiceAccount is an identity for processes running *inside* the cluster (as opposed to human users) to authenticate to the API server. By default every Pod gets a token for its namespace's `default` ServiceAccount automatically mounted at a well-known path; that token (a projected, time-limited, audience-bound JWT in modern Kubernetes) is what an in-cluster client (like a controller or an app calling the K8s API to, say, list its own Pods) presents. RBAC bindings then determine what that ServiceAccount is actually authorized to do — best practice is a dedicated, minimally-privileged ServiceAccount per workload rather than relying on `default`.

### 28. What is etcd, and why is its health so critical to the whole cluster?
`etcd` is the distributed, strongly-consistent (Raft-based) key-value store holding the entire cluster's state — every object (Pods, Deployments, Secrets, everything) ultimately lives there; the API server is essentially a validating, authenticating façade in front of it. If `etcd` becomes unavailable or loses quorum, the API server can't read or write cluster state — existing running Pods keep running (kubelets operate somewhat independently once they have their assignment), but nothing can be scheduled, updated, or reconciled, effectively freezing the cluster's control plane. This is why `etcd` typically runs as an odd-numbered cluster (3 or 5 members) for quorum-based fault tolerance and gets frequent, tested backups.

### 29. How would you perform a zero-downtime cluster/node upgrade?
`kubectl drain <node> --ignore-daemonsets --delete-emptydir-data` cordons the node (marks unschedulable) and evicts its Pods (respecting PodDisruptionBudgets, so it won't violate availability guarantees — it will wait/retry if a PDB blocks eviction), letting their controllers reschedule replacements on other nodes; once drained, upgrade/replace the node, then `kubectl uncordon` to let it accept Pods again. At the cluster/control-plane level, managed Kubernetes offerings typically upgrade control-plane components with built-in HA (multiple API server/etcd replicas) so there's no single point of failure during the upgrade, then roll worker nodes through the same drain/replace/uncordon cycle, often via a managed node-group rolling upgrade.

### 30. Explain the difference between `kubectl apply` and `kubectl create`/`kubectl replace`.
`kubectl create` creates a new object and fails if it already exists (imperative, one-shot). `kubectl replace` fully overwrites an existing object with the given spec, failing if it doesn't already exist. `kubectl apply` is declarative: it computes a three-way diff (last-applied-config annotation, current live state, and your new desired state) and merges/patches accordingly — it creates the object if absent or updates just the changed fields if present, making it idempotent and the standard tool for GitOps-style workflows where the same manifest is repeatedly applied.

### 31. What is a sidecar container pattern, and give two real examples.
A sidecar runs alongside the main application container in the same Pod, sharing its network/volumes, to add cross-cutting functionality without modifying the main app. Examples: a service mesh proxy (Envoy in Istio) intercepting all inbound/outbound traffic for mTLS, retries, and observability without any app code changes; a log-shipping sidecar (Fluent Bit) tailing log files written to a shared volume by the main container and forwarding them to a central logging backend.

### 32. What is GitOps, and how does a tool like Argo CD or Flux fit into a Kubernetes deployment pipeline?
GitOps treats a Git repository as the single source of truth for a cluster's desired declarative state; a controller running *inside* the cluster (Argo CD, Flux) continuously watches that repo and reconciles the live cluster to match it (pull-based), rather than a CI pipeline pushing changes directly into the cluster (push-based). Benefits: every change is a Git commit (full audit trail, easy rollback via `git revert`), drift detection (the controller notices and can auto-correct if someone manually edited the live cluster out-of-band), and the cluster never needs to expose broad deploy credentials to external CI systems — only the in-cluster controller needs cluster access, and it only needs read access to Git.
