# Jenkins & CI/CD Tooling — Interview Questions

> Sourced/topic-checked against GeeksforGeeks, InterviewBit, KodeKloud, and DataCamp's Jenkins interview question lists. Complements `06-ci-cd-pipelines.md` (concepts) with tool-specific Jenkins questions.

---

### 1. What is Jenkins, and why is it still widely used despite newer CI/CD platforms (GitHub Actions, GitLab CI)?
Jenkins is a self-hosted, open-source automation server for building CI/CD pipelines, with an enormous plugin ecosystem (1,800+ plugins) covering nearly every tool/integration imaginable. It remains widely used because of that plugin ecosystem, its maturity (two decades of production use, extensive documentation/community knowledge), full control over the runtime environment (self-hosted, so no SaaS vendor lock-in or per-minute billing), and because many large, established organizations already have deep Jenkins investment (custom plugins, shared libraries) that isn't trivially migrated — newer SaaS-native tools (GitHub Actions, GitLab CI, CircleCI) are often preferred for greenfield projects for their simpler setup and tighter source-control integration.

### 2. What is a Jenkins agent (formerly "slave"), and what's the controller-agent architecture?
The Jenkins controller (formerly "master") schedules builds, manages configuration, and serves the UI/API — it doesn't necessarily execute build steps itself. Agents are separate machines/containers that connect to the controller and actually execute the build work, allowing horizontal scaling (many agents processing many builds in parallel) and workload isolation (specific agents configured with specific tools/OS/hardware, e.g., a Windows agent, a GPU agent, an agent inside a specific network segment for integration tests) — a job's `agent` directive specifies which agent(s) it can run on (a specific label, `any`, or `none` for a pipeline that only orchestrates other stages without needing its own executor).

### 3. What is a Jenkinsfile, and what's the difference between Declarative and Scripted pipeline syntax?
A Jenkinsfile defines a pipeline as code, committed to source control alongside the application (pipeline-as-code — see the CI/CD file). Declarative syntax uses a structured, opinionated format (`pipeline { agent {...} stages { stage('Build') { steps {...} } } }`) that's easier to read/validate and covers most common needs with less boilerplate. Scripted syntax is full Groovy code with more flexibility/power (arbitrary control flow, complex logic) but is harder to read/maintain and lacks some of Declarative's built-in validation and directives (`post`, `when`, `options`) — Declarative is the recommended default for new pipelines, with Scripted blocks (`script { ... }`) usable *within* a Declarative pipeline for edge cases needing extra logic.

### 4. What does the `agent` directive's possible values mean: `any`, `none`, `label`, `docker`?
`any` — run on any available agent. `none` — no top-level agent is allocated; each `stage` must then declare its own `agent` (used when different stages genuinely need different environments). `label 'my-label'` — run only on agents tagged with that specific label (used to route jobs to agents with required tools/hardware/network access). `docker { image 'node:18' }` — dynamically spin up a container from the specified image as the agent for that stage, guaranteeing a clean, consistent, disposable build environment matching exactly what's declared, rather than depending on whatever happens to be pre-installed on a static agent.

### 5. How do you securely handle credentials (API keys, passwords) in a Jenkins pipeline?
Never hardcode secrets in the Jenkinsfile (it's committed to source control, visible to anyone with repo access). Store them in Jenkins' built-in Credentials store (encrypted at rest) and reference them by ID in the pipeline via the `credentials()` helper or the `withCredentials` step, which injects them as environment variables/files only for the duration of the specific step that needs them and masks them in the build log output automatically — combined, where possible, with a real secrets manager (Vault) as the actual source of truth that Jenkins credentials are configured to fetch from dynamically, rather than storing long-lived static secrets directly in Jenkins itself.

### 6. What's the difference between Poll SCM and a webhook for triggering a Jenkins build, and which should you use?
Poll SCM has Jenkins periodically check the source repository (on a cron-like schedule) for new commits, triggering a build if changes are found — simple to set up, but wastes resources on empty polls and adds latency (up to the polling interval) between a commit and the build starting. A webhook has the source control platform (GitHub, GitLab) actively notify Jenkins immediately when a push/PR event happens, triggering the build instantly with no polling overhead — webhooks are the preferred approach whenever Jenkins is network-reachable from the SCM platform (webhooks require an inbound connection to Jenkins, which can be a blocker for a Jenkins instance behind a strict firewall with no public endpoint, in which case polling becomes the practical fallback).

### 7. What is a Jenkins Shared Library, and why use one?
A Shared Library is reusable Groovy pipeline code (common steps, functions, or entire pipeline templates) stored in its own separate source repository and imported into any Jenkinsfile (`@Library('my-shared-lib') _`). It solves the problem of duplicated pipeline logic across many projects/teams (e.g., a standardized "build, scan, deploy" sequence every team should follow) — centralizing it means a fix or improvement to the shared logic propagates to every consuming pipeline by updating the library version, rather than needing to manually edit dozens of individual Jenkinsfiles.

### 8. Explain the `when` directive and give a practical use case.
`when` conditionally controls whether a `stage` executes, based on an expression (branch name, environment variable, a previous stage's outcome, a custom boolean expression). Practical use case: `when { branch 'main' }` on a "Deploy to Production" stage, so that stage only runs for builds of the `main` branch — feature-branch builds run the earlier build/test stages but skip production deployment entirely, all within a single shared pipeline definition rather than needing separate pipeline files per branch type.

### 9. What is the `input` step, and how do you implement a manual approval gate in a pipeline?
`input` pauses pipeline execution and waits for a human to approve (or reject/provide parameters) via the Jenkins UI before continuing — implementing a manual approval gate (e.g., "approve before deploying to production") directly within the pipeline-as-code definition, rather than as an external, undocumented process. It's commonly combined with `timeout` (so a pipeline doesn't hang indefinitely waiting for an approval that never comes) and restricted to specific authorized approvers via Jenkins' role-based access control.

### 10. What does the `parallel` block do, and when would you use it?
`parallel` runs multiple stages/branches of a pipeline concurrently instead of sequentially — e.g., running unit tests, a linter, and a security scan simultaneously rather than one after another, since they're independent of each other, significantly reducing total pipeline duration. Each parallel branch runs on its own agent/executor (or the same one, depending on configuration), and the pipeline typically only proceeds past the `parallel` block once all branches complete (or fails fast if `failFast: true` is set and any branch fails).

### 11. What's the difference between a Freestyle project and a Pipeline job in Jenkins?
A Freestyle project is configured entirely through the Jenkins UI (a form-based, point-and-click job definition) — simple for basic use cases, but the configuration lives only in Jenkins' internal state, not in source control, making it hard to version, review, or reproduce/migrate. A Pipeline job is defined as code (a Jenkinsfile in source control) — reviewable, versioned alongside the application, and far more expressive for complex multi-stage workflows (parallelism, conditional logic, shared libraries) — Pipeline jobs are the modern standard; Freestyle is mostly encountered in legacy setups.

### 12. A new commit was pushed to your repository, but Jenkins didn't trigger a build. How do you troubleshoot this?
Check whether the trigger mechanism is webhook-based or polling-based first — for a webhook, check the SCM platform's webhook delivery log (GitHub shows recent webhook deliveries and their response codes) to see if the webhook actually fired and what Jenkins responded (a network/firewall issue between GitHub and Jenkins, or an expired/misconfigured webhook secret, are common causes); for polling, verify the poll schedule/cron syntax is correct and check "Poll Log" in the job's build history. Also check basic configuration: is the branch that received the commit actually the one the job is configured to watch, and are there any recent Jenkins system log errors around the time of the push (Jenkins itself down/restarting, or a plugin failure)?

### 13. Your Jenkins pipeline job is producing inconsistent results (sometimes passes, sometimes fails, with no code change). How do you approach this?
This is Jenkins' version of the general flaky-test/flaky-CI problem (see the CI/CD file) — check whether the pipeline is genuinely running on the same agent each time or bouncing between different agents with potentially different tool versions/environment configuration (a classic hidden cause of "works sometimes" in a multi-agent Jenkins setup); check for actual test flakiness (timing/race conditions in tests themselves) versus infrastructure flakiness (an external dependency, a shared resource contested by concurrently-running jobs on the same agent); and check if the job relies on any non-idempotent or order-dependent state left over from a previous build on the same agent workspace (Jenkins reuses agent workspaces by default unless configured to clean them, which can leak state between builds).

### 14. What is Jenkins Configuration as Code (JCasC), and what problem does it solve?
JCasC lets you define Jenkins' own system-level configuration (security settings, installed plugins' configuration, credentials references, agent definitions) declaratively in a YAML file, rather than through manual UI clicks. This solves the classic "snowflake Jenkins instance" problem — a Jenkins controller manually configured over years through the UI becomes an undocumented, unreproducible, hard-to-disaster-recover piece of infrastructure; JCasC makes the controller's own configuration reviewable, versioned, and reproducible (spin up an identical Jenkins instance from the same YAML) — applying the same Infrastructure-as-Code philosophy to the CI tool itself, not just the pipelines it runs.

### 15. What's the difference between Continuous Delivery and Continuous Deployment in the context of a Jenkins pipeline specifically?
(See also the CI/CD file's general definitions.) In Jenkins terms, Continuous Delivery typically means the pipeline runs all the way through building, testing, and packaging a deployable artifact automatically, but the final "deploy to production" stage is gated by an `input` step requiring manual approval. Continuous Deployment removes that manual gate entirely — a pipeline that passes every automated stage deploys straight to production with no human in the loop, requiring a very high level of confidence in the automated test/quality gates (comprehensive test coverage, robust automated rollback) since there's no human checkpoint left to catch a bad release before it ships.

### 16. How would you design a Jenkins pipeline to deploy to Kubernetes?
Stages typically: checkout code → build and unit test → build a container image → push the image to a registry (tagged with the commit SHA or a semantic version, never `:latest` — see the Docker file) → run a security/vulnerability scan on the image → update the Kubernetes manifests (or a Helm chart's values) to reference the new image tag → apply the change to the cluster (`kubectl apply`, `helm upgrade`, or — in a GitOps setup — commit the manifest change to a Git repo that Argo CD/Flux watches, rather than Jenkins applying directly, keeping cluster-write credentials out of Jenkins entirely) → run a post-deploy smoke test → optionally, an `input` gate before production if not using full Continuous Deployment.

### 17. What is the Jenkins CLI and the Jenkins REST API used for, and how do they differ from the web UI?
Both let you interact with Jenkins programmatically instead of manually through the browser — useful for scripting routine operations (triggering builds, fetching job status/console output, managing configuration) as part of other automation, or for integrating Jenkins actions into external tools/dashboards. The CLI is invoked via a downloadable jar over SSH or HTTP and is convenient for shell-script-style automation; the REST API returns structured JSON/XML and is better suited for programmatic integration from other applications/services. Both require proper authentication/authorization just like the UI, and should be used with credentials scoped no more broadly than necessary (see the least-privilege discussion in the security file).

### 18. What is a Jenkins "fingerprint," and what is it used for?
A fingerprint is a checksum Jenkins records for a specific file (commonly a build artifact) that lets it track that exact file's usage and lineage across multiple jobs/builds — e.g., "this exact jar file, built by job A build #42, was later consumed and deployed by job B build #17." This is useful for traceability in complex multi-job pipelines (which upstream build actually produced the artifact currently running in a given downstream deployment) without needing to manually correlate build numbers and timestamps.

### 19. Compare Jenkins to GitHub Actions/GitLab CI at a high level — what's the core architectural difference?
Jenkins is self-hosted infrastructure you provision, scale, and maintain yourself (controller + agents), giving full control but requiring ongoing operational ownership (patching, scaling, securing the Jenkins instance itself). GitHub Actions/GitLab CI are SaaS-native, tightly integrated directly into the source-control platform's own UI/permissions/webhooks with zero infrastructure to manage (using their hosted runners, though self-hosted runners are also an option for both) — pipeline configuration lives as YAML directly in the repo with less setup friction, at the cost of less flexibility for highly custom/legacy environments and a different (usage-based) cost model compared to Jenkins' "you already own the hardware" model.
