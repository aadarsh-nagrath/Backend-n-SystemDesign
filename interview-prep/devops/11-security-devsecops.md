# Security & DevSecOps — DevOps Interview Questions

---

### 1. What is "shift-left security," and why has it become a standard DevOps practice?
Shift-left means moving security checks earlier in the development lifecycle (into the IDE, pre-commit hooks, and CI pipeline) rather than only at the end (a pre-release security audit) or after deployment. It's standard practice because bugs/vulnerabilities are dramatically cheaper to fix the earlier they're caught (a flagged issue in a PR takes minutes to fix; the same issue found in production after a breach can cost incident response, customer trust, and regulatory exposure) and it scales security review across every change instead of bottlenecking on a small central security team reviewing everything at the end.

### 2. Explain the principle of least privilege and give a concrete infrastructure example.
Grant an identity (user, service, role) only the minimum permissions necessary to perform its function, nothing more "just in case." Example: a CI pipeline's deployment role should have permission to deploy to its specific target environment/namespace only — not organization-wide admin access — so that if the CI credentials are ever compromised (a common real-world breach vector), the blast radius is limited to what that pipeline actually needed, not the entire infrastructure.

### 3. What is defense in depth?
Layering multiple independent security controls so that a failure of any single layer doesn't result in a full compromise — e.g., network segmentation (private subnets) + security groups + application-level authentication + encryption at rest + audit logging + intrusion detection, rather than relying on any one of these alone (like assuming a firewall is sufficient and skipping application-level auth). If an attacker bypasses one layer, subsequent layers still need to be defeated.

### 4. What's the difference between authentication and authorization?
Authentication (AuthN) verifies *who* you are (login, API key, certificate, token validation). Authorization (AuthZ) determines *what* an already-authenticated identity is allowed to do (permissions/roles/policies). A system can authenticate someone correctly and still (correctly) deny them an action they're authenticated but not authorized to perform — these are distinct checks and conflating them is a common source of security bugs (e.g., checking only "is this a valid logged-in user" and forgetting to also check "is this user allowed to access *this specific* resource," leading to IDOR vulnerabilities).

### 5. What is an IDOR (Insecure Direct Object Reference) vulnerability?
An IDOR occurs when an application exposes a direct reference to an internal object (e.g., `/api/orders/1234`) and only checks that the requester is authenticated, but fails to verify they're *authorized* to access that specific object (order 1234 belongs to a different user) — letting an attacker simply change the ID in the URL/request to access or modify other users' data. The fix is always enforcing an object-level authorization check (does this authenticated user own/have permission for this specific resource ID) server-side on every access, never relying on IDs being "hard to guess."

### 6. Explain the OWASP Top 10 at a high level (name several and what they mean).
A regularly updated list of the most critical web application security risks. Notable/recurring ones: **Broken Access Control** (missing/incorrect authorization checks, includes IDOR); **Injection** (SQL/NoSQL/command injection — untrusted input executed as code/query); **Cryptographic Failures** (weak/missing encryption of sensitive data in transit or at rest); **Security Misconfiguration** (default credentials, verbose error messages leaking internals, unnecessary features enabled); **Vulnerable and Outdated Components** (using dependencies with known CVEs); **Identification and Authentication Failures** (weak session management, credential stuffing susceptibility); **Server-Side Request Forgery (SSRF)** (tricking a server into making requests to unintended internal/external destinations on the attacker's behalf).

### 7. What is SQL injection, and how do you prevent it?
SQL injection occurs when untrusted user input is concatenated directly into a SQL query string, letting an attacker inject their own SQL logic (e.g., `' OR '1'='1` to bypass a login check, or `; DROP TABLE users;--` to destroy data). Prevention: always use parameterized queries/prepared statements (the query structure and the data are sent to the database separately, so input can never be interpreted as SQL syntax) or a well-vetted ORM that does this correctly under the hood — never build queries via string concatenation/interpolation of user input, and apply least-privilege database accounts as a defense-in-depth backstop.

### 8. What is Cross-Site Scripting (XSS), and the difference between stored, reflected, and DOM-based XSS?
XSS lets an attacker inject malicious JavaScript that executes in another user's browser session, in the security context of the vulnerable site (able to steal session cookies/tokens, perform actions as that user). **Stored** — the malicious script is saved server-side (e.g., in a comment field) and served to every subsequent visitor. **Reflected** — the script is embedded in a request (e.g., a URL parameter) and immediately reflected back in the response without proper sanitization, requiring a victim to click a crafted malicious link. **DOM-based** — the vulnerability exists entirely in client-side JavaScript that unsafely inserts untrusted data into the DOM, without the malicious payload ever necessarily touching the server. Prevention across all three: context-appropriate output encoding/escaping of any untrusted data rendered into HTML/JS/URLs, a strict Content Security Policy, and using frameworks that auto-escape by default rather than raw string concatenation into HTML.

### 9. What is CSRF (Cross-Site Request Forgery), and how do anti-CSRF tokens prevent it?
CSRF tricks a victim's browser, which is already authenticated to a site (via cookies), into unknowingly submitting a request to that site from a different, malicious page the victim visits — the browser automatically attaches the victim's cookies, so the request looks legitimate to the server. Anti-CSRF tokens are unique, unpredictable values embedded in legitimate forms/requests by the server and required to be echoed back on state-changing requests; a malicious third-party page has no way to know or include this token, so its forged request is rejected. Modern browsers' `SameSite` cookie attribute (set to `Strict` or `Lax`) provides significant additional/alternative protection by preventing cookies from being sent on most cross-site requests in the first place.

### 10. What is the difference between encryption at rest and encryption in transit?
Encryption in transit (TLS) protects data as it moves across a network from interception/tampering by anyone positioned between the two endpoints. Encryption at rest protects data stored on disk (databases, backups, object storage) from being read if the underlying storage medium/backup is stolen, improperly accessed, or a misconfigured access-control leak exposes the raw files — the two are independent and both are typically required for a complete data-protection posture (transit-only encryption doesn't help if a stolen unencrypted disk snapshot leaks the data).

### 11. What is symmetric vs. asymmetric encryption, and where is each used?
Symmetric encryption uses the same key to encrypt and decrypt (fast, efficient for bulk data — AES is the standard) but requires securely sharing that key with anyone who needs to decrypt. Asymmetric encryption uses a public/private key pair (data encrypted with the public key can only be decrypted with the corresponding private key, or vice versa for signing) — solves the key-distribution problem (the public key can be shared openly) but is computationally much slower. In practice, TLS uses asymmetric crypto only briefly during the handshake (to securely agree on a shared secret without ever transmitting it) and then switches to fast symmetric encryption for the actual bulk data transfer — combining the strengths of both.

### 12. What is a JWT, and what are its security pitfalls?
A JWT (JSON Web Token) is a signed (and optionally encrypted) token encoding claims (e.g., user ID, expiry, roles) that a server can verify without a database lookup, by checking its signature. Pitfalls: accepting the `alg` field from the token itself without restricting to an expected algorithm (an attacker can set `alg: none` or trick a server verifying with an RSA public key into treating that key as an HMAC secret — the classic "algorithm confusion" attack); storing sensitive data in the payload (it's base64-encoded, not encrypted, and trivially readable by anyone who has the token); not enforcing short expiry combined with a real revocation mechanism (a stateless JWT can't be "logged out" server-side unless you maintain some form of denylist/short-lived-token-plus-refresh pattern); and storing tokens insecurely client-side (e.g., in `localStorage`, which is readable by any XSS payload, vs. an `HttpOnly` cookie).

### 13. What is a secrets manager (Vault, AWS Secrets Manager), and why not just use environment variables or config files for secrets?
A secrets manager centrally stores, encrypts, audits access to, and can automatically rotate sensitive credentials, issuing them to applications at runtime rather than having them baked into config files, environment variables, or source code (all of which tend to end up in backups, logs, shell history, or version control by accident). Centralization also means rotating a compromised credential once updates it everywhere it's consumed, and every access is logged/auditable — answering "who/what accessed this secret and when" is nearly impossible with scattered static config files.

### 14. What is a WAF (Web Application Firewall), and what does it protect against that a network firewall doesn't?
A WAF inspects HTTP(S) traffic at the application layer, filtering requests based on patterns associated with common web attacks (SQL injection payloads, XSS patterns, known bad bot signatures, abnormal request rates) — a network firewall (operating at L3/L4) has no visibility into HTTP request bodies/headers/application logic and can't distinguish a malicious API call from a legitimate one if both use an allowed port/protocol. A WAF is a defense-in-depth layer, not a substitute for fixing the underlying application vulnerabilities it's compensating for.

### 15. What is a supply chain attack, and give a real category of example relevant to CI/CD.
A supply chain attack compromises software indirectly, through a trusted dependency, build tool, or distribution channel rather than attacking the target directly — e.g., a compromised open-source package (typosquatting a popular package name, or an attacker gaining access to a maintainer's account and publishing a malicious version), a compromised CI/CD pipeline injecting malicious code during the build step, or a compromised base container image. Mitigations: dependency pinning + lockfiles, SCA scanning for known-bad/typosquatted packages, verifying package signatures/checksums, minimizing third-party CI plugin usage and auditing their permissions, and generating/verifying SBOMs (Software Bill of Materials) and build provenance attestations (e.g., SLSA framework) to know exactly what's in a shipped artifact and how it was built.

### 16. What is an SBOM (Software Bill of Materials), and why do organizations increasingly require them?
An SBOM is a structured, machine-readable inventory of every component (direct and transitive dependencies, their versions) that makes up a software artifact. Organizations increasingly require them (and some regulations mandate them) so that when a new CVE is disclosed in a widely-used library, they can instantly query "which of our deployed artifacts include this exact vulnerable version" instead of manually auditing every codebase — dramatically speeding up incident response to supply-chain vulnerabilities (as famously demonstrated by the difficulty many organizations had determining their exposure during the Log4Shell vulnerability disclosure).

### 17. What is a zero-trust security model, and how does it differ from a traditional "perimeter" security model?
Traditional perimeter security assumes anything inside the network boundary (behind the firewall/VPN) is trusted, with most defense concentrated at the edge — once an attacker is inside (e.g., via a phished credential or compromised device), lateral movement is often easy. Zero-trust assumes no implicit trust based on network location alone — every request, whether from inside or outside the traditional perimeter, must be authenticated and authorized based on identity and context (device posture, location, behavior), typically enforced via strong service-to-service identity (mTLS), fine-grained per-request authorization, and continuous verification rather than a one-time "you're on the VPN, you're trusted" check.

### 18. What's the difference between hashing and encryption, and why must passwords be hashed, not encrypted?
Encryption is reversible (given the right key, you can decrypt back to the original plaintext) — appropriate for data you need to retrieve later. Hashing is a one-way function (computationally infeasible to reverse) that produces a fixed-size digest — appropriate for passwords, since the system never needs to "read back" the original password, only verify a submitted one matches (by hashing the input and comparing digests). If passwords were encrypted instead of hashed, anyone who obtained the decryption key (or the database plus a config/key leak) could recover every plaintext password at once — hashing means even a full database breach doesn't directly reveal passwords (though weak/unsalted hashing algorithms remain crackable via precomputed rainbow tables or brute force, which is why slow, salted algorithms like bcrypt/scrypt/Argon2 are required, not fast general-purpose hashes like MD5/SHA-256 alone).

### 19. Why is `bcrypt`/`scrypt`/`Argon2` preferred over plain SHA-256 for password hashing?
General-purpose hash functions like SHA-256 are designed to be *fast* (a property useful for checksums/data integrity, but a liability for password storage) — fast hashing means an attacker with a stolen hash database can attempt billions of guesses per second on modern hardware/GPUs. bcrypt/scrypt/Argon2 are deliberately slow and configurably "expensive" (adjustable work factor/memory cost), and incorporate a unique salt per password automatically, making both brute-force and precomputed rainbow-table attacks dramatically more expensive per guess — trading a few extra milliseconds of legitimate login latency for a massive increase in attacker cost per password guessed.

### 20. What is Principle of Least Privilege applied specifically to a compromised CI/CD credential scenario — how do you limit blast radius?
Scope CI credentials narrowly per pipeline/environment (a pipeline deploying to staging shouldn't hold production credentials at all, let alone broad admin access); prefer short-lived, dynamically issued credentials (OIDC federation to cloud providers, issuing a token valid only for the duration of that specific pipeline run) over long-lived static secrets stored in CI configuration; separate credentials per environment so a leak in one pipeline/environment can't be used to pivot into others; and maintain audit logging of what each credential/role actually did, so a compromise can be detected and its actual impact scoped quickly rather than assuming worst-case across all systems.

### 21. What is a security misconfiguration, and give three common real-world examples in cloud/infra.
A security misconfiguration is any insecure setting left in place, usually a default or an oversight rather than a code vulnerability per se. Common examples: a public S3 bucket/storage container accidentally left world-readable (or worse, world-writable) containing sensitive data; default credentials left unchanged on a database or admin panel; overly permissive security group rules (`0.0.0.0/0` allowed on a database port instead of restricted to specific application security groups); verbose error pages/stack traces exposed in production, leaking internal implementation details/file paths useful to an attacker reconnoitering the system.

### 22. What's the difference between vulnerability scanning and penetration testing?
Vulnerability scanning is automated, broad, and continuous — tools check for known CVEs, misconfigurations, and common weakness patterns across your systems on a schedule, producing a list of potential issues (with some false positives) quickly and cheaply. Penetration testing is manual (or semi-manual), goal-directed, and typically periodic — skilled testers actively attempt to exploit vulnerabilities (including chaining multiple minor issues into a serious compromise, and finding business-logic flaws automated scanners can't recognize), producing deeper, validated findings but at higher cost and lower frequency — the two are complementary, not substitutes for each other.
