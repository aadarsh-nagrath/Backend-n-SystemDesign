# AWS DevOps Tooling — Real Interview Questions (CodePipeline, CodeBuild, CodeDeploy & More)

> Sourced/topic-checked against igmGuru's and Taggd's AWS DevOps interview question lists. Supplements `07-aws-cloud.md` (core AWS architecture) with the CI/CD-and-operations-tooling side of AWS specifically asked in "AWS DevOps Engineer" interviews.

---

### 1. Walk through AWS's native CI/CD toolchain: CodeCommit, CodeBuild, CodeDeploy, CodePipeline, CodeStar.
**CodeCommit** — a managed Git repository service (AWS's now-largely-deprecated answer to GitHub/GitLab; many teams now just use GitHub/GitLab and integrate it with the rest of this toolchain instead). **CodeBuild** — a managed build service that compiles code, runs tests, and produces artifacts, defined via a `buildspec.yml` file, billed per build-minute with no servers to manage. **CodeDeploy** — automates deploying application code/artifacts to EC2, on-prem servers, Lambda, or ECS, supporting in-place and blue/green deployment strategies with automatic rollback on failure. **CodePipeline** — the orchestrator tying these (and third-party tools) together into a defined multi-stage release pipeline (source → build → test → deploy), visualizing the whole flow and managing transitions/approvals between stages. **CodeStar** — a higher-level project-management layer that quickly provisions a CodeCommit/CodeBuild/CodeDeploy/CodePipeline stack together for a new project from a template, mainly useful for getting started quickly rather than for fine-grained pipeline control.

### 2. How does CodeDeploy's blue/green deployment work on EC2 specifically?
CodeDeploy provisions (or uses) a second, parallel set of EC2 instances ("green," the new version) alongside the currently-live "blue" set, deploys the new application revision to green, runs configured validation/health checks, and then shifts traffic (via an associated load balancer's target groups) from blue to green — either all at once or gradually, depending on the configured deployment configuration. If validation fails or an alarm triggers during the shift, CodeDeploy can automatically roll back by shifting traffic back to the original blue instances, which are kept running (not terminated) for a configurable period specifically to make instant rollback possible.

### 3. What is a `buildspec.yml` file, and what are its main phases?
It's CodeBuild's build definition file (analogous to a Jenkinsfile or GitHub Actions workflow YAML), specifying phases: `install` (install runtime dependencies/tools), `pre_build` (steps before the main build, e.g., logging into a container registry, running tests), `build` (the actual compile/build commands), and `post_build` (steps after, e.g., pushing a built container image, generating final artifacts) — plus an `artifacts` section defining what output files should be captured and passed to the next pipeline stage.

### 4. What's the difference between AWS Elastic Beanstalk and CloudFormation, and when would you choose each?
Elastic Beanstalk is a Platform-as-a-Service abstraction — you upload application code/a container image and describe the environment (runtime, instance type, scaling settings), and Beanstalk automatically provisions and manages the underlying EC2 instances, load balancer, and Auto Scaling Group for you, handling most operational details. CloudFormation (like Terraform, but AWS-native) is a general-purpose Infrastructure-as-Code tool where you explicitly declare every resource (VPC, subnets, EC2, RDS, IAM roles, everything) in a template — far more control and flexibility, but you're responsible for the entire architecture design. Choose Beanstalk for a straightforward web application that fits its opinionated model and where minimizing operational overhead matters most; choose CloudFormation (or Terraform) when you need custom architecture, fine-grained control, or are integrating many services beyond what Beanstalk's abstraction assumes.

### 5. What is AWS Systems Manager, and what are a few of its most commonly used capabilities for a DevOps engineer?
Systems Manager is a suite of operational tools for managing EC2 (and hybrid on-prem) instances at scale. Key capabilities: **Parameter Store** (a simple, free key-value store for configuration/secrets, often used as a lighter-weight alternative to Secrets Manager for non-rotating configuration values); **Session Manager** (secure shell access to an instance without needing SSH keys, bastion hosts, or open inbound ports — access is brokered entirely through IAM and the Systems Manager agent, and every session is logged/auditable); **Run Command** (execute a command/script across many instances simultaneously without manually SSHing into each); **Patch Manager** (automate OS patching across a fleet on a defined schedule).

### 6. What is AWS CloudTrail, and how does it differ from CloudWatch?
CloudTrail records *who did what* — an audit log of every API call made against your AWS account (which IAM identity called which action on which resource, from what IP, when), essential for security auditing, compliance, and incident forensics ("who deleted this S3 bucket, and when"). CloudWatch is about *system behavior/performance* — metrics, logs, and alarms about how your resources are actually running (CPU utilization, error rates, application logs) — the two are complementary but answer fundamentally different questions: CloudTrail is a security/compliance audit trail of control-plane actions, CloudWatch is operational observability of running workloads.

### 7. What is the "dogpile effect" in a DevOps/caching context, and how do you avoid it?
The dogpile effect (also called a cache stampede or thundering herd — see the caching file) occurs when a popular cached value expires and a large number of concurrent requests simultaneously "pile on" to recompute/refetch it from the backend at once, potentially overwhelming it. Avoidance techniques: staggered/jittered expiration times (so not every cache entry expires at the exact same moment), a lock/single-flight mechanism ensuring only one request recomputes a given expired value while others wait for that result, or serving stale content while asynchronously refreshing in the background (stale-while-revalidate).

### 8. What is session affinity (sticky sessions), and why is it generally discouraged in a scalable architecture?
Session affinity configures a load balancer to consistently route a given client's requests to the same backend instance (based on a cookie or source IP), typically because that instance is holding some client-specific state in memory. It's generally discouraged because it undermines the benefits of horizontal scaling and load balancing (uneven load if some "sticky" clients are much heavier than others, and losing that specific instance loses that client's in-memory state entirely) — the preferred alternative is designing the application to be stateless (see the backend fundamentals file), externalizing session state to a shared store (Redis/DynamoDB) so any instance can serve any request, making sticky sessions unnecessary.

### 9. What is SSL/TLS termination, and where does it typically happen in an AWS architecture?
TLS termination is the point where encrypted HTTPS traffic is decrypted back to plain HTTP — commonly done at the load balancer (an AWS ALB/NLB with an attached ACM certificate) rather than at each individual backend instance, so backend instances only need to handle simpler plain HTTP internally (within the trusted private VPC network), and certificate management/rotation is centralized at the load balancer rather than needing to be replicated across every instance. Some architectures instead re-encrypt traffic between the load balancer and backend ("TLS passthrough" or "end-to-end encryption") when compliance requirements mandate encryption all the way to the actual application, at the cost of more certificate management complexity.

### 10. What are common DevOps "anti-patterns" an interviewer might ask you to identify?
Manually making changes directly in the console/production instead of through Infrastructure as Code (causing drift — see the Terraform file); deploying infrequently in large, risky batches instead of small, frequent, low-risk changes; treating monitoring/alerting as an afterthought added only after an incident rather than built in from the start; having no rollback strategy and treating every deployment as effectively irreversible; siloed "ops throws it over the wall to dev" (or vice versa) workflows without shared ownership/on-call; and skipping automated testing in the name of shipping faster, which reliably backfires as manual QA and incident response costs grow faster than the time "saved."

### 11. How does AWS CloudFront improve web application performance, and what's a common misconfiguration that reduces its effectiveness?
(See also the CDN question in the networking file.) CloudFront caches content at edge locations near users, reducing latency and origin load. A common misconfiguration: overly restrictive or incorrect cache-control headers/behaviors causing a low cache hit ratio (e.g., forwarding all query strings/cookies to the origin for cache-key purposes when they don't actually vary the response, fragmenting the cache into many near-duplicate entries) — monitoring the actual cache hit ratio (via CloudFront's own metrics) and tuning cache behaviors/TTLs accordingly is a routine but important CloudFront optimization task.

### 12. What is AWS QuickSight, and where does it fit in a DevOps engineer's toolkit (if at all)?
QuickSight is AWS's managed business intelligence/dashboarding service for visualizing data from sources like S3, Redshift, and RDS. It's less central to core DevOps infrastructure work than CloudWatch (which is the primary observability tool for operational metrics/logs) but can come up when a DevOps team is asked to build cost-reporting dashboards, capacity-planning visualizations, or business-metric dashboards drawing from operational data lakes — worth knowing it exists and its general purpose, even if it's not a daily-driver DevOps tool the way CloudWatch/CloudTrail are.

### 13. How would you design disaster recovery for a critical application specifically using AWS-native services, considering data residency requirements (e.g., needing DR within India)?
Use Multi-AZ deployment for the primary region's database (RDS/Aurora Multi-AZ) as the first layer of resilience against a single data-center failure. For DR against a full regional outage while respecting data-residency constraints, replicate to a second AWS region *within the same country/regulatory jurisdiction* if the provider offers multiple regions there (rather than defaulting to a globally "nearest" region that might violate residency requirements), using cross-region read replicas or Aurora Global Database for the data layer, S3 Cross-Region Replication for object storage, and Route 53 health-check-based failover routing to redirect traffic to the DR region if the primary becomes unavailable — with the specific RTO/RPO targets (see the SRE file) driving whether this is a warm-standby or a more expensive active-active setup.

### 14. At a conceptual level, what does "using AWS services to replace traditional message queues for high-scale data ingestion" mean, and what services are typically involved?
Instead of (or in addition to) a self-managed message broker, high-scale ingestion pipelines commonly use **Kinesis Data Streams** (a managed, sharded, real-time streaming service — conceptually similar to Kafka, suited for high-throughput ordered ingestion with multiple independent consumers) or **Managed Streaming for Kafka (MSK)** (a fully-managed Kafka offering, for teams wanting Kafka's exact semantics/ecosystem without operating the cluster themselves) alongside **SQS/SNS** for simpler queue/pub-sub needs (see the AWS cloud file's Q16) — the choice depends on whether you need Kafka-style replayable, partitioned log semantics at very high throughput (Kinesis/MSK) versus simpler point-to-point or fan-out messaging (SQS/SNS).

### 15. What's the difference between AWS X-Ray and the AWS Distro for OpenTelemetry (ADOT), and which should a new project use?
X-Ray is AWS's own proprietary distributed tracing service, tightly integrated with other AWS services (Lambda, API Gateway auto-instrument easily) but locking your instrumentation into AWS-specific SDKs/format. ADOT is AWS's own distribution/packaging of the vendor-neutral OpenTelemetry project (see the observability file), letting you instrument once using open standards and export traces to X-Ray, or to any other OpenTelemetry-compatible backend, without being locked in. For a new project, ADOT is generally the more future-proof choice specifically because it avoids proprietary lock-in while still fully supporting export to X-Ray if that's your chosen backend today — you get the AWS integration without giving up the ability to switch backends later.
