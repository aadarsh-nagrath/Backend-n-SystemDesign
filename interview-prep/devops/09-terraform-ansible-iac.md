# Infrastructure as Code: Terraform & Ansible — DevOps Interview Questions

---

### 1. What is Terraform, and how does its declarative model differ from an imperative script?
Terraform lets you declare the *desired end state* of infrastructure (e.g., "there should be an EC2 instance of type t3.medium with these tags") in HCL, and its engine computes and executes whatever create/update/delete operations are needed to reconcile real infrastructure to match — you don't write the step-by-step "how." An imperative script (a bash script calling the AWS CLI) instead specifies exact sequential actions to take, with no built-in awareness of current state, no automatic diffing, and no idempotency guarantee unless you hand-code it.

### 2. Explain the Terraform workflow: `init`, `plan`, `apply`, `destroy`.
`terraform init` downloads required providers/modules and sets up the backend (where state is stored). `terraform plan` computes and displays the diff between current state and desired configuration — an execution plan of what would be created/changed/destroyed, without making any real changes (critical for review before applying). `terraform apply` executes that plan against real infrastructure and updates the state file. `terraform destroy` tears down all resources Terraform manages in that configuration/state.

### 3. What is Terraform state, and why is it critical (and dangerous if mishandled)?
The state file (`terraform.tfstate`) is Terraform's record of what real-world resources it's actually created and their current attributes — it's how `plan` computes a diff (comparing config vs. state vs., ideally, a refresh against real infrastructure) rather than needing to enumerate all cloud resources on every run. It's dangerous if mishandled because: it can contain sensitive data (some resource attributes, like generated passwords, in plaintext) so it must be stored securely; if lost or corrupted, Terraform loses track of what it manages (risking orphaned resources or destructive "recreate everything" plans); and if two people apply concurrently against local state files, changes can conflict/overwrite each other's tracked state.

### 4. Why should Terraform state be stored remotely (e.g., S3 + DynamoDB, or Terraform Cloud) instead of locally?
Remote state enables team collaboration (everyone's `plan`/`apply` reads/writes the same shared source of truth instead of divergent local files), state locking (e.g., a DynamoDB lock table prevents two people from running `apply` concurrently and corrupting state or applying conflicting changes), durability/versioning (S3 versioning lets you recover a previous state if something goes wrong), and keeps sensitive state content out of individual laptops/version control (never commit `.tfstate` to Git).

### 5. What is a Terraform module, and why use them?
A module is a reusable, parameterized package of Terraform configuration (e.g., "a standard VPC with public/private subnets across 3 AZs") that can be instantiated multiple times with different inputs (dev VPC, staging VPC, prod VPC) — promoting DRY infrastructure code, consistency across environments/teams, and encapsulating best practices/organizational standards behind a simple interface so consumers don't need to know every underlying resource's configuration details.

### 6. Explain `terraform import` and when you'd need it.
`terraform import` brings an existing resource (created manually or by another tool, outside Terraform) under Terraform's management by associating it with a resource block in your configuration and recording it in state — without recreating or modifying the actual resource. Needed when adopting Terraform for previously-manually-managed infrastructure, or recovering a resource that was accidentally removed from state without being destroyed in reality.

### 7. What's the difference between a Terraform "resource" and a "data source"?
A `resource` block declares something Terraform should create, manage, and be able to destroy. A `data` block reads and references information about something that already exists (managed by Terraform or not — e.g., looking up the latest AMI ID, or referencing a VPC created in a completely separate Terraform configuration/state) without Terraform ever managing its lifecycle.

### 8. What happens when you change an immutable attribute of a resource (e.g., an EC2 instance's AMI) in Terraform config?
Terraform can't modify certain attributes in place (the underlying cloud API doesn't support changing them on an existing resource) — for these, `plan` shows a "destroy and re-create" action: the old resource is deleted and a new one created with the new configuration. This can be dangerous for stateful resources (a database) if not anticipated, which is why Terraform supports `lifecycle { create_before_destroy = true }` (provision the replacement before destroying the old one, useful for zero-downtime replacement behind a load balancer) and `prevent_destroy = true` (a safety guard that errors out `plan`/`apply` if it would destroy a critical resource).

### 9. What is "drift" in Terraform, and how do you detect/handle it?
Drift is when real infrastructure no longer matches Terraform's recorded state — typically caused by manual out-of-band changes (someone edited a security group rule directly in the AWS console). `terraform plan` (which refreshes state against real infrastructure first) will show the drift as a proposed change to revert it back to the declared configuration. Handling it means either updating the Terraform configuration to reflect the intentional manual change (if it should be kept) or applying to revert it (if it was an unauthorized/accidental change) — and, organizationally, restricting console/CLI write access so all changes flow through Terraform going forward to prevent recurring drift.

### 10. Explain Terraform workspaces and their limitation for managing multiple environments.
Workspaces let you maintain multiple named state files from the same configuration (e.g., `dev`, `staging`, `prod`), switched via `terraform workspace select`. The limitation: all workspaces share the exact same configuration code, so if environments need meaningfully different resource configurations (not just different variable values — e.g., prod needs Multi-AZ but dev doesn't), workspaces alone become awkward, and many teams instead use separate directories/configurations per environment (or a tool like Terragrunt) with shared modules, reserving workspaces for cases where environments truly are just parameter variations of identical infrastructure.

### 11. What is the difference between Terraform and Ansible, and can/should they be used together?
Terraform is primarily for *provisioning* infrastructure (creating the VMs, networks, databases, load balancers themselves) via a declarative, state-tracked model. Ansible is primarily for *configuration management* — installing software, managing config files, and orchestrating tasks on already-existing machines, via an imperative, mostly stateless, sequential playbook model (though it aims for idempotent tasks). A common pattern: Terraform provisions the infrastructure (including bootstrapping enough for Ansible to reach it, e.g., via SSH), then Ansible configures the software on top — though modern container/immutable-image approaches (bake configuration into the image with Packer, deploy immutable instances) have reduced how often teams need a separate configuration-management step after provisioning.

### 12. Explain Ansible's core concepts: inventory, playbook, task, module, role.
**Inventory** — the list of hosts (and groupings/variables) Ansible manages, static (an INI/YAML file) or dynamic (queried from a cloud provider API). **Playbook** — a YAML file defining an ordered set of plays (which hosts to target and what tasks to run on them). **Task** — a single action (e.g., "install a package," "copy a file," "restart a service"). **Module** — the actual unit of work a task invokes (e.g., the `apt`, `copy`, `service` modules) — Ansible ships hundreds of built-in modules covering most common operations. **Role** — a reusable, structured bundle of tasks/handlers/templates/variables/files (analogous to a Terraform module) for a specific piece of functionality (e.g., "install and configure nginx"), shareable across playbooks and projects.

### 13. Why is Ansible described as "agentless," and what does that mean operationally?
Ansible doesn't require any persistent daemon/agent installed on managed hosts — it connects over standard SSH (or WinRM for Windows), pushes small Python scripts (modules) to execute, and cleans up afterward. Operationally, this means lower overhead to start managing a new host (no agent installation/registration step, no agent process consuming resources or needing its own patching/security maintenance), and no agent-to-controller connectivity requirement beyond the control node being able to SSH to targets when a playbook actually runs.

### 14. What does "idempotent" mean for an Ansible task, and why does it matter?
An idempotent task, when run multiple times against the same target, produces the same end result and reports "unchanged" (no-op) if the desired state is already achieved, rather than blindly re-executing and potentially causing errors or unwanted side effects on repeat runs. Most built-in Ansible modules are idempotent by design (`apt: name=nginx state=present` checks if nginx is already installed before acting) — but a raw `shell`/`command` task calling an arbitrary CLI command is *not* automatically idempotent unless you add your own guard logic (`creates:`, `when:` conditions, or checking exit codes) — a very common Ansible interview/practical gotcha.

### 15. What is a Packer image, and how does it fit alongside Terraform?
Packer builds a machine image (an AMI, a Docker image, a VM template) from a declarative template — installing software, applying configuration, baking everything needed into an immutable image ahead of time. Terraform then provisions instances *from* that pre-built image, rather than provisioning a bare instance and configuring it live at boot/via Ansible every time — an "immutable infrastructure" pattern that trades slower image build time for much faster, more predictable, more reproducible instance launches (no configuration drift risk between "identical" instances, since they're all literally the same baked image).

### 16. What's the difference between mutable and immutable infrastructure, and what problem does immutability solve?
Mutable infrastructure is updated in place (SSH in, patch, update config, restart service on the *same* running server over its lifetime) — over months/years, small undocumented manual changes accumulate into "configuration drift," producing servers that are subtly different from each other and from what's documented ("snowflakes"), making failures hard to reproduce/debug. Immutable infrastructure never modifies a running instance after creation — any change (a new app version, a config update, an OS patch) is deployed by building an entirely new image/instance and replacing the old one wholesale (then destroying it), guaranteeing every instance of a given version is byte-for-byte identical and eliminating drift entirely, at the cost of needing fast, automated image-build and replacement pipelines.

### 17. How do you handle secrets in Terraform/Ansible code without committing them to version control?
Terraform: mark sensitive variables (`sensitive = true`, which redacts them from plan/apply CLI output — note it does *not* encrypt them in the state file, which must still be protected separately), source actual secret values from environment variables or a secrets manager data source (e.g., `aws_secretsmanager_secret_version`) rather than hardcoding them in `.tfvars` files committed to Git. Ansible: use Ansible Vault to encrypt sensitive variables/files at rest in the repository (`ansible-vault encrypt`), decrypted only at playbook run time with a vault password (itself ideally sourced from a secrets manager or a password prompt, not also committed).

### 18. Your `terraform apply` was interrupted midway (network drop, killed process). What do you do?
First, don't panic or immediately re-run blindly. Run `terraform plan` to see the current actual diff — Terraform's state tracks what completed before the interruption, so plan will show what's left to reconcile (some resources may have been created but not yet recorded, or partially applied) accurately in most cases. If state and reality have diverged (e.g., a resource was created in the cloud but the interruption happened before state was written), you may need `terraform import` to reconcile, or in rare cases manual state surgery (`terraform state rm`/`state mv`) — always back up the state file before manual edits, and prefer a remote backend with state locking specifically to reduce the chance of this scenario (locking prevents a *second* concurrent apply, but doesn't prevent a single apply itself from being interrupted).
